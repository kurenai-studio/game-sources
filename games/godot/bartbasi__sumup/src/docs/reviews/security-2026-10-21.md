## New finding

### SEC-06 (Low): near the ceiling, the exact fit test and the chain points take seconds, because pow2 is slow at those sizes and its cache thrashes

**Owner:** core-logic-dev (src/core/big_num.gd, src/core/core_rules.gd).

**Code.**
- `BigNum.pow2` (big_num.gd lines 57 to 74) builds 2^e by repeated schoolbook squaring in GDScript. A cold `pow2(65535)` takes 110 ms on this PC. Each call stores itself and every intermediate exponent of its recursion (about 10 entries for e near 65535) in `_pow2_cache`, which holds 64 entries and is cleared completely when full (line 71).
- `CoreRules._chain_fits` (core_rules.gd lines 276 to 290) takes the exact path when the score has 65,600 bits, that is a score of 2^65599 or more. The exact path sums `pow2(k)` for every tile of the chain (`_points_of`, line 261), and `bit_length` of a sum next to a power of two calls `pow2` again (big_num.gd lines 278 to 283).
- `RunRules.commit_chain` (run_rules.gd line 47) always sums `pow2(k)` for the chain, whatever the score.

A chain of tiles with many different exponents near 65535 needs more than 64 cache entries, so the cache is cleared during the sum and every new check starts cold.

**Steps to reproduce (done, desktop, Windows 11, timings from `Time.get_ticks_msec`).**
1. Board: a snake path through all 40 cells holding 65490, 65490, 65491, 65492 and so on up to 65528. Score 2^65599, which is inside the ceiling and loads (a run file with score 2^65600 minus 1 loads in 79 ms).
2. Drag the full snake as the board does: `joinable_cells` and `step_chain` at every step. Result: 88 seconds for the 40 steps, the worst single step 5.4 seconds. `is_valid_chain` on the full chain: 2.8 seconds. `commit_chain`: 5.7 seconds.
3. The same board with score 0 (fast path): the drag takes 5 ms, but `commit_chain` still takes 2.8 seconds, all of it `_points_of`.
4. A board of 20 pairs near 65535 with score 2^65600 minus 1: `has_valid_move` takes 1.3 seconds, and `BoosterRules.outcome` the same. Both run after every move and on resume.
5. With Bart's fixture or any board of exponents up to about 60, every step and commit took under 2 ms.

**Why it matters.** All of this runs on the main thread. A phone is slower than this PC, so a drag step or a commit on such a board would freeze the screen for several seconds, long enough for Android's "app isn't responding" dialog. It is not a hang: every operation ends, the run can still be played or ended, and memory stays small (at most 64 cached numbers of about 58 KB each). It can only come from a hand edited save. The board needs tiles near 2^65535, and the exact path needs a score of 2^65599 or more. Real play stays near 2^60 for a very long time (GDD D-37). On Android the save sits in app private storage, the manifest has allowBackup false, and release builds are not debuggable, so editing it needs a rooted phone. The ceiling exists to make tampered saves harmless, and this is the one place where a tampered save still hurts, so it is worth a note. Low, in line with SEC-05.

**Possible fixes (for the owner to choose).**
- Cache by more than a full clear: a larger cap, or drop only the oldest entries, so a 40 tile chain never thrashes.
- Avoid big pow2 values in the fit test: points lie between 2^merge and 2^(merge + 1) minus 1, so the test can decide most cases with `pow2(merge)` and `pow2(merge + 1)` alone (both cached), and sum exactly only when the score falls between the two bounds.
- Build 2^e faster, for example by doubling a cached neighbour (2^(e+1) is 2^e plus itself, one linear add) when a nearby exponent is cached.

## SEC-01 principle (can a loaded or played state be stuck)

Checked by reading every caller and by probes. Clean.

- There is one fit test, `CoreRules._chain_fits`. `can_join`, `joinable_cells`, `step_chain`, `is_valid_chain`, `has_valid_move` (through `pair_fits`) and `RunRules.commit_chain` (through `is_valid_chain`) all use it, and the score is a required argument of each. The board's only rule call (board_controller.gd line 354) passes `_session.state.score`; the highlight goes through `GameSession.joinable_cells`, which passes `state.score`. No caller passes a placeholder.
- The fast path (score below 2^65599 and merge + 2 at most 65600) is a correct bound: points are below 2^(merge + 1), so the sum stays below 2^65600. It and the exact path agree.
- A pair is a move only when it fits, and a longer chain only adds points, so "highlight shows but commit refuses" cannot happen, and `outcome` never says PLAY on a board where nothing commits.
- When no pair fits, `outcome` opens the offer if any booster is usable, else ends the run. Probes: a board of 3s with score 2^65600 minus 1 opens the offer (Hammer is affordable); after Hammer the score drops by 2^7 and pairs of 3 fit again. A board of all 65535 with score 100 and no free booster ends the run (outcome END), as it should. The same board with free boosters held opens the offer.
- Shuffle measures with the score after its charge, and its fallback uses `pair_fits` with that score. A fallback that finds nothing leaves the board, and the offer opens again; each paid booster lowers the score, so the loop cannot go on forever without the score falling until a pair fits or nothing is affordable.
- Double refuses a tile at 65535, so no tile can pass the ceiling. Costs go up to 2^65536 (Double on a 65535 board), well inside pow2's guard.
- A loaded snapshot whose points are above the score (accepted by the codec, see below) makes Undo CANNOT_AFFORD. `sub` returns null rather than going negative, and `usability` checks for it. Nothing breaks.

## Re-check, 2026-10-21: SEC-06 after commit 1ca4e82

The fix is commit 1ca4e82 on branch `unlimited`. pow2 now builds a power from a cached neighbour up to 300 bits away by linear shifts, evicts only the oldest cache entry, and squares large numbers with Karatsuba. `_points_of` works out small times 2^lowest. `_chain_fits` decides by comparing bit lengths against a remembered headroom (2^limit minus 1 minus the score), and adds the points up exactly only when the bit lengths tie. I re-ran the same probe scripts against this commit. src/core/ had no uncommitted changes.

### The answers have not changed

- The first 4,321 case BigNum fuzz (add, sub, compare, equals, bit_length, fits_int, to_int and pow2 edges) still matches Python's exact integers with no difference.
- 1,500 pow2 calls in random order matched Python. The exponents ran from 63 to 70,000, with clusters near 65,400 and small ones mixed in, so values came from the neighbour shift, from squaring and from Karatsuba, with the cache filling and evicting along the way. Each was exact by MD5 of its digits, with bit length e + 1 and e for 2^e minus 1 after a fresh parse.
- `_points_of` matched the plain sum of `pow2` on 400 random valid chains (2 to 40 tiles, exponents up to 65,535).
- `_chain_fits` gave the same answer as "score plus the plain sum has at most limit bits" in all 6,300 cases. The cases used limits 65,600, 300 and 70. Each tested score was placed exactly on the boundary (2^limit minus the points, plus and minus 1), at 2^limit minus 1, at 2^(limit minus 1), at zero, and at a random point. Each was also re-run with a new BigNum object of the same value, to check the remembered headroom follows the score and the limit.
- Every hostile file in the table above gave the same result as before, loaded or refused, with the same outcome.
- The full suite passes: 1,185 tests in 79 files, 0 failed.

### The fix itself

- **Remembered headroom.** It is keyed by the score object's identity and the limit. BigNum is immutable: every operation builds new limbs, and the packed arrays copy on write. So the same object always has the same value, and a new score is a new object that misses the key. The static field holds one score and one headroom, at most about 60 KB in all. Only the main thread uses it.
- **Cache growth.** It holds at most 64 entries. Reachable exponents stop near 65,601, so that is under about 4 MB, as before. Eviction is now oldest first, so a chain of many exponents no longer empties the cache.
- **Overflow.** `_times_small` takes factors up to 2^30. `_divided_small` keeps the remainder below the divisor. `_times` keeps every total below 10^18 plus 2 x 10^9, and its last carry is at most 10^9 minus 1. All stay below 2^63, as their comments say. The Karatsuba middle term is never negative, so `sub` never returns null there.

Two new slow spots, neither reachable in play. **Not findings.**

- **`_points_of` on exponents far apart.** It is fast only when the values are close. `_points_of([32000, 65535])` takes 222 ms, because it multiplies two numbers of about 1,100 limbs. Every caller passes a chain that already passed the joining order check: equal, or one more than the tile before. In those calls the spread is at most 39, so this cannot be reached. A future caller with unordered values would bring the slowness back.
- **More than 64 widely spaced exponents in rotation.** Oldest first eviction makes every call a miss: 65 exponents 1,000 apart took 1,165 ms, and 1,260 ms on the second pass. One operation in the game needs far fewer: the tiles of one chain or one board (at most 40), the costs and the score limit. So this cannot happen within a single check.
