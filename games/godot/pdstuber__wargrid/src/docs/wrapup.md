# Wrap-up

End a Wargrid work day in any agent. Prepare the next `docs/kickoff.md`. `AGENTS.md` holds standing rules; this file sets check order.

1. Check local links and referenced paths in changed documentation, including `docs/kickoff.md`, this file and `docs/session-notes.md`. Verify the session-note headings kickoff reads exist. No documentation-checker script currently exists; do not claim to have run one.
2. If game code, tests, wrappers or engine configuration changed, run `sh tools/run_tests.sh` with output redirected to a file, reading only the summary lines (AGENTS test-output rule). Report case/check counts, exit status and diagnostics. If `relay/` or `protocol/` changed, run `go test -race ./...` and `golangci-lint run` in `relay/`, `sh tools/run_conformance.sh`, and the affected `sh tools/run_netplay.sh` scenarios. Run only affected additional checks; keep them headless. Documentation-only work needs link/path/status checks, not a game test run. Complete the required single substantive review and final Ponytail pass for implementation work if not already done; do not repeat a completed review without cause.
3. Read what kickoff reads. Update plainly stale entries in Session, Pending user action, Deferred experiments and research, Next action, and newest dated notes. Record today's verified end state, not this morning's. Give tomorrow one concrete next action. Preserve uncertainty and distinguish local verification from remote CI, visuals and reference fidelity.
4. Check statuses agree across `docs/development.md`, `AGENTS.md`, relevant blueprint sections, the active execution plan, reference evidence and session notes. Search changed wording with scoped `rg`. Do not duplicate rules or numeric design values into session notes when a link suffices.
5. Do not promote a proposal, rewrite a decision or invent history to make docs agree. If resolving disagreement requires a decision, list it for the user.
6. Check the working tree for stray root files, scratch output, your own background jobs, and unmerged branch work. Preserve other sessions' files and processes. Keep caches and local environment files untracked. Never clean destructively as part of wrap-up.
7. Show documentation changes, verification results and proposed commits grouped by purpose with short messages and branch name. Recap decisions made today, their effects, mistakes and ambiguous interpretations. Ask once for commit approval, using a selector tool when available. Do not stage unrelated user work.
8. Only after approval, commit the approved scope. If on `main`, include a proposed branch name in the approval request and obtain agreement before creating it. If no HEAD exists, explicitly identify this as the first commit. Never push, open a PR or merge as part of commit approval; those need separate explicit approval.
9. Finish in three lines: branch and last commit (or no commits yet), what awaits the user, and the first action kickoff will offer tomorrow. If commit approval is still pending, report that state without claiming a commit.
