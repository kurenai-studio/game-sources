## 2. How the game was driven

- One driver, `%TEMP%\numbersgame_qa6\qa6.gd`, assembled from `driver.gd` and `modes_*.gd` in that folder, run as a SceneTree script: `godot --path . --resolution WxH --script <qa6.gd> -- --mode=<mode> --folder=user://qa_p6_<mode>/`. Nothing was added to the repo.
- It instances the real `res://scenes/main.tscn`, sets the App's `save_folder` (and `quit_handler`, so a back press that quits is counted instead of ending the process) before the App enters the tree.
- Fixtures: each setup board is written with `SaveService.save_run` and `save_profile` into the QA folder, then a new App instance resumes it, exactly as a reopened app does. Bart's save was copied byte for byte into `user://qa_p6_phone/`.
- Input: real events through `Input.parse_input_event`: InputEventScreenTouch and InputEventScreenDrag at tile centers from the board view (second fingers with index 1), InputEventMouseButton for mouse clicks, InputEventKey for Escape. Buttons were tapped by touch, through Godot's touch to mouse emulation, the same path a phone uses. The Android back button was sent as `NOTIFICATION_WM_GO_BACK_REQUEST` to the tree, app focus loss as `NOTIFICATION_APPLICATION_FOCUS_OUT`.
- Restarts: the restart chain (`restart_chain.sh`) ran 11 processes in a row on one folder. Each wrote a marker; the script then closed the window for real (`taskkill /PID`, which Godot receives as a close request), hard killed it (`taskkill /PID /F`), or the process killed itself with `OS.kill`. The next process checked what survived. For "mid animation" cases the driver set `Engine.time_scale` to 0.02 so the real close arrived while the move was still animating.
- Save timing is read without touching the files: the driver waits until the App's save queue is empty, then reads `run.json` once.
- What a desktop cannot show: real multi touch hardware, the real Android back gesture, the home button, the swipe from recents (simulated by a hard kill, which is harsher), the phone's fonts (Slate draws Segoe UI on Windows and Roboto on Android), the real camera cutout and gesture bar (simulated with `SafeArea.simulated_insets`), and phone frame rates.

Save folders: only `user://qa_p6_*` subfolders were used, all deleted at the end. Bart's real `user://run.json` and `user://profile.json` (and their `.tmp` files) were absent before my first run and are still absent after cleanup. Bart's phone save copy in the scratchpad is unchanged: SHA-256 `50f3693e...0a9f` (run.json) and `d001dd7c...fb63` (profile.json) before and after.

## 6. Findings

### QA6-01. Medium. A touch tap on the main menu's Settings button opens two Settings panels

- Owner: ui-motion-artist (src/design/shared/icon_button_base.gd:74 to 92, `_gui_input`).
- Steps: first launch (or after a run ends), tap the gear at the top right of the main menu with a finger (on the phone, or touch events on desktop). Then tap the X.
- Expected: one Settings panel; one tap on X closes it.
- Actual: two identical Settings panels are stacked (the scrim is doubly dark); X closes only the top one, so Settings seems not to close until X (or back) is tapped a second time (e_menu_after_one_close_gumdrop.png). With a mouse click only one panel opens, which is why desktop testing missed it. Same in all three skins.
- Cause, from an event trace on the button: the script's `_gui_input` handles the emulated mouse press and release and emits `pressed` itself, and Godot 4.7's BaseButton also handles the InputEventScreenTouch press and release natively and emits `pressed` again. Order seen: `MouseButton(emulated)`, `ScreenTouch`, `button_down`, `MouseButton(emulated)`, `PRESSED`, `ScreenTouch`, `PRESSED`, `button_up`.
- Both icon buttons are affected: the menu gear (two panels) and the Settings X (its second `closed` is ignored, so no visible effect today). Regular Buttons and the booster and HUD press buttons fire once.
- Why Medium: it happens on Bart's phone every time Settings is opened from the menu, and the workaround is a second tap.

### QA6-02. Medium. Gumdrop's 64K and higher tiles multiply draw calls and frame cost in the late game

- Owner: tile-board-artist (src/skins/gumdrop/gumdrop_tile_painter.gd:221 to 228, `_draw_rim`: one antialiased polyline per rim segment, `special_rim_segments` = 16, for every tile from `special_from` 65536).
- Measured on Bart's late board (ten tiles of 64K or more), section 5b: 843 draw calls per frame at rest against 237 on an early board (Slate 180, Nova 511 on the same board); 10.3 percent of frames at rest miss vsync on this desktop against 3.0 percent early; dragging a 9 tile chain costs 11.7 ms per frame on average and 19.8 ms at p95 with vsync off (Slate 3.8, Nova 7.6); the commit of the 9 tile merge spends 16 ms on average and up to 29 ms in the rules and view setup (Slate 2.7, Nova 3.8).
- Expected: 60 fps on a mid range phone with a full board (brief section 4, DESIGN_SYSTEM.md 1.5).
- Actual: on a desktop many times faster than a phone, late game Gumdrop already drops frames at rest and during drags. Late game is exactly where long runs like Bart's spend their time, and Gumdrop is the default skin.
- Not seen on the phone: Bart plays Nova. Please have the DM measure Gumdrop with Bart's save on the phone before deciding the fix. A likely fix is one polyline with per point colors, or one polygon, per rim, instead of 16.

### QA6-03. Low. No "New best" badge after a resume when the run set the record before the restart

- Owner: boosters-dev (src/boosters/game_session.gd:80 and 373).
- Steps: play a run until it sets the Best Score, close the app, reopen it (the run resumes), end the run with End run without beating the score again.
- Expected: the end screen shows New best, because this run set the Best Score (RunSummary.new_best_score in docs/ARCHITECTURE.md section 4).
- Actual: no badge. `resume()` takes `_best_score_at_start` from the records loaded from the profile, which already hold this run's score, so `records.best_score > _best_score_at_start` is false. Reproduced with D1024 at 50,000 and a profile best of 50,000 (e2_new_best_after_resume_gumdrop.png). Bart's long runs span many app sessions, so he will often miss the badge.
- Question for the owner: the run would need to carry whether it set the record (or the Best Score before it began), which touches the save format, so the DM may want to decide.

### QA6-04. Low. A clear made from the offer is not shown while the offer is open

- Owner: ui-systems-dev (src/ui/game_screen.gd:169 hides the HUD while the offer is open, and :219 asks the HUD to show the notice) together with ui-motion-artist (the HUDs parent the notice).
- Steps: AT-101 setup (Board E with (0,3) = 2 and (2,0) = 1024, score 5,000), Double on (2,0) from the offer.
- Expected: D-38: "The player must see which values were cleared and that they no longer spawn", as part of the move's animation.
- Actual: the notice is a child of the hidden HUD, so it is invisible during the clear (w_at101_clear_gumdrop.png). It appears only once the move ends and the offer closes, partway through its hold (w_at101_after_gumdrop.png). If the Double does not rescue the run, the offer stays open and the notice is never seen.

### QA6-05. Low. Tap targets are below 48 dp on most phone shapes, and Nova's tiles are under 56 dp on the Fold5 cover screen

- Owner: senior-graphic-designer (docs/DESIGN_SYSTEM.md 2.7 and 2.4).
- DESIGN_SYSTEM.md 2.7 says `touch_min` is "144 px, 48 dp on a 360 dp wide phone". That holds only on phones that are 20:9 or taller and at least 360 dp wide. Measured smallest target (the HUD pause, the menu gear, the Settings X and the sound toggle are all exactly 144 px): Fold5 cover screen (344 dp wide) 45.9 dp; 18:9 phones 43.2 dp; 16:9 phones 38.4 dp; Fold5 inner screen 49.8 dp; 360 x 800 dp 48.0 dp; tablet 76.8 dp. Gumdrop's booster buttons are 150 px tall, 47.8 dp on the cover screen.
- On Bart's cover screen, Nova's orbs are 55.7 dp against GDD A-1's 56 dp (digits 12.4 dp, above 12). The cover screen is narrower than the 360 dp the design assumed.
- Question: keep it (the GDD accepted smaller tiles on 16:9), or raise `touch_min` and the HUD buttons so they reach 48 dp?

### QA6-06. Low. A hard kill in the first 1 to 4 frames after a commit loses the move

- Owner: ui-systems-dev (src/ui/app.gd:214 to 218 and src/save/save_service.gd, the QA4-02 fix).
- Measured: r_f killed the process in the first frame after the lift (the writer was still busy) and r_g killed it inside `save_requested`, right after the App queued the save. Both times the reopened run was the one from before the move, intact. In 22 measured moves the save landed 1 to 4 frames (mean 14 ms, max 25 ms) after the lift.
- Expected: D-33 is met (saved well before the animation ends). But "closing the app during an animation cannot undo or reroll a move" (GDD 15.1) now holds only after those first frames; before QA4-02 the write finished inside the commit itself, before the first frame of the move was shown.
- Why Low: on Android, closing the app or swiping it away pauses it first, and the pause handler saves synchronously after a flush, so only a crash or an out of memory kill in that window can hit it. Please confirm the trade-off is acceptable; I am not asking for a change.

### QA6-07. Low. Windows only: after a failed rename the newer save is thrown away on the next load

- Owner: ui-systems-dev (src/save/save_service.gd:139 to 144 and 384 to 400).
- Steps: save a run (score 111); while another handle has run.json open for reading, save again (score 222); close the handle; load.
- Actual: the second save returns false and leaves the new data in run.json.tmp (Godot's Windows rename deletes the target first, which fails while it is open). The next `load_run` finds a valid run.json, uses the old run (111) and deletes the newer run.json.tmp. Found because my first driver's poll read run.json while the game's writer renamed (warning "SaveService: could not save run.json"); reproduced on purpose in mode edges2.
- Expected: after a failed rename, the newest complete save wins, as the class comment promises ("a kill at any moment leaves the old save or the new one" is still true, but the newer one is then discarded).
- Why Low: Windows is a development platform only, the next save writes again, and on Android the rename is atomic. Antivirus, backup or indexing tools could hold the file open on a desktop.

### QA6-08. Low. On the near square inner screen and on tablets, sheets, cards and buttons stretch across the whole width

- Owner: senior-graphic-designer (DESIGN_SYSTEM.md section 7).
- Seen: on the Fold5 inner screen (1998 logical px wide) Pause, Settings, the confirm dialog, the end screen and the offer run edge to edge, with buttons about 1,850 px wide and record rows whose label and value sit at opposite screen edges (s_fold_inner_gumdrop_6_pause.png, s_fold_inner_slate_11_end_nomoves.png, s_fold_inner_gumdrop_9_offer.png). Nothing is broken; it just looks stretched next to the centered board.
- Question: cap the panel width (for example at the board's width) on wide canvases?
