# 今日群島：城市議題地圖與自動更新　設計

日期：2026-10-30　狀態：草稿，待 Kerry 確認

## 為什麼要改

現在的內容照抄規格的政見書格式：12 個施政主題，每個細項是一條「承諾」，附數字和「第幾年完成」。這波政策島（HEART 政策島、施政島、竹北版等）全都長這樣。Kerry 要一個跟別人不一樣、而且能依時事自動更新的版本。

新定位：**一座虛構城市，呈現「此刻大家在討論的真實議題」**。它是中立的議題地圖，不是任何人的競選文宣。

## 已拍板的決定（Kerry 決定的）

1. 方向是「虛構城市＋真實議題」：議題取材自真實新聞，但城市是虛構的，不代表任何候選人、政黨或機構。
2. 自動更新**只能改細項**。12 座島的 id、名稱、位置、配色、樹種都固定，橋和路網因此不受影響。
3. 自動更新用 Claude Code 的 `/schedule` 雲端例行任務執行，結果一律開 PR，由 Kerry 審核後合併，**不直接推 main**。
4. 內容方向是「城市議題地圖」：
   - 細項 = 一則具體議題。
   - 卡片分三段：發生什麼／為什麼跟你有關／各方怎麼看。
   - 「時程」換成「議題狀態」。
   - 加上熱度。
   - 協作線改成議題之間的牽連。

## 目標

- 打開頁面，第一眼就看得出「今天哪些議題最熱」。
- 每則議題都看得到它取材自哪些新聞，連結可點。
- 例行任務每次產出的 PR，Kerry 五分鐘內審得完。
- 畫面、互動、效能維持現有水準，現有功能都不退化：日夜、小人、日誌、手機版、reduced-motion、`#en`。

## 非目標

- 不做即時新聞串流，頁面本身不連任何新聞 API，資料在 build 時就固定了。
- 不改島、橋、路網、模型庫，也不新增模型種類。
- 不做留言、投票、帳號。
- 細項的英文說明照舊不翻，只翻名稱。

## 反目標（做出來也算失敗的情況）

- **看起來替某一方背書**。各方看法必須並列至少兩種不同立場，用字對等。
- **出現真實人名**，包括政治人物、記者、網紅。立場一律用角色描述，例如「家長團體」「市府」「業者」「學者」。
- **捏造數字或引言**。卡片不放數字磚了。若文字裡提到數字，必須能在附上的來源裡找到，且要寫成「報導指出…」。
- **AI 直接改到上線版**，或 PR 大到審不完。

## 資料格式

### 位置

`DATA` 拆成兩部分：

- **`data/issues.json`**：只放細項，以島 id 分組，例如 `{ "traffic": [ …細項… ], "care": [ … ] }`。例行任務只能動這個檔案。
- **`parts/10-data.js`**：保留城市、島（不含 items）、協作線、時段。

`build.sh` 把 JSON 嵌進輸出，讓 `index.html` 維持單一檔案，artifact 的限制仍然成立。

### 細項欄位

```json
{
  "id": "tr-2026-10-mrt-peak",
  "name": "捷運尖峰加班車",
  "en": "Extra peak-hour trains",
  "model": "busstop",
  "status": "debating",
  "heat": 3,
  "what": "一句話：發生了什麼。",
  "why": "一句話：這件事怎麼碰到一般人的日常。",
  "views": [
    { "who": "通勤族", "says": "…" },
    { "who": "營運單位", "says": "…" }
  ],
  "sources": [
    { "title": "報導標題", "outlet": "媒體名", "url": "https://…", "date": "2026-10-28" }
  ],
  "updated": "2026-10-30"
}
```

- **`id`**：新增後永久不變。不再沿用 `tr1` 這種流水號，避免刪了再加時撞號。
- **`model`**：沿用現有 15 種。
- **`status`**：四種：
  - `new`（剛冒出來）
  - `debating`（討論中）
  - `progress`（有進展）
  - `settled`（已定案）
- **`heat`**：0 到 3。
  - 3 = 本週討論度最高，全城最多 6 則。
  - 2 = 有在討論。
  - 1 = 冷下來了。
  - 0 = 已沉寂，下次更新應考慮移除。
- **`views`**：2 到 3 筆。`who` 只能是角色，不能是人名。
- **`sources`**：1 到 3 筆。至少一筆在 `updated` 之前 14 天內。
- **每座島 3 到 8 則**。`layoutIsland` 用 0.62 的格子就排得下 8 則，這點在寫開發指南時已經核對過。超過 8 則格子才會縮小，所以驗證的上限就定為 8。總數建議維持在 36 到 60 則。
- **排序**：載入時，每座島的細項依 heat 高到低排，同 heat 再依 `updated` 新到舊。
  - 排第一的佔島中央的主位，編號 ①②… 也照這個順序。
  - 每天更新後模型位置可能換，這可以接受。
  - 這樣 JSON 裡的順序就沒有意義，例行任務不用管排序。

### 舊欄位的處理

- `phase`、`desc`、`facts` 移除，對應的程式一起改掉，不留相容層。
- 時段的 `lit` 改成**模型種類**，不再寫細項 id。例如上學通勤是 `['busstop', 'bikes', 'classroom']`，該時段所有這類模型的細項都會亮。這樣細項每天換，時段高亮也不會懸空，現有的時段功能不會退化。
- 協作線欄位不變：
  - `evidence` 的語意改成：`official` = 直接牽動（實線）、`thematic` = 間接相關（虛線）、`pending` = 有人提出關聯（點線）。
  - 介面上的標籤文字照新語意改。
- 協作線與島的 `summary` 在這次改版時由人工重寫一次，之後例行任務不碰。

## 畫面與互動的改動

1. **細項卡片**：
   - 移除大數字磚、重點事實、時程條。
   - 依序顯示：狀態標籤＋熱度（1 到 3 個小火焰圖示或圓點）→ 發生什麼 → 為什麼跟你有關 → 各方怎麼看（每筆一行：粗體角色＋說法）→ 取材來源（媒體名、日期、標題連結，新分頁開啟）→「更新於 YYYY-MM-DD」。
2. **熱度在場景上看得到**：
   - `heat` 3 的細項，模型旁插一支小旗子。旗子做成零件庫裡的新零件，不算新模型，用島的 `band` 色。
   - 只有 heat 3 插旗：首版 39 則裡有 31 則是 heat 2，heat 2 也插旗的話幾乎每棟都有，旗子就失去意義。
   - 夜晚時 heat 3 的旗頂發光，沿用 `glowsphere`。
3. **右側清單**：
   - 細項依熱度、狀態排序，列表右側的小字從時程改成狀態。
   - 清單頂端加一區「本週熱門」，列出所有 heat 3 的細項，點了就飛過去。
4. **品牌卡**：眉標從「示範 · 虛構資料」改成「虛構城市 · 議題取材自新聞」，旁邊加「資料更新於 YYYY-MM-DD」，取所有細項 `updated` 的最大值。
5. **說明視窗與文件**：說明改成議題地圖的讀法。README、遊戲介紹、操作手冊、開發指南的對應段落照實改寫，虛構聲明更新。
6. 搜尋框改成也搜 `what`、`why`、`views[].says`。

## 自動更新流程

```
/schedule 例行任務（雲端，每天 07:00 台北時間）
  1. clone repo，讀 data/issues.json 與 docs/update-guide.md（更新守則）
  2. 依 12 座島的分類搜尋近 7 天台灣新聞（WebSearch；以主要媒體與政府新聞稿為主）
  3. 決定改動：新增議題、更新 status/heat/views/sources、移除 heat 0 或過期的議題
     - 每次最多改 8 則；heat 依新聞量重新評估，舊議題沒有新報導就降 1
  4. 寫回 JSON → 跑 node scripts/validate.mjs → 跑 sh build.sh
  5. 驗證通過才開 PR，標題「議題更新 YYYY-MM-DD」；內文是改動表（島／議題／改了什麼／來源連結）
     沒有值得改的就不開 PR
  6. 驗證失敗：不開 PR，把錯誤寫進一個 issue（或 PR 草稿）讓 Kerry 知道
PR 只包含 data/issues.json（index.html、preview.html、dist/ 都在 .gitignore 裡，不進版控）
合併到 main
  → GitHub Action：sh build.sh && wrangler deploy（需要 CLOUDFLARE_API_TOKEN secret）
```

### `docs/update-guide.md`（更新守則）

例行任務與人工更新共用這份守則，內容包括：

- 反目標清單。
- 欄位規則。
- 分類對照：每座島收哪類新聞。
- 中立用字的寫法。
- 「沒把握就不改」原則。
- PR 內文格式。

### `scripts/validate.mjs`

用 Node 寫，不引入套件。檢查項目：

- JSON 結構與欄位型別、列舉值。
- id 不重複，格式是 `<島縮寫>-<YYYY-MM>-<slug>`。不比對 git 歷史：刪除議題是允許的，「改名」在技術上分辨不出來，交給人工審核。
- 每島 3 到 8 則。
- heat 3 的細項不超過 6 則，超過就擋下。build 本身不做裁切。
- views 2 到 3 筆，sources 1 到 3 筆。
- 至少一筆 source 落在 14 天內。
- url 是 https。
- `who` 不在人名黑名單內。黑名單只是輔助，真正的關卡是人工審核。

驗證失敗時以非 0 結束。
