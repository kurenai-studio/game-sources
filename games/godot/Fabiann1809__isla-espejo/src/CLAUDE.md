# Isla Espejo — project rules

Top-down pixel-art roguelike made in **Godot 4.7 (GDScript)** by two developers. Working title: "Isla Espejo" (may change).
Game design: `docs/JUEGO.md` and task list: `docs/TAREAS.md` (both written in Spanish). **Read both before starting any task.**
Visual references: `docs/referencias/` (concept images only; they are NOT game sprites).

## Core idea (do not lose sight of it)
Nico is stuck on an island that mirrors and learns from him. He crosses 3 scenarios, defeats 3 bosses (each gives a compass fragment and a skill) and goes home. Three pillars:
1. **Every run is different**: procedural maps built from hand-made rooms.
2. **Fixed skills, one per boss** (no combos for now, but keep the system data-driven so combos can be added later).
3. **The island learns**: adaptive AI in two layers — player profile (layer 1) and island reaction (layer 2). Both are mandatory.

## Workflow
1. Work on **one task at a time**, in the order of `docs/TAREAS.md`, and only on tasks assigned to you (A or B) unless told otherwise. Do not add anything that is not in the docs.
2. A task is done only when:
   - the project opens and runs with no errors in the Godot console,
   - `./tools/run_tests.sh` passes (it runs the smoke check and every `tests/test_*.gd`, and fails on non-zero exit codes, timeouts or `SCRIPT ERROR`; `./tools/run_tests.sh test_skills` runs just one). On Windows set `GODOT` to the `*_console.exe` build. Add a `tests/test_<system>.gd` for each new gameplay system; in tests never `preload` scenes or reference `class_name` types of scripts that use autoloads: load at runtime, use untyped variables, `await process_frame` first if the test touches an autoload,
   - its "Hecho cuando" criterion is verified,
   - a short explanation of what was done and why is given to the user (in Spanish).
3. If anything is ambiguous or touches the scope, **ask the user** before assuming. Never expand the scope: anything marked as out of scope or as an extra in the docs is not built unless the user says so.
4. Never break what already works. If a change could affect another system, run the project and check that system before committing.

## Git and collaboration
5. Work directly on `main` and push to it (no pull requests needed). Before every push: `git pull --rebase`, run the project, and run `./tools/run_tests.sh` (must pass). Never push something that does not open or breaks what already worked. CI (`godot-check`) runs on every push; if it fails, fix it first.
   - Optional: use a short-lived branch `feature/<short-name>` for a big or risky change, then merge it into `main`.
6. One commit per task or fix. Tick the task checkbox (`[x]`) in `docs/TAREAS.md` in the same commit.
7. Commit format: [Conventional Commits](https://www.conventionalcommits.org/) in English: `type(scope): imperative summary`.
   - Types: `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `chore`, `style`.
   - Scopes: `player`, `combat`, `skills`, `enemies`, `bosses`, `world`, `ai`, `npc`, `dialogue`, `ui`, `audio`, `art`, `save`, `ci`.
   - Summary ≤ 72 chars, imperative, no trailing period. Example: `feat(player): add dash with cooldown`.
8. Each person commits with **their own name and email**. **Never** add `Co-Authored-By` trailers or any AI/tool attribution to commits, PRs or files.
9. Avoid merge conflicts in Godot: do not edit a `.tscn` scene that the other person is currently working on, and `git pull --rebase` often. Shared files (`project.godot`, autoloads, `data/`) are changed in small commits, announced first. Prefer many small scenes over one big scene.
10. Releases: pushing a tag `v*` publishes a public GitHub Release (CD). Never create or push tags unless the user explicitly asks. Never commit: `.godot/`, builds, secrets, personal files, or huge unused assets. Never force-push to shared branches.

## Code
11. Everything in **English** (identifiers, comments, commits, filenames) **except player-facing text** (dialogues, UI, item names), which is **Spanish** and lives in `data/` files, never hardcoded in scripts.
12. GDScript style: `snake_case` for files, variables and functions; `PascalCase` for classes and nodes; static typing everywhere possible (`var hp: int = 10`); small functions; comment only the non-obvious "why".
13. Structure: one scene per entity and one script per scene.
    - `scenes/` (player, enemies, bosses, npcs, levels, ui), `scripts/` (same subfolders plus `skills/`, `ai/`, `world/`), `assets/` (`sprites/`, `tilesets/`, `audio/`), `data/` (JSON/Resources), `tests/`.
14. Game data is data, not code: skills, enemies, rooms and dialogues are defined in `data/` (JSON or Godot Resources) and read by generic systems. Adding a new enemy or skill must not require changing the core systems.
15. The adaptive AI lives in `scripts/ai/` and is separated from combat code. Combat code only **emits events** (e.g. "player dashed", "player hit enemy", "enemy detected player"); the AI listens. Use signals or a small event bus autoload.
16. The player profile is saved to `user://profile.json`. Keep the format versioned (`"version": 1`).
17. Resolution is 640x360 with integer scaling and *nearest* filtering. Do not change display settings without asking.
18. Combat uses the reusable components in `scripts/components/`: `HealthComponent` (health), `Hitbox` (deals damage, once per activation) and `Hurtbox` (receives damage). Never write ad-hoc damage code; a new enemy or trap reuses them.
    - Hitboxes and hurtboxes are `Area2D` nodes. Keep `monitorable = true` on them (turning it off makes the area blind).
    - Collision layers (named in `project.godot`): 1 `world`, 2 `player` (body + Hurtbox), 3 `enemy` (body + Hurtbox), 4 `player_attack`, 5 `enemy_attack`. Player Hitbox: layer 4, mask 3. Enemy/trap Hitbox: layer 5, mask 2.
    - Bodies only collide with `world` (and the player body also with `enemy`); damage is decided only by Hitbox vs Hurtbox.
    - Combat code publishes what happens on the `Events` autoload (`scripts/core/events.gd`); the AI and HUD listen there. Add a signal there when a new gameplay fact must be observable.
    - **Enemies**: inherit `scenes/enemies/enemy.tscn` (see `grunt.tscn`), create an `EnemyData` `.tres` in `data/enemies/` and set it as `data`. Only override the `_process_*` / `_start_attack` hooks of `scripts/enemies/enemy.gd` (in a script extending `Enemy`) when the behaviour differs. Never copy `enemy.gd`. The AI director tunes enemies through the `*_multiplier` properties before adding them to the tree.
    - **Maps** (`scripts/world/`): a scenario is a `ScenarioData` (`data/scenarios/`) with `RoomData` entries (`data/rooms/`). `MapGenerator.generate(scenario, seed, weight_modifiers)` returns a pure-data `MapLayout`; `Level` turns it into rooms, corridors, enemies and the player. Same seed = same map. The director steers rooms only through `weight_modifiers` (room tag -> multiplier) and rooms emit `Events.room_entered/exited/cleared`.
    - **Rooms**: a room is a scene inheriting `scenes/levels/rooms/room_base.tscn`, 30x18 tiles (480x288 px). Add obstacles as `StaticBody2D`, keep the center cross (x 208..272, y 112..176) free so doors stay reachable (`tests/test_room_designs.gd` checks every room of every scenario with real physics), and use the marker nodes `PlayerSpawn`, `EnemySpawns`, `BossSpawn`, `NpcSpawn`, `ChestSpawn`, `SpecialSpawn`. Then create its `RoomData` `.tres` (see `tools/make_test_data.gd`) and add it to the scenario's `rooms`. Run `tests/test_map_generator.gd` and `tests/test_level_build.gd` after any change.
    - **Skills** (`scripts/skills/`): a skill is a `SkillData` (`data/skills/`) whose behaviour is a `SkillEffect` resource. To add one: subclass `SkillEffect` (override `activate`, return how many enemies were affected), expose its numbers with `@export`, and create the `.tres` (see `tools/make_skill_data.gd`). Do not edit `SkillManager`. Unlock with `player.skills.unlock(skill_data)`. Skills only touch enemies through their public methods (`apply_root`, `apply_slow`, `apply_knockback`, Hurtbox for damage); each cast is published as `Events.skill_used(id, direction, affected)`. Stealth is `player.visibility` (enemies scale their sight by it).
    - **Player profile / AI layer 1** (`scripts/ai/`, autoload `PlayerProfile`): it only listens to `Events` and keeps `user://profile.json` (`"version": 1`). `RunStats` (counters of a run) and `ProfileModel` (scores and learning) are pure logic with no nodes; do not add game dependencies to them. Tuning and the summary texts live in `data/ai/profile_config.tres` (see `tools/make_ai_data.gd`), never in code. The director (layer 2) reads `PlayerProfile.live_scores()` / `live_style()` and must not touch the model or the counters. Saving is disabled in headless mode so tests never touch a real profile. To record a new gameplay fact, add a signal to `Events`, emit it from the gameplay code and count it in `RunStats`.
    - **Director / AI layer 2** (`scripts/ai/`, autoload `Director`): `Director.make_plan()` reads `PlayerProfile.live_scores()` and returns a `DirectorPlan` (stat multipliers, enemy count and weights, room-tag weights, Spanish island line and hints). `DirectorLogic.plan_for(...)` is the pure decision (test it without nodes). The rule table is `data/ai/director_rules.tres` (`DirectorRule` per style, see `tools/make_director_data.gd`): tune the AI there, never in code. `Level` applies the plan (room weights to the generator, count and multipliers to the enemies); no other code may read the profile to alter gameplay. An enemy's id is its scene file name. New enemy behaviour must respect the director's multipliers (`_speed_scale()`, `can_see()`). Order matters: `Events.level_started` is emitted first so the profile learns the previous run before the director plans.
    - **Visual theme / tiles** (`scripts/world/tile_art.gd`, `room_theme.gd`, `room_prop.gd`): the Kenney Roguelike/RPG sheet (CC0, in `assets/tilesets/kenney_roguelike_rpg/`) is registered as `assets/tilesets/forest_tileset.tres`. Tiles are referred to by NAME in `TileArt` (never hardcode `Vector2i(16, 9)` elsewhere); to find more tiles render a labeled preview with `tools/atlas_preview.gd` (needs a window) and add a constant. A `ScenarioData.theme` (`data/themes/*.tres`) dresses rooms and corridors; collision never depends on it. Rooms are described with `RoomProp` nodes (kind, position, size) so they stay readable in text; forest rooms are generated by `python tools/make_forest_rooms.py`, which validates lanes and spawns (edit the layouts there and regenerate, or edit the scenes by hand and run `tests/test_room_designs.gd`). Every new third-party asset goes in `CREDITS.md` with its license file next to the art.
    - **Interaction and dialogue** (`scripts/world/interactable.gd`, `npc.gd`, `chest.gd`, autoloads `Dialogue` and `GameState`): anything the player uses with E has an `Interactable` child (Area2D on physics layer 6, with a Spanish `prompt`); the player picks the nearest and shows `[E] prompt` in the HUD. NPCs are `scenes/npcs/npc.tscn` instances with a `dialogue_id`; **conversations are JSON files in `data/dialogues/`** (format in `docs/EMPEZAR.md`, validated by `tests/test_dialogues.gd`: every NPC needs the states `first`, `again` and `final`). Dialogue text never goes in scripts. Story progress that survives death (fragments, learned skills, flags) lives in `GameState`; never keep it in a node that is destroyed with the level.
    - **Bosses, fragments and exits**: a boss is a scene inheriting `enemy.tscn` with `scripts/enemies/boss.gd` and a `BossData` (`data/enemies/`). It is territorial, has super armor (immune to push and root), two warned attack patterns and a second phase; the director never modifies bosses. On death it sets its `defeated_flag` (`<scenario>_boss_defeated`) in `GameState`, emits `Events.boss_defeated` and leaves a `FragmentPickup`, which records the fragment, teaches its skill and opens the `ExitPortal`. `Level` re-applies `GameState` to the player on every map, so earned skills survive dying. `tests/test_boss.gd` is the model test for a new boss.
    - **Menus, save and options** (`scripts/ui/`, `scripts/core/`): the game opens on `scenes/ui/main_menu.tscn`. Menus are built in code with `UiKit` (shared theme) and every player-facing text comes from `data/ui/texts.json` through `UiText.t("key")`. Progress lives in the `SaveGame` autoload (`user://save.json`, version 1: `GameState` + current chapter; it saves by itself on level start, fragment, skill and boss) and options in `Settings` (`user://settings.json`); both are disabled in headless mode and with `--no-save`. `Level` resumes the saved chapter through `SaveGame.take_pending_scenario()`. The pause menu (`pause` action, Esc) is a child of the playable levels. The credits screen reads `CREDITS.md`, so keep that file's table format (`| Resource | Author | License | ... |`). A `ScenarioData` has `objective`, `objective_done` and `objective_flag` for the HUD. `tests/test_save_menu.gd` covers it all.
19. Use the input actions defined in `project.godot` (`move_*`, `dash`, `attack`, `skill_1..3`, `interact`). Never hardcode keys.
20. Placeholders: until real sprites exist, use `ColorRect`/simple shapes. Never block a task waiting for art.

## Art and assets
21. Characters are made by the team in **Pixelorama**: 32x32 sprites for Nico and small enemies (bosses, big enemies and NPCs may be 64x64), one shared palette of 16–24 colors, minimum animations idle / walk / attack / hurt / die. Views: Nico has 3 (front, back, side) + flip; enemies and bosses one side + flip; NPCs front only. Animations are found by name, `<animation>_<view>` with the views `down` (front), `up` (back) and `side` (facing right): Nico's art is the strips `assets/sprites/nico/nico_<animation>_<view>.png` read by `tools/make_nico_frames.gd` (`idle`/`walk` in the 3 views; `attack`, `hurt`, `death`, `dash` side only). A missing view falls back to `<animation>_side`.
22. Tilesets are 16x16 (a free pack may be used; record it in `CREDITS.md`). Every third-party asset must be listed in `CREDITS.md` **in the same commit** that adds it, with its license.
23. Keep source art (`.pxo`) next to exported PNGs under `assets/sprites/<name>/`.

## Safety
24. No API keys, tokens or personal data in code, docs, logs or commits.
25. The repository is public: do not publish anything that is not meant to be public.
