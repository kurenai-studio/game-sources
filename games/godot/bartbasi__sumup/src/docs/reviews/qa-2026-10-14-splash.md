## 2. How the App was driven

The same method as round 2. A SceneTree driver in `%TEMP%\sumup_qa3\` instances the real `res://scenes/main.tscn`, points the App's save folder at a `user://qa_sp_*` folder, and drives it with real InputEvents through `Input.parse_input_event` (touch, with `Input.emulate_touch_from_mouse` on so the ScrollContainer scrolls by touch drag as on a phone), Android back as `NOTIFICATION_WM_GO_BACK_REQUEST`, and lifecycle notifications. Fixtures are written with SaveService. Every launch in the restart and kill chains is a real separate process on one save folder: a close is a real window close (`taskkill` without `/F`, so the App gets `WM_CLOSE_REQUEST`), a hard kill is `OS.kill` of the process itself at a chosen frame, and the "back on the splash quits" step let the App call `get_tree().quit()` for real. File checks use SHA-256 of `run.json`, read only. Window 540 x 1200 (the 1080 x 2400 canvas) unless stated. Every `user://qa_sp_*` folder was deleted afterwards; the game's real user folder holds no run or profile file, as before.

## 7. Findings

### SPL-01. Low. A damaged run file with a last good copy continues the older run, but the GDD says Play starts a new run

Owner: lead-game-designer (docs/GDD.md), question for the DM. The code follows ARCHITECTURE.md section 10 (SEC-02).

Steps: play a run for at least two moves (each save after the first keeps the previous run.json as run.json.bak). Damage run.json (for example cut it off part way). Launch, tap Play.

Expected (GDD 15.1, 15.4 "A saved run that fails the launch check is discarded at launch ... PLAY starts a new run", example SP8, AT-95's App line): a new run.

Actual: SaveService.load_run (src/save/save_service.gd lines 210 to 227) deletes the damaged run.json, finds the valid .bak and returns it, so the splash holds that run and Play continues it, one save behind. Records are kept either way. Seen in all three skins (score 19,000 from the .bak where the damaged file had 20,000). Since a real run almost always has a .bak, this is what a player will see in practice.

Question: is continuing from the last good copy the intended behaviour after SEC-02? If so, GDD 15.1, 15.4, SP8 and AT-95 need a line for it. If not, the loader would need to change, which undoes part of SEC-02.

### SPL-02. Low. Info builds the whole guide in one frame when it opens

Owner: ui-systems-dev (src/ui/info_panel.gd).

Steps: on the splash or in Pause, tap Info.

Expected: the screen fades in smoothly, as the other screens do (60 fps budget 16.7 ms).

Actual: `InfoPanel.setup` builds all sixteen sections, three one row board views, four result tiles, the Double row and five icons in the tap's frame: 30 to 100 ms on this desktop, one 60 to 78 ms frame with vsync on. A phone is several times slower, so the tap may stall for a few hundred ms before the fade starts. Settings (25 to 71 ms) has the same pattern on a smaller scale. Not measured on a phone, so the real size of the stall is unknown; worth a look on Bart's Fold5.

### SPL-03. Low. A stale comment still names the main menu

Owner: tile-board-artist (src/skins/skin_tile_view.gd).

File and line: src/skins/skin_tile_view.gd line 3 lists "the main menu" among the places a lone tile is drawn; it is now the splash and Info. Comments in tests/skins/test_label_fit.gd line 6 and tests/skins/test_one_row_boards.gd lines 2 and 93 still say How to play. Code and behaviour are right; only the wording is out of date.
