## Findings

### SEC-01 (Low): two touching 2^62 tiles count as a valid move but can never be merged

**Owner:** core-logic-dev (src/core/). The rule it collides with is the overflow rule in docs/ARCHITECTURE.md section 3 (DM), and the move check is D-15 in docs/GDD.md (lead-game-designer), so the fix needs a rule decision through the DM first.

**Where:**
- src/core/core_rules.gd lines 104 to 116: `has_valid_move` returns true for any two touching tiles of equal value.
- src/core/run_rules.gd lines 43 to 48: `commit_chain` refuses a chain whose sum would pass 2^63 minus 1, so 2^62 + 2^62 is refused with `&"invalid_chain"`.
- src/boosters/booster_rules.gd lines 78 to 84: `outcome` returns PLAY whenever `has_valid_move` is true, so the no moves offer never opens and the run never ends.

**Steps to reproduce:**
1. In a save folder, write a run.json that passes validation: the GDD 19.0 Board D pattern (no touching pair), with cells 35 and 36 (bottom row, columns 0 and 1) set to exponent 62, `"score": "0"`, `"run_highest": 62`, `"snapshot": null`.
2. Start the App on that folder.
3. Measured result: the run resumes in PLAYING. Committing the chain (0,7) to (1,7) is refused with `invalid_chain`, the merge preview is 0, every booster is unaffordable, and the offer never opens. The only way out is Pause, then New game.
4. Variant: all 40 tiles at exponent 62 and `"score": "9223372036854775807"`. Hammer, Swap and Shuffle each show as usable once (Swap has no legal pair, since every tile is equal); after one booster the score is below the 2^62 price and the same dead end follows.

**Why it matters:** no crash, no freeze and no data loss, and real play can never get near 2^62 (D-37). But the game loads a file into a state its own rules call playable that cannot be played. It is Low because only someone editing the save file can get there.

**Suggestion:** count a touching pair as a move only when its sum fits in 64 bits (the same test `commit_chain` uses), or have SaveCodec refuse a board with two touching 2^62 tiles. Either way it is a rule question for the DM and the lead game designer.

### SEC-02 (Low): saves are not forced to storage before the rename, and the profile has no second copy

**Owner:** ui-systems-dev (src/save/).

**Where:** src/save/save_service.gd lines 384 to 400 (`_write_file`: store_buffer, close, read back, rename) and lines 209 to 225 (`load_profile`).

**What I saw:** the write path is right for a killed process. In 60 hard kills of a process saving in a loop (section 1 below), every kill left a run and a profile that loaded, including 4 kills that landed in the Windows moment where only run.json.tmp exists. What it does not cover is a power cut or an OS crash on the phone. SaveService never asks the OS to put the bytes on storage before it renames the file. Godot's FileAccess offers only `flush()` and `close()` for this (checked with ClassDB); SaveService calls `close()` only, and I could not confirm on this machine whether either one makes Android write the data to storage. On some file systems a rename that is not preceded by a sync can leave the renamed file empty or cut short after a power cut.

**Consequence if that happens**, following the code:
- A damaged run.json is discarded and the player lands on the main menu.
- A damaged profile.json falls back to profile.json.tmp only if one exists, which it does not after a finished write. So defaults load, and the next save writes them over the file. Best Score and Best Tile are then gone for good.

The validation keeps this safe: no crash, no freeze, and the other file is not touched. But the records are the one long term thing the player keeps in an endless high score game.

**Not tested:** I did not cut power on a phone (no device work this round). This is a gap found by reading the code, not a reproduced failure.

**Suggestion:** find out whether Godot's `flush()` syncs to storage on Android and call it before `close()` if it does, and consider keeping the last good profile as a fallback that `load_profile` can use when profile.json is damaged.

**Where:**

## Observations (not rated)

1. **Duplicate provider authority in both packages.** The manifest declares `androidx.startup.InitializationProvider` with the authority `com.bartbasi.numbersgame.fileprovider`, the same authority as `androidx.core.content.FileProvider`. The preset has no provider settings, so this comes from Godot's export of its prebuilt template, not from the project. Both providers are `exported=false` and the app installs and runs, so I see no security effect. Android normally keeps only one provider per authority, so the androidx startup initializer (the baseline profile installer) may not run. Owner: platform-dev, for awareness only; nothing in the project can change it without a Gradle build.
2. **`<profileable android:shell="true">`** is in both debug and release (Godot template default). It lets the adb shell attach profilers to a release build. It does not allow reading app files or attaching a debugger. Fine for v1.
3. **Backup.** allowBackup is false and no backup rules are declared. On Android 12 and later with target SDK 31 or higher, allowBackup false stops cloud backup, but a device to device transfer can still copy app data to a new phone. The save files hold nothing sensitive, so this is fine and arguably helps the player.
4. **Hand edited saves can set any Best Score or Best Tile.** The profile accepts any valid number, and resuming a run updates the records from its board and score. There are no leaderboards and nothing online, so this has no security effect.
5. **README.md line 108** says the export leaves out launcher/. The package does contain `assets/launcher/main_192.png`, because project.godot uses it as the project icon. It is the approved code drawn icon (its hash matches the committed file and the tool's output), so this is a wording point for platform-dev, not a third party problem.
6. **.gitignore** covers everything the brief asks for. Checked with `git check-ignore`: *.keystore, *.jks, *.p12, *.pfx, *.pk8, *.pem, *.key, keystore.properties, export_credentials.cfg inside and outside .godot/, build/, *.apk, *.aab, *.idsig, android/, .godot/ and .claude/settings.local.json. It does not cover generic secret file names such as .env, credentials.json, local.properties or signing.properties. None exist and nothing uses them; platform-dev could add them as cheap insurance.
7. **Developer tools take paths from their own command line.** tools/capture.gd loads any `--scene` path and writes its PNG to any `--out` path, and the build scripts run whatever the GODOT and ADB variables point to. These run only on the dev machine, with arguments and environment the developer controls, so no trust boundary is crossed. With `-Icons` or `--icons`, or when a launcher PNG is missing, the build scripts also write launcher/*.png and docs/design/review/launcher-icon-check.png (git ignored) through the icon tool. README.md documents this.
8. **The 16 level depth scan before parsing is extra protection.** Godot's own JSON parser already refuses nesting deeper than about 1024 levels (measured: 1025 parses, 2000 returns "JSON structure is too deep"). I tried to make the scan and the parser disagree about where strings start, using invalid UTF-8 lead bytes before a quote. The UTF-8 decoder keeps the quote byte, so the two agree, and the file was refused.

## What I checked and found clean

### 1. Save system (src/save/, read in full)

**Reading:**
- JSON only, through `JSON.new().parse`. No str_to_var, bytes_to_var, bytes_to_var_with_objects, FileAccess.get_var, ConfigFile, ResourceLoader or load() in src/save/, and no shipped code anywhere loads objects from file data (section 6).
- Files are read only from the SaveService folder, which is user:// in the game (src/ui/app.gd line 34, a test seam the game never changes). The file names are constants.
- Limits before parsing: 1 to 65536 bytes, checked from the file length before anything is read; a NUL byte is refused; nesting deeper than 16 is refused.
- SaveCodec checks exact keys, types and ranges for every field, as ARCHITECTURE.md section 10 and GDD 15.1 require. Numbers must be whole and finite. Digit strings are 1 to 19 ASCII digits with no sign and no leading zero, within 2^63 minus 1. The skin id is 1 to 32 characters of a to z and underscore.
- A well formed but unknown skin id cannot pick a file to load: SkinCatalog.get_skin (src/skins/skin_catalog.gd line 29) checks the id against its fixed list before it builds the res:// path, and the App then uses the default skin.

**Hostile files through the real SaveService.** A driver in the session scratchpad (not the repo) wrote each hostile run.json next to a good profile.json, each case in its own user://sec_review/case_NNN folder, and loaded both. Then the same the other way round. 97 run cases and 29 profile cases; every load took 0.4 to 15 ms.

Refused, the run discarded, the profile untouched (82 run cases):
- Damaged files: zero bytes; whitespace only; cut off at half and one byte short; 4 KB of random bytes; 5 MB of padded valid JSON; 65537 bytes; 30000 nested arrays; 2000 nested objects; 17 levels inside one field; invalid UTF-8 lead bytes before a quote with 5000 levels behind them; UTF-16 text; a NUL after valid JSON.
- Wrong shape: a top level array, string, null or number; format 2, "1" or true; columns 6; rows 7 or 8.5; 39, 41 or 20000 cells; cells as a string or an object; a missing key; an unknown extra key; duplicate keys whose last value is bad; an object with 5000 keys.
- Bad numbers: cell exponents 0, -1, 63, 64, 1000, 1.5, 2.0000000000000004, -0.0, 1e400, -1e400, NaN, Infinity, true, null, "4", [4] and 0x4; run_highest 0, 63, or below the board's highest tile.
- Bad score strings: "9223372036854775808", "18446744073709551616", "99999999999999999999", "-1", "+1", " 1", "1 ", "1e3", "0x10", "00", "007", "", "12a", Arabic-Indic digits, full width digits, an embedded NUL, a 60000 digit string, and the score as a plain number, a float, null, a bool or an array.
- Bad snapshots: points "3", 3 cells, an extra key, and the snapshot as [], false or {}.

Accepted, all valid by the format (15 run cases): the valid control file; exactly 65536 bytes; a UTF-8 byte order mark before valid JSON; format 1.0; exponent 4e0; run_highest 62 above the board; score "0" and "9223372036854775807"; snapshot points "4"; snapshot points above the score (Undo then never becomes affordable); duplicate keys whose last value is good (the parser keeps the last one); and the four rule breaking runs below.

Valid format, but breaking the rules, started in the real App (headless, real frames so every animation ran, 19 App cases across Gumdrop, Slate and Nova):
- A board with no valid move and score 0: straight to the end of run screen, the run deleted, the profile kept.
- The same board with a huge score: the no moves offer opens.
- A 2^40 among 2s (tiles below the spawn window floor): plays normally, chains commit.
- All 40 tiles at 2^62 with score 9223372036854775807, and the offer and end of run screens with maximum records: render in all three skins. Worst frame 7 ms (48 ms once on the Slate main menu with maximum records), no script errors.
- Only run.json.tmp present: the run resumes and the temp file is renamed into place.
- A damaged profile next to a good run: the run resumes with default settings.
- The one problem found here is SEC-01.

Profile cases. A damaged profile (zero bytes, cut off, 5 MB, 30000 levels deep, a top level array, format 2, no format) gives defaults, the file is kept, and the run is untouched. Bad single fields fall back on their own and keep the good parts: the skins "../../evil", "res://x", 33 characters, "NOVA" and 123 are refused; "\u006eova" (a JSON escape) decodes to nova and is accepted; sound_on 1 or "false" is refused; best_score "9223372036854775808", "-5" and the number 5 are refused; best_tile 63, -1, 1e400 and 2.5 are refused; settings as a list, records missing, unknown keys everywhere, and a duplicate best_score with a bad last value are each handled per part. In no case did a bad file change or delete the other file.

**Atomic writes and leftover temp files.**
- Code path: write `<name>.tmp`, close, read it back and compare, then rename over the real file. On Windows, Godot's rename deletes the target and then moves the file, so there is a moment when only the temp file exists. load_run and load_profile both recover from a good temp file and rename it into place.
- Leftover temp cases: a good run plus a half written temp loads the good run and removes the temp. A good run plus a complete newer temp loads the older run and removes the temp (old or new, as designed). No run plus a complete temp is recovered and renamed into place. No run plus a half temp gives no run and removes the temp. A zero byte run plus a complete temp is recovered. Garbage in both gives no run and removes both. A profile that exists only as profile.json.tmp is recovered. 50 queued writes followed by save_run leave only run.json.
- Real kills: a second Godot process wrote the run and the profile in a loop, with save_run and save_profile on two of every three rounds and queue_run and queue_profile (the worker thread) on the third. The orchestrator waited for the first run.json, waited a random 1 to 400 ms, killed the writer with OS.kill (TerminateProcess on Windows), and loaded what was left. 60 rounds: 60 good runs and 60 good profiles. Files at the kill: run.json.tmp beside run.json 22 times, profile.json.tmp 20 times, only run.json.tmp (the Windows rename gap) 4 times, no temp file 14 times.

**Save folder guard** (src/save/save_service.gd lines 86 to 91). Refused, with nothing written: "C:/Windows/Temp/...", "res://", "res://x", "user://../x", "user://a/../../x", "user:/x", "USER://x", "user:\\x", "/tmp/x", " user://x" and "". Accepted only folders inside the user data folder: "user://sec_review/guard_ok", a literal folder named "%2e%2e" inside it, and "user:////..." (which resolves inside it). "user://C:/x" passes the guard but the write fails, because it resolves to an invalid path under the user data folder, and nothing was created. No file appeared outside the user data folder. The guard also refuses a harmless folder named "..hidden", which is fine.

**Write side.** save_run refuses a state that would not load back (a negative score, a value that is not a power of two) and keeps the last good file. The largest legal values (2^62 tiles, a score of 2^63 minus 1) round trip exactly.
