# Score Changes and Gravity Timing

Where the score assumptions hold, and where row clearing needs more evidence.

The gravity-number result assumes a finite nonnegative integer score at the request. Source review gives that premise for initialization and accepted Continue. It does not give it for every row-clear input that R1 permits. More than four full rows make the shipped score-table lookup undefined, so that writer needs a separate domain argument.

This is a proposed writer-premise reconciliation and extension for independent review, not a new discovery, execution or finding certification. It does not claim ordinary legal play creates more than four full rows. No code, test, CI or requirement change is included.

## Row-clear partitions

For count1..4 and an ordinary finite nonnegative integer prior score, the lookup supplies100,300,500 or800. Binary64 addition yields a represented integer in this bounded-positive-increment domain, but precision can change the semantic score at huge magnitudes. Even at the largest finite score, these small increments round back to a finite score rather than crossing the overflow threshold. These must not be silently certified as exact SCO score additions. At ordinary small safe scores the arithmetic is exact within the safe-result range.

For count5..20 the table lacks a property. Under ordinary built-ins and no prototype modification, its value is undefined. Adding it to an ordinary numeric prior score yields NaN. This is a source deduction, not a production return log. A guarded route may catch the invalid score later and stop; direct clearFullRows has no postcondition check. Side effects between score assignment and the enclosing check remain separate.

An independent admissible snapshot partition can use a dense20x10 board with five full bottom rows, ordinary canonical current piece above them, real upcoming pieces, scorezero and compatible paused/playing fields. B15 does not reject this snapshot merely because those rows are full. The released parser rejects any fully filled row (session.js93-94), so this five-full-row board cannot pass it under ordinary complete-payload premises. That implementation rejection does not change B15 snapshot meaning. Direct field/writer injection and legal gameplay reachability remain separate; accepted Continue is not a route to this exact full-row board. No incomplete snapshot is labeled wholly valid here.

## Relation to gravity request certification

Initialization and accepted Continue support the numeric score premise at their assignments only. They do not discharge all later writers. The greater-than-four-row case means a proof saying every R1-valid input keeps that numeric premise is incomplete without a selected handling/route theorem. If a guard stops before issuing a gravity request, the absence of a request is not a bad ms value. If NaN reaches a request through direct or failed-stop composition, that is a distinct case needing evidence, not an inference from this map.

Keep snapshot admission, ordinary legal reachability, every writer's arithmetic, error/persistence/checkpoint effects, request existence and requested value separate. No broadened F22/PLY2/SCO2/R1/Phase4 certificate follows from the previous documentation merges.
