O1
requirement/property:
  O1. Authoritative transition boundary

A transition is a specified legal operation that attempts to move the authoritative state from one certified state to another certified state, or to the certified safe terminal/fault state. Phase 1 independently defines which states are valid, which operations are legal, and what each operation is permitted to change.

The Phase 1 model must also define whether a transition is evaluated only at its commit point or whether intermediate mutations must themselves preserve validity. Where intermediate mutations are permitted, the model defines the failure or rollback semantics that make a thrown transition safe. The audit assumes neither atomicity nor a rollback mandate unless the requirements provide one.

Defining the boundary does not narrow when SAF-4 requires invariants to be checked. SAF-4 requires the engine to check its invariants "after every action and every timer", and the model preserves that wording literally. Reading it as a check at fewer points, for example only at commit points, is a requirement clarification or change that needs the owner's approval. It is not a modelling choice.

A certified authoritative state is a state satisfying the Phase 1 valid-state model (1.3), or the safe terminal state as defined in 1.3. Phase 2 uses this definition and does not redefine it while inventorying routes. Until Phase 1 approval, this definition is a specification target, not a production predicate and not evidence of correctness; it is never defined retrospectively from what the implementation accepts. After Phase 1 approval it is the approved audit definition, and production code is judged against it.

The authoritative transition boundary is the conceptual commit boundary at which a specified legal operation commits the changes Phase 1 permits it to make to authoritative state, or enters the certified safe terminal/fault state, including authorized persistence effects belonging to that transition.

The boundary is defined independently of the current implementation. Phase 2 maps it onto the production code and inventories every route that can reach or bypass it.

Existing functions do not become authoritative merely because they contain validation.

Any privileged exception is explicit and separately proved.

Whether multiple implementation routes should be consolidated is a Phase 6 construction question, not a premise of the audit.
Applicable requirement identification: PCE-6,STA-1,STA-2,STA-3,SAF-3,SAF-4 (D25); shaped D16/D17/D20 plus D18/D22-D23,D31-D34.
the applicable state property it implies:

O4
requirement/property:
  O4. Persistence ordering

For persistence effects where the applicable requirements require preservation of the last-known-good persisted representation, the transition must not destroy that representation before the corresponding engine transition has reached the required post-transition validation boundary.

This ordering rule applies only where preservation is required. The authority order is: REQUIREMENTS.md, then an owner-approved requirement clarification or change, then adopted security properties such as O4, then implementation interpretation. O4 is subordinate to the applicable requirement semantics. An owner decision on R2 or R4 cannot silently override an existing requirement: if a decision would contradict a requirement (for example SAF-3 or STA-1), the requirement must first be clarified or changed through the owner-approved route, and until then the conflict is recorded and not certified. O4 does not by itself decide those questions.

For this audit, “last known-good” means the persisted representation observable through the application's storage interface. Stronger crash/power-loss durability is outside the certification claim unless independently established.

What makes a persisted representation "good" is defined from the requirements and the Phase 1 valid-state model (1.3), not from the production parser or the implementation's current validation sequence. A newly written save is good when it encodes a state that is valid under the Phase 1 model and satisfies the applicable persisted-state requirements (SAF-1 and STA-4). A save already in storage when the game started is good when it encodes such a valid persisted state (SAF-1, STA-4 and STA-6; STA-6 requires supported earlier formats to keep loading, and such a save cannot be known to have passed the current implementation's checks), regardless of whether the current implementation would accept it. This is the default content definition. It does not mention the transition that wrote the save, so it does not depend on what O4 and F20 examine, and it does not decide whether a save written during a step that then faults counts as the last good save; that is decided under R4. O4 then asks separately whether a transition preserves that last good representation until the required post-transition validation boundary. Validity of the persisted state, correspondence of what is persisted to the committed state the requirement calls for (examined in F20), and implementation ordering are three separate questions. Whether `parseSession` accepts a stored value is evidence about that definition, not the definition. A disagreement between the model-side validity predicate and `parseSession` is itself a candidate finding.

This definition covers the saved game only. What makes the saved-game flag and the stored high score good is decided under R4.

A required forgetting effect is not automatically treated as a replacement write.

R2 must explicitly determine:

* what persistence effect New Game (STA-1) and game over (STA-3) each require, and whether "forgotten" means deletion;
* exactly when that effect commits;
* whether a replacement persistent state exists;
* what must survive if New Game, or the step that ends the game, fails after or around that effect;
* whether the existing REQUIREMENTS.md text already determines the result, or an explicit requirement clarification or change is required first.
Applicable requirement identification: STA-1,STA-3,STA-4,SAF-2,SAF-3 (D25); D21S1-S9,D22,D23U1,D33C1.
the applicable state property it implies:
  Where preservation required, storage-interface last-good representation survives until required validated commit. Separate content goodness, correspondence to completed turn and ordering. Good save successfully written even if later fault per S6; no rollback mandate. Forget means withdraw, not delete.
the transition classes that can affect it, where applicable:
  Confirmed NewGame, ordinary over from spawn/hold, completed-turn line-clear save, pause save, failed save/withdraw/read, invalid-save withdrawal, engine fault around each effect; highscore independent R4 goodness/order question.
the production routes or trusted components for those transition classes:
  P2-B W-a..c and P2-A call sites reset/generate/hold/save/clear/failSafe/runChecked; no blanket every-write-preservation premise.
the model transitions that correspond to them, where the model is applicable (otherwise actual independent evidence method):
  Rev4 _withdraw/_save/_lock/pause/_game_over/continue_game/fault_stop provide semantic effects only; storage callable cannot rewind on Undefined. No engine-validation checkpoint or arbitrary throw/cancel/instruction-level ordering oracle. Actual independent storage/fault injection needed.
claim:
  Each required-preservation effect retains the correct good state through relevant failures while mandated withdrawal and successful-good-write rules are honored. Crash/power-loss durability not claimed.
Proof Method:
  Effect-by-effect applicability table; inject each real failure before/after mutation, serialization,write and validation; compare actual storage interface and model-independent good-content predicate plus completed-turn mapping. Document cutpoints and consequences separately.
assumptions:
  D23 successful operations trusted; failures do not stop gameplay; D21 last-good/no rollback/withdraw semantics. No disk durability or rollback of caller side effects assumed.
covered production code:
  manager.js:182-243,317-350,389-454,559-580; session serialize/parser; highscore/flag getters/setters:133-176. P2-B call-chain/cutpoint inventory.
covered model code, if applicable:
  Rev4 _withdraw:121-123,_save:128-132,_lock:284-295,pause:307-314,continue:326-342,fault_stop:406-409; atomic:30-40 handles Undefined only, not storage rollback semantics.
evidence:
  D21/D33 decisions and P3-D persistence candidates; frozen source confirms semantic write outcome interface and stated side-effect limitation. No instruction cutpoint failure tests or storage observations run.
limitations:
  Need per-effect preservation applicability and actual throw/validation/cancel trace matrix. Highscore order cannot be presumed saved-game rule. Model externally observable write callback can fire before Undefined: preflight choices and reject trace, not infer preservation. F20 ordering/consequence and F23 mechanism still candidates, not folded without reproduction.
certification status:
  Not Assessed. Candidate mapping/evidence only;no implementation certification or oracle acceptance.

O8
requirement/property:
  O8. Independent executable reference model and correspondence

The reference model is independently constructed and executable.

It must not mechanically reuse implementation transition logic or validation helpers.

The model and production implementation must not share faulty logic capable of making both agree on the same incorrect behavior.

Correspondence between the model and implementation is established through independently designed differential tests and an explicit independence argument.

Correspondence evidence is not treated as proof merely because both sides agree.

Authorship independence: this limits how the model is constructed. The model author builds the model only from a model input pack. Someone other than the author prepares the pack, the owner approves it, and its contents are recorded by checksum. The pack contains only: (1) REQUIREMENTS.md; (2) the text of the owner's approved Phase 1 decisions, including the applicable state categories and transition/property scope, with implementation names, code locations, test names, observed behavior and finding records removed, except that an identifier of a persisted or user-visible field stays where the decision cannot be stated without it; (3) a published specification or oracle that the owner adopted in Phase 1, as published. The author does not receive the rest of this blueprint or DECISIONS.md, because they report implementation behavior, and must not read the production implementation code, the production tests (test/ and e2e/), or fixtures and expected outputs derived from the implementation, including saved-game fixtures from released versions. Where this cannot be met, the exception, the reason and the independence argument that replaces it are recorded. The owner must approve the exception before model construction proceeds. An exception cannot permit exposure to production behavior unless the owner accepts the replacement independence argument. The limit ends when the model is frozen: its source and the pack are recorded by checksum before any comparison with the implementation. After the freeze the author may take part in differential testing and correspondence review. After the freeze any change to the model gets a new checksum and a written justification from REQUIREMENTS.md or an approved Phase 1 decision that does not rely on the implementation's behavior; a change made only to agree with the implementation is recorded as a correspondence result, not as a model fix.
