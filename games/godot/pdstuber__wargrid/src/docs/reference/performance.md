### Known M4 combat cost risks (found by code review 2026-11-03, unmeasured)

Both risks come from the Tasks 1–4 code (`game/scripts/simulation/combat.gd`). Neither is fixed. Task 9a's `contact`/`open` layouts are the measurement. Fixes need user approval.

1. **Full enemy rescan (confirmed by the scratch spike in History: 12.5–15.3 ms p95).** A guard or attack-move unit with no valid in-range target scans every enemy object every tick (`Combat._nearest`). Retaining a valid target skips the scan, but approaching armies have none. Cost grows as armed units × enemy objects: 150 v 150 advancing is about 22,500 distance checks per tick, and `combat_work()` counts them. The plan names a candidate fix: a coarse grid index for acquisition.
2. **Attack-move halt/resume thrash.** A halted attack-move unit resumes when its target leaves range or dies, through `_assign_move` → `Allocation.assign`. Resumes are batched to one call per goal group per tick, but each call costs 2.2–2.4 ms on 48×32 and 6.0–6.3 ms on 64×64 ([envelope](m4-scenario-envelope.md)): about 1.3–3.8× the whole 1.67 ms p95 budget. A fight at a range boundary can trigger a call on many ticks. Plan Task 4c adds `allocation_calls()` so 9a can report how often this happens. Candidate fixes, not designed: a short resume cooldown, or resuming toward the previous destination without reallocation.
**Decision 2026-11-03 (user approved P1 and P2; implementation is plan step 4d, assigned to Sonnet):**
- **P1: throttled acquisition.** 15-tick staggered rescans for untargeted units; immediate on spawn, order or target loss.
- **P2: halted attack-move units keep their slot.** They resume without `Allocation.assign`.
- **Source basis:** Zero Hour `MoodAttackCheckRate` (default 2 s, `AIUpdate.cpp` 89, 4566–4576), immediate retarget on loss (`AIStates.cpp` 3617–3641), and attack-move re-pathing to its existing goal (`AIStates.cpp` 3661–3664), at revision `0a05454`.
- **Scratch prototype results (reverted, not in tree):**

| change | contact p95 | open p95 | open ticks with an allocation pass |
|---|---|---|---|
| before | 12.5 ms | 15.3 ms | n/a |
| P1 | 1.31 ms | 6.6 ms | 119, about 7.5 ms each |
| P1 + P2 | 1.41 ms | 1.69 ms | 1 |

- **Remaining:**
  - `open` sits at the 1.67 ms line; 300 moving units alone cost about 1.58 ms.
  - Worst tick, about 28 ms: the initial attack-move command allocation, outside Task 9a's 300-tick warmup, but about 170 ms at F = 6.
  - Further options, not approved:
    - P3: grid index for acquisition.
    - P4: ring-expansion `Allocation.assign` instead of a full component sort. P4 also helps M2 command ticks but touches replay-compared M2 code.

3. **Mass pursuit spike (Grok review).** `_firing_cell` scans the target's range box (rifle about 9×9 cells, cannon about 13×13, plus a building's footprint). If 150 units get `attack` in one tick, or their chase destinations are invalidated on the same 15-tick beat, that is about 25,000 cell tests in one tick, on top of the existing command-tick path burst. Unmeasured; it shows up as `combat_work()` max in Task 9a.

Derived budgets are proposals. Do not loosen a budget or the factor to make a row pass; either optimize, or ask the user to change the target. M4 snapshots add combat fields, so plumbing will grow; the cheapest fix is probably to stop copying the whole state twice per tick (not designed).

## Rule per milestone

A milestone exit gate is not met until: `sh tools/run_benchmark.sh` passes, the rendered benchmark was rerun if presentation changed (`sh tools/run_game.sh res://scenes/movement_benchmark.tscn`, header must show `vsync=off`), and this ledger has a new History row with measured values against the budget table, with the machine named. Missing or exceeded rows are reported as exceeded, never as passed.

### Technology findings

- Typing: the simulation was already typed on numbers; the gain came only where a Variant sat in float arithmetic inside a per-unit loop (Horde, Locomotion, `_advance`: about 0.03-0.08 ms per tick, 3-5 %). Typing `_nearest`, `plan` and friends gained nothing. About 125 of 1,044 `unsafe_*` findings sit in the hot functions and the count does not predict gain, so driving it to zero is not a performance task.
- Threads, native: safe but not worth it. Parallel `advance.move` gave digests equal in every tick of 2100 on four workloads (P1-P4 plus two mutations red) but only 0.04-0.07 ms (2-3 %) at 4 threads, a loss at 2 threads; speculative `_nearest` was slower on every row. Scope of "safe": native, M6 only, P4 (no shared route arrays) sampled, load 3.2 at the start of timing; native against WASM agreement in parallel mode was never measured.
- Threads, web: a threaded build costs +4.7 % (combat open p50) to +8.3 % (dense) in Firefox and about 0 in Vivaldi (Chrome/156). A threaded web build is expected to lose, measured for Firefox only; the Vivaldi net effect is unmeasured (task 5c skipped by coordinator decision: the native gain is 2-3 %, far below the 10 % bar). It works: on the fly static server (test app, COOP and COEP on all 18 responses including precompressed ones) Firefox and Vivaldi boot the threaded build with `crossOriginIsolated=true`; rolled back. Safari untested. The relay works under COEP (`RELAY OK`) only from the local origin; from the fly origin the check was boot-only. Chromium results come from Vivaldi; Chrome was not tested.
- Digests: native editor, native release, no-threads web and threaded web gave equal `DIGEST` lines on 8 workloads including the 45000-tick team match. That does not close the README item "mixed browser and desktop match (floats in WASM versus native)": no mixed match through the relay was run, so it stays open in the README.
- C++ / GDExtension: not investigated, by user decision.

### Recommendations (benefit, effort, risk)

Rec numbers are kept as first written (other notes cite them); rec 1 is listed last because its design says not to build it.

- **Rec 2.** Per-cell, per-team enemy counts so empty cells skip `_nearest` buckets. Benefit: fewer `_nearest` bucket visits. Bound (T0c, 2026-11-08, from code reading, no new run): since 2b `_nearest` already skips non-hostile owners and empty cells at one `cells.has(key)` per window cell per hostile owner, so per-team counts save only the extra lookups when there is more than one hostile owner. `open`, `dense`, `contact` and `hordes300` have one hostile owner (bound 0); only the team match and `skirmish3v3` have more, and both already pass 1.82 / 3.64. Not attempted, not on a failing row; the per-lookup cost is an unmeasured estimate. Effort: medium. Risk: state to keep in sync with removals.
- **Rec 3.** One entity pass for `draw.units` instead of five. Benefit: up to about 0.3-0.5 ms per rendered tick on 300 units (estimate, not measured: the audit shows `draw.units` 1.05 ms, of which four of the five passes are the ones to merge; the saving is unprototyped and needs the U3 rendered batch). Effort: small. Risk: low, presentation only.
- **Rec 4.** hordes300 (2.82 against 1.82) needs a structural change; it is not closable in GDScript with what was tried. Benefit: large. Effort: large. Risk: high. **Planned for later (user, 2026-11-08):** a shared persistent grid with incremental horde and locomotion updates, as its own task after the `_hold_cells` occupancy set (rec 1) has been measured; not started, needs its own design and the same trace-preservation gate.
- **Rec 5.** Consider enabling `unsafe_method_access` and `unsafe_property_access` warnings after counting the violations. Benefit: catches new Variant-in-hot-loop regressions. Effort: small to count, unknown to clear. Risk: warning noise.
- **Rec 1. Design recommends: do not build; at most run its Task 0 gate (user's go only)**, see [the design](../superpowers/specs/2026-11-08-hold-cells-occupancy-design.md). Persistent occupancy set for `_hold_cells`, maintained across ticks. Benefit: removes the 0.06-0.16 ms post-removal cost (2i), the largest remaining open / dense p95 item. Effort: medium. Risk: touches several functions in `combat.gd`; needs an Opus design first.
