## 1. The system at a glance

SPPPD has two programs:

| Program | Language | Runs as | License |
| --- | --- | --- | --- |
| The game | Lua on LÖVE 11.5 (LuaJIT, Box2D, OpenAL) | Desktop, Windows zip, Android APK | GPLv3 |
| The relay | Go 1.21, standard library only | One binary, UDP plus an optional HTTP dashboard | AGPLv3 |

The game ships almost no assets. The only binary in the repository is one font.
Textures, car sprites, meshes and every sound are generated by code at startup. The
player's own music, in freestyle, is the single exception.

The game has these layers. Each one uses its own layer and those below it:

```
 main.lua            LÖVE callbacks, screen switching, loading
 ───────────────────────────────────────────────────────────────────
 Screens             splash   menu   editor
 ───────────────────────────────────────────────────────────────────
 Session             race_manager: owns one running race and everything
                     around it (camera, ghost, pace notes, finish, sound
                     and vibration updates)
 ───────────────────────────────────────────────────────────────────
 Presentation        render/*  hud  minimap  vfx  skids  audio  radio  rumble
 Input               input  touch  ui
 Network             network_manager
 ───────────────────────────────────────────────────────────────────
 Rules               sim/race  sim/slipstream  sim/remote_driver  ai_controller
 World               entities/car  world (Box2D)
 Pure models         sim/dynamics  sim/track  entities/vehicles/*  config
```

Three ideas shape everything else:

1. **The simulation knows nothing about the screen.** `sim/race` steps at a fixed
   120 Hz and draws nothing, so whole races run headless in tests. `sim/dynamics` and
   `sim/track` don't touch LÖVE at all and run under plain LuaJIT.
2. **Box2D only handles contact.** Tyres, engines and aero live in `sim/dynamics`,
   which hands Box2D a net force and torque each step. Box2D integrates them and
   resolves collisions.
3. **The AI drives through the same input table as a player.** It can't do anything a
   car's physics wouldn't let a person do. It only knows the racing line in advance.

### Who owns what

Most game state lives in module-level singletons, because there's only ever one of
each thing at a time:

| Singleton | Holds |
| --- | --- |
| `state.screen` | `splash`, `menu`, `race` or `editor` |
| `race_manager` (private `session`) | The running race, or the demo race behind the menus, with one view per driver at the screen |
| `world` | The one Box2D world. `Race.new` replaces it, so two `Race` objects can't exist at once |
| `network` | The one connection |
| `input`, `touch`, `ui` | Current controls and menu state |
| `settings` | Saved preferences, plus private lap records |

## 3. Startup and the main loop

### Choosing what to run

`conf.lua` runs first and reads the command line. `--test` removes the window,
graphics and audio modules and switches the save identity to `spppd-test`. `--visual`
keeps them, turns vsync off and uses the same test identity.

`main.lua` then picks one of these:

| Command | What runs |
| --- | --- |
| `love .` | The game |
| `love . --test [filter]` | `tests/run.lua`, then quit with its result. Main returns before loading any game module |
| `love . --perf` | `tests/perf.lua` after a blocking load |
| `love . --visual flow` | `tests/flow.lua` |
| `love . --visual online` | `tests/flow_online.lua`, with `SPPPD_RELAY` set to a local relay |
| `love . --visual <scene> [out] [frames]` | One scene from `tests/visual.lua` |

### Loading behind the splash

`love.load` wraps the slow work in a coroutine, `loadGame`: compile shaders, generate
textures, then load or render every sound. `love.update` resumes it once a frame, and
the splash shows `LOADING` while it's alive. `audio.load` yields through `breathe()`
at most every 1/30 s, and every frame while threads render a first launch, so a slow phone keeps drawing frames during a first launch. The
yield sits inside a `pcall`, which works because LuaJIT can yield across `pcall`.

The splash timer starts only when loading finishes. Its first update plays the
1.7 s startup sound, and the menu follows when that ends.

### Screens

```
             1.7 s sound              START, HOST/JOIN
   splash ───────────────▶ menu ─────────────────────▶ race
                            ▲ ▲                         │
                            │ └────── QUIT TO MENU ─────┘
                 BACK       │
                            ▼        T (test drive)
                          editor ──────────────────────▶ race
                            ▲                             │
                            └────── BACK TO EDITOR ───────┘
```

### One frame

LÖVE delivers input events, then `love.update`, then `love.draw`.

`love.update` dispatches by screen. In a race it also does the pause check:

```lua
if input.consume("pause") and not rm.isFinished() then
  rm.setPaused(not rm.isPaused())
  ui.nav.back, ui.nav.ok = nil, nil   -- Esc and Start also work the menu
end
rm.update(dt)
menu.updateOnline(dt)   -- network, and a rematch starts from here
```

`love.draw` draws the current screen, then the pause or results overlay if one is up.
It plays any menu sound the UI asked for and calls `ui.endFrame()`, which clears
one-frame clicks and navigation. That's why the pause check clears `back` and `ok`:
the pause menu draws in the same frame, and would otherwise act on the same press.

### Who receives each event

| Event | Goes to |
| --- | --- |
| Key press | The editor alone on that screen. Otherwise `ui` and `input`, and in a race it hands control back from touch |
| Text | Editor or `ui` |
| Touch press | Sets `touch.active`. Reaches `touch` only while driving, not paused and not finished |
| Mouse press | `ui`, the editor, and `touch` as a finger with id `"mouse"` unless it's a tap |
| Pad button | `input` and `ui`, and clears `touch.active` |
| File dropped | `radio.addFile` |
| Focus lost | Pauses a race, unless `rm.keepRunningUnfocused` is set by the test harnesses |
| Focus gained | Rescans the music folder and the saved tracks |

Phones deliver a tap twice: once as a touch and once as a mouse event marked
`istouch`. The touch drives the car and the mouse event works the menus, which is why
the handlers check `istouch`.

## 4. Units and coordinates

| Quantity | Unit | Conversion |
| --- | --- | --- |
| World positions, Box2D, rendering | Pixels | 12 px per metre (`config.METER`) |
| Vehicle model | SI: metres, m/s, N, kg, radians | `Car:getVelocity` divides by 12 |
| Forces sent to Box2D | kg·px/s² | Newtons × 12 |
| Torque sent to Box2D | kg·px²/s² | N·m × 144 |
| Inertia in Box2D | kg·px² | kg·m² × 144 |
| Track file units | 1/3 px by default | `TRACK_SCALE = 3`, so 4 units = 1 m. BOAT uses 3.8 |
| Layout | `ui.scale` units | 1 at 640×360, in half steps, 1.5× larger on a phone |

Directions:

- World: +x right, +y down, angles clockwise on screen.
- Car body frame: +x forward, +y to the driver's right, positive yaw clockwise.
- Wheels: 1 front left, 2 front right, 3 rear left, 4 rear right.
- Track: sample 1 sits on the start line, indices increase in the driving direction,
  and each sample's normal `(nx, ny)` points to the driver's right.

## 5. The simulation step

### Fixed timestep

`rm.update` adds frame time to an accumulator and runs `race:step(1/120)` until it's
spent. The accumulator is capped at 8 steps (`MAX_STEPS_PER_FRAME`), or 66.7 ms. Below
15 fps the race slows down instead of spiralling. Drawing interpolates between each
car's last two poses using `session.alpha`.

### `Race:step(dt)`

```
countdown phase                          racing and finished phases
  timer += dt                              time += dt
  for each car:                            for each car:
    throttle, steer, handbrake = off         driver:update(car, race, dt)
    input.rev = driver:revs(dt) or 0
    input.boost = driver:boostButton()
  timer >= startDelay:
    phase = racing, justStarted = true
    clear input.rev; launch every local car

then, in every phase:
  for each car:
    slipstream.update (local cars only)
    car:step(dt, track)        surfaces, dynamics, apply force and torque
  world.step(dt)               Box2D: 8 velocity, 3 position iterations
  for each car:
    car:afterStep()            record the new pose
    updateProgress             distance, laps, wrong way, finish
  standings()                  sort and assign places
  finishGrace countdown
```

The race keeps stepping after `phase` becomes `finished`, so cars drive on behind the
results.

### `Car`

A car is one dynamic Box2D body plus a `dynamics` model:

- The fixture is a chamfered eight-sided box from `spec.length` and `spec.width`, so
  cars don't snag on each other. Friction 0.25, restitution 0.15.
- Mass and inertia come from the spec through `setMassData`, not from the shape.
- It's a bullet body, so a fast car can't tunnel through a barrier.
- `input` is the table every driver fills: `throttle`, `brake`, `steer`, `handbrake`,
  `boost`, `manual`, `shiftUp`, `shiftDown`, plus `keyboard` and `rev`.

`Car:step` finds the surface under each wheel with `track:surfaceAt`, then calls
`dynamics.step` with the body-frame velocity, rotates the result into world space and
applies it. A remote car stops after the surface check: its motion comes from packets.

`Car:teleport` zeroes the body and part of the model. With `ghostTime`, the car also
ignores other cars for that long by masking `CATEGORY_CAR`, and `car_view` flickers it.

### `world`

`world.load(track)` builds a zero-gravity Box2D world and one chain shape for each
barrier (friction 0.15, restitution 0.2). The `postSolve` callback records impacts
above `200 * M` into `world.events`, capped at 16 per drain. `race_manager` reads them
after each step, so collisions trigger sparks, camera shake, sound and vibration
without any Box2D callback touching those systems. Any contact at all also sets
`car.scraped`, because a car dragging along a wall is far below that threshold.
`race_manager` turns that into `car.scraping`, 0 to 1, for the sound.

The same callback adds each hit from a fence to `car.fenceImpulse`, whatever its size,
and sets `car.touchedCar` on a contact between cars. See "Wrecks" in section 9.

## 6. The vehicle model

`src/sim/dynamics.lua` turns chassis velocity and driver input into a net force and
yaw moment. Its model object (`c`) holds everything persistent: steering angle, gear,
revs, filtered accelerations, boost state, and per-wheel loads and slips.

### Order of one `dynamics.step`

1. Boost state, drift amount, steering.
2. Pedals, including the shift into reverse.
3. Slip angle `beta` and its rate.
4. Stability control and drift moments.
5. Vertical load on each wheel.
6. Gearbox and drive force.
7. For each wheel: grip, tyre forces, brakes, ABS, traction control, friction circle,
   rolling resistance.
8. Aero drag, then the arcade push terms: carry, tow, launch and boost.
9. Filter `ax`, `ay` for the next step's weight transfer.

### Handling tiers

Set in `dynamics.ASSISTS`. `steer` and `caster` are real effects. Everything from
`grip` on is arcade tuning, and its neutral value leaves the physics alone.

| | ARCADE | FULL | SPORT | SIM |
| --- | --- | --- | --- | --- |
| Selectable | Yes, default | No | Yes | Yes |
| `tc`, `abs`, `esc` | 1, 1, 0.7 | 1, 1, 1 | 0.8, 1, 0.5 | 0, 0, 0 |
| `steer`, `caster` | 1, 0.85 | 1, 0.85 | 0.9, 0.75 | 0, 0.35 |
| `grip` | 1.3 | 1 | 1 | 1 |
| `tyreC` (lower keeps more grip past the peak) | 1.15 | 1.35 | 1.35 | 1.35 |
| `transfer` (weight transfer felt) | 0.6 | 1 | 1 | 1 |
| `keyRate` (keyboard steering speed) | 1.9 | 1 | 1 | 1 |
| `turn` (yaw pull towards the steering) | 7 | 0 | 0 | 0 |
| `carry` (cornering scrub given back as speed) | 0.75 | 0 | 0 | 0 |
| `drift` (handbrake starts a held drift) | 1 | 0 | 0 | 0 |
| `offroad` (loose-surface penalty forgiven) | 0.6 | 0 | 0.14 | 0 |
| `brake`, `shift` multipliers | 1.25, 0.5 | 1, 1 | 1, 1 | 1, 1 |
| `tow` (slipstream pull, m/s²) | 0.9 | 0 | 0 | 0 |

FULL exists for the AI and the demo race. AI cars use ARCADE when the player does and
FULL otherwise, because arcade grip is much higher and the grid wouldn't match. Online,
each driver uses their own tier and gearbox: another driver's car runs no tyre model on
this screen (see Remote cars), so their handling changes nothing for anyone else, and
slipstream `tow` follows the handling of the car being pulled. 3.0 games still force
ARCADE on themselves.

### Surfaces

| Surface | Grip | Rolling | Speed drag | Loose |
| --- | --- | --- | --- | --- |
| Asphalt | 1.00 | 0.014 | 0 | |
| Kerb | 0.90 | 0.020 | 0 | |
| Grass | 0.48 | 0.070 | 0.022 | Yes |
| Gravel | 0.42 | 0.180 | 0.060 | Yes |

On a loose surface grip is multiplied by `spec.looseGrip`, then pulled back towards
full grip by the tier's `offroad`. The rolling and drag penalties are scaled by
`(1 - offroad) * spec.looseDrag`.

### Steering

`dynamics.steerLimit` gives the angle a full input asks for at this speed:

```
turnIn = atan(wheelbase × grip × g / speed²) + 0.9 × peakSlip
limit  = lock + (min(lock, turnIn) - lock) × assist.steer
```

So with assists on, full input is the angle that holds the front tyres near peak
grip, and on SIM it's full lock. Keyboard steering is all-or-nothing, so it winds on at
`7 × keyRate / (1 + speed/22)` units/s and releases at 9. Analogue input passes
straight through.

The steering target adds a caster term that pulls the wheels towards the direction of
travel at the front axle, which is what catches a slide. Then the wheel moves at a
speed-limited rate, `steerSpeed / (1 + 0.018 × speed)`, and 1.6× faster when input is
released.

### Tyres

Each wheel works in its own frame, rotated by the steering angle at the front.

```
loadRatio = fz / nominalLoad
mu        = grip × max(0.6, 1 - 0.09 × (loadRatio - 1))     load sensitivity
maxForce  = mu × fz
alpha     = atan2(lateral speed, max(|forward speed|, 2))
Fy        = -maxForce × sin(C × atan(B × alpha))            Pacejka shape
B         = tan(π / 2C) / peakSlip                          peak at peakSlip
```

`Fy` is clamped to what would stop lateral motion within one step, which prevents
jitter at low speed. Past the peak a tyre keeps `sin(C × π/2)` of its grip: about 0.85
at the realistic `C` and 0.97 on ARCADE, which is much of why ARCADE slides are easy.

Longitudinal demand then goes through these stages in order:

1. Drive share by layout. AWD splits by `awdFront`.
2. Braking by `brakeBias`, plus handbrake force on the rears.
3. ABS: limits the brake force so spare friction remains for steering. A wheel locked
   by the handbrake is exempt.
4. Traction control: limits drive to the spare friction.
5. **Friction circle:** if `sqrt(Fx² + Fy²) > maxForce`, both axes scale down, so a
   spinning or locked tyre loses side grip too.

`w.slide` (0 to 1) and `w.spin` report how far past the limit a tyre is. They're used
for sound, smoke and the HUD, and have no effect on forces.

### Vertical load

```
downforce = 0.5 × 1.2 × liftArea × v²
static    = (weight + downforce) split by weightFront
longShift = mass × ax × cgHeight / wheelbase / 2 × transfer
latTotal  = mass × ay × cgHeight / track × transfer, split by rollBalance
```

`ax` and `ay` are the previous step's accelerations, low-pass filtered at 70 ms, which
stands in for suspension. Each wheel keeps at least 120 N.

### Powertrain

- **Torque curve:** a piston engine peaks at 60% of redline. A motor (`spec.motor`) is
  flat to 30% and then constant power.
- **Revs:** follow `max(wheel-coupled rpm, clutch-slip target)` with a rate of 14/s.
  The clutch target holds a launching engine near 48% of redline. A motor has no
  clutch and its torque is read directly from wheel speed.
- **Automatic gearbox:** up at 96.5% of redline with a 0.45 s lockout. Down as soon as
  the lower gear would sit under `redline × (0.62 + 0.18 × throttle)`, with a 0.3 s
  lockout. No drive during a shift (`shiftTime × assist.shift`).
- **Manual gearbox:** `shiftUp` and `shiftDown` only. It needs the MANUAL setting, and
  touch always forces the automatic.
- **Engine braking:** a small negative drive force with the throttle closed.
- **Reverse:** hold the brake for 0.25 s below 0.8 m/s. The brake pedal then acts as a
  60% throttle, up to 11 m/s, and pressing the throttle cancels it.

### The lights and launch

During the countdown the clutch is in, so `input.rev` spins the engine against a
limiter (cuts at 97% of redline, recovers at 92%). The revs move slowly enough to hold
by ear: rising at 3/s, falling at 1.5/s.

When the lights go out, `dynamics.launch` scores the revs. Inside 62 to 82% of redline
scores 1, falling to 0 over a further 15% of redline. The score gives up to
7.5 m/s² of extra push, fading over 1.2 s and scaled by throttle. It's applied to the
chassis, not the tyres, so wheelspin can't eat it.

### Boost

`boostState` is `ready`, `active` or `cooldown`, and each press toggles it. The full
rules:

- The tank holds `boostTime` seconds (3 by default) and burns 1 per second.
- It refills at `boostTime / boostCooldown` per second, only while boost is off.
- A slide triples the refill. `dynamics.sliding` means more than 20° of slip above
  7 m/s, not in reverse. **This is the only way to earn boost, and that's deliberate.**
- Below 0.25 s in the tank it reads `cooldown` and can't be lit.
- Braking shuts it off and blocks lighting it.
- Nothing happens at the lights, and a button held through lights-out needs a fresh
  press.

While active, the pedal is at least 0.75, and the car gets a force of
`boostPower / 22` N directly on the chassis. It bypasses the tyres because traction
control would otherwise cut it exactly where it's wanted, in low gears and out of
corners.

It also carries the car where its nose points, which is what saves a slide. A second
force acts across the direction of travel, towards the nose, swinging the travel round
at 4 times the slip angle per second, up to 0.9 g plus 2 g times `c.drift`, without
changing the speed. A drift is a bigger slide than the tyres alone get into, and
unwinds quickly on its own, so a boost save out of one needs the extra. It
never turns the nose itself, so a turn on grip, where nose and travel already agree,
is barely tighter (the test allows 12%), and the driver still has to point the car
somewhere. Grass and gravel drag is halved under boost. Not removed, or a boosted cut
across the grass would cost nothing.

### Stability control and drifting

This is the most tuned part of the model. It applies when `esc > 0`, speed is over
4 m/s and the car is moving forwards. It produces one yaw moment, `escMoment`, built
in stages:

1. **Reference yaw:** `vx × tan(steer) / wheelbase`, capped at
   `1.15 × grip × g / speed`.
2. **Turn help** (ARCADE only): adds yaw to rotate on to the line sooner.
3. **Over-limit correction:** when slip exceeds about 6° (0.11 rad), or yaw error
   exceeds 0.18 rad/s, it pushes back and cuts throttle. During a drift the slip limit
   moves out to 40° (0.7 rad).
4. **Past the drift limit:** a stronger moment turns the nose back towards the
   direction of travel.
5. **Settle on release:** letting go of a drift bleeds off rotation with both a yaw
   term and a damping term, which stops the tail swinging past centre.
6. **Hold:** with the handbrake held and the steering into the slide, the tail is
   sprung and damped towards `-steer × 0.7` rad. This replaced a catch that collapsed
   the slide about every 1.6 s.

The result is eased in over 60 ms so corrections never snap, except with the handbrake
held, when it applies instantly or a fast drift would spin first.

`c.drift` (0 to 1) rises at 15/s while the handbrake is held above 9 m/s on a tier with
`drift`. It then fades at 1/s, or 2.5/s once the slide ends or the throttle lifts. It widens the steering
range, weakens the caster, cuts rear grip by up to 55% and cuts handbrake force by up
to 85%, so the tail slides rather than locks. Key and arrow steering winds on up to 1.5
times faster in a drift.

`base.define` fills in defaults, so a vehicle file only states what's different. It
also derives `brakeForce` and `inertia` unless a file sets its own.
`garage` order matters: settings save a position in that list, so new cars go on the
end.

### Slipstream

`slipstream.wake(car, other)` returns how far `car` sits in `other`'s wake, 0 to 1:

- Both cars above 18 m/s and travelling within about 37° of each other.
- 3 to 32 m behind, measured along the leader's direction of travel.
- A wake 1.6 m wide near the car, spreading to 3.2 m.
- Full strength in the near half, centred.

`slipstream.update` moves `model.slipstream` towards the strongest wake, at 0.5/s up
and 0.9/s down. The slow fade is what makes a slingshot. The effect is up to 30% less
drag on every tier, plus an ARCADE-only pull of `mass × 0.9 × slipstream × pedal`.

## 7. Track geometry

`Track.new(def)` turns a definition into an evenly sampled closed ribbon that physics,
AI, rendering and race rules all share. It has no LÖVE dependency.

### Definitions

```lua
-- Spline: a centre line with a width on each side
{ title, theme, scale, runoff,
  nodes = { {x, y, wl, wr}, ... },
  startPoint = {x, y, angle} }

-- Boundary: two hand-drawn edges (BOAT)
{ left = segments, right = segments, startPoint = ... }
```

### The build pipeline

```
 def.nodes ──Catmull-Rom + widths──┐
                                   ├─▶ left and right edges
 def.left, right ──Bézier flatten──┘
            │
            ▼
 resample both edges at 1.25 m; reverse one if they're wound differently
            │
            ▼
 buildSamples   pair the edges into rungs, always advancing the side that gives
                the shorter rung (this copes with hairpins), resample to 2.5 m,
                and smooth three times
            │
            ▼
 orient         rotate so sample 1 is at startPoint, flip to match its angle,
                and decide which edge is the driver's left by majority vote
            │
            ▼
 computeCurvature   signed curvature over ±3 samples, averaged over ±2
 assignKerbs        corners tighter than 40 m radius: inside the apex, outside the exit
 assignGravel       corners tighter than 34 m: 7 m deep on the outside
 buildBarrierSide   twice, once per side
 buildRacingLine
 bounds
```

### What each sample holds

| Field | Meaning |
| --- | --- |
| `x, y` | Centre of the road |
| `lx, ly, rx, ry` | Left and right edges |
| `s` | Distance along the lap, px |
| `tx, ty`, `nx, ny` | Tangent, and normal to the driver's right |
| `w` | Road width |
| `k` | Signed curvature of the centre line |
| `kerbL`, `kerbR` | Kerb flags |
| `gravelL`, `gravelR` | Gravel depth, px |
| `barrierl`, `barrierr` | Distance from edge to barrier |
| `lineX, lineY, lineK` | Racing line and its curvature |

### Barriers

For each sample, the barrier wants to sit `runoff` metres from the edge (12 m by
default). That's reduced in three ways:

- On the inside of a corner it can't exceed `0.7 / curvature`, or the offset folds.
- A ray cast finds any other stretch of road nearby, and the barrier takes 46% of that
  gap, so neighbouring roads each get their own wall.
- It never goes below 2.2 m.

Offsets are then eroded over ±7 samples and smoothed eight times, so a barrier pulls
in ahead of a squeeze and stays a flowing line. `removeLoops` cuts any self-crossing
so Box2D gets a clean wall.

### Racing line

The line relaxes towards minimum curvature with a fourth-order stencil, each point
limited to the road less a 2 m margin. It runs at strides of 12, 6, 3 and 1 samples:
wide strides find the big arcs through a corner, and fine strides clean up. The
out-in-out shape comes from this and isn't drawn by hand.

### Queries

- **`Track:locate(x, y, hint)`** returns the nearest sample, distance along the lap,
  lateral offset and how far past the edge. With a `hint` it searches ±12 samples, so
  a parallel stretch of road can't steal the car, and only falls back to a full scan if
  the best match is over 30 m away.
- **`Track:surfaceAt`** is asphalt on the road. Past the edge it's kerb, then gravel,
  then grass.
- **`Track:gridSlot(n)`** gives staggered pairs: about 7.5, 10, 15, 17.5 m behind the
  line, alternating sides.
- **`Track:speedProfile`** gives a target speed per sample: `sqrt(mu × g / k)`, then
  backward passes for braking and forward passes for acceleration. The AI and pace
  notes use it with different parameters.
- **`Track:validate`** reports the editor's warnings: under 300 m, under 7 m wide,
  crossing itself, overlapping.
- **`Track:toNodes`** converts any track to editable nodes.

## 8. AI drivers

`AI.new` builds a speed profile for the car, and `AI:update` fills `car.input` each
step. Each driver has a `skill`, usually between 0.8 and 1.

**Speed profile inputs:**

| Parameter | Value |
| --- | --- |
| `mu` | `spec.grip × tier grip × 0.92 × skill` |
| `vmax` | `min(95, gearing limit)` m/s |
| `brake` | `0.72 × spec.grip × tier grip × g` |
| `accel` | `min(9, peakPower / (mass × 28))` |

**Steering** is pure pursuit. The target is on the racing line
`clamp(0.62 × speed + 5, 9, 46)` metres ahead, shifted sideways by the overtaking
offset. The wheel angle is `atan(2 × wheelbase × lateral / distance²)`, with the
caster term subtracted so the AI doesn't fight the steering model.

**Speed:** take the slowest profile value within `0.25 × speed` metres, multiply by
`skill`, and take 3% off while passing. Then:

```
throttle = clamp(0.45 × error + 0.1)
brake    = clamp(-0.3 × error)      and throttle = 0 if braking
```

Throttle is limited to 0.6 on loose ground and cut by 40% when sliding.

**Overtaking:** `planOffset` looks at cars from 2 m behind to 22 m ahead and within
4 m sideways, pushes away from them, and picks the side with more road when a car is
dead ahead. The offset is up to 4.5 m and eases in at 2.5/s.

**Getting stuck:** under 1 m/s with throttle on for 1.2 s means reverse for 1.4 s
with opposite lock. After three tries it respawns.

**At the lights** each driver hunts around 68% throttle on a sine wave. The swing
grows as skill falls, so better drivers launch better and none is perfect.

AI drivers never use boost or the handbrake, and darkness doesn't affect them.

`opts.digital` and `opts.reaction` make the AI behave like a keyboard or thumb player.
Only tests use them, to prove a person with those limits can lap every track.

A player who takes the flag gets an AI driver with `skill = 0.7` for the cool-down.

## 9. Race rules

### Modes

| Mode | Track | Laps | Grid | Ends |
| --- | --- | --- | --- | --- |
| `race` | Yes | 1 to 20 | Player last, up to 5 AI. Two at a screen take the last two slots, P1 first | At the flag |
| `trial` | Yes | 9999 | Alone, slot 1 | Never |
| `freestyle` | THE LOT (a concrete apron with a playground), or any track | 9999 | Alone, or two: slots 1 and 2 on a track, 3 m either side of the start box on the lot | Never |
| Online | Yes | Host's choice | Two to four drivers, in seat order | 25 s after the first car home |

Difficulty sets AI skill:

| | Skill | Spread |
| --- | --- | --- |
| ROOKIE | 0.84 | 0.03 |
| PRO | 0.92 | 0.025 |
| ACE | 0.985 | 0.015 |

Cars in the front half of the grid get `+spread`, the rest `-spread`, plus a random
share of the spread. AI cars come from the garage, offset by the seed.

### Progress

`updateProgress` keeps a continuous `car.distance` along the race:

- A car starting behind the line begins with a negative distance into lap 1.
- Each step adds the signed change in `s`, wrapped around the lap, so reversing takes
  distance away.
- **A jump over 45 m isn't counted**, and under clean rules it marks the lap unclean.
  That's how cutting across the infield fails to pay.
- A lap completes when `floor(distance / length)` rises, during `racing`.

So laps come from distance covered, and no checkpoints are needed.

`Race.new` takes `rules`. Under `"clean"`, the default and what a race always uses, a
lap stays **clean** unless all four wheels leave the road, a jump happens, the car
respawns or it's wrecked. `spoil` is the one place that marks it, and it calls
`onSpoil(car, reason)` once per lap with `off`, `cut`, `reset` or `wreck`. Time trial
shows that as a toast. Under `"open"`, the time trial default (SETUP > RULES), nothing
spoils a lap and every lap counts. Only clean laps count as a best lap.

Going backwards at over 4 m/s for 1.2 s shows WRONG WAY. Pressing reset (`R`) moves
the car two samples ahead on the racing line, stationary, and ghosted for 2.5 s.

### Wrecks

Fences can wreck a car. `Race:updateCrash` keeps `car.fenceHit`, the speed in m/s lost
to fences, which is impulse over mass and fades with a 0.15 s time constant, so a nose
and then the tail swinging in count as one hit. Using speed means every car has the
same limit, however heavy it is.

At `CRASH_SPEED` (15 m/s) the car is wrecked for `WRECK_TIME` (1.2 s). Its controls are
cut and the brake is held. `input.wrecked` stops that brake finding reverse and stops
the slide earning boost. Then the car goes back to the racing line where it hit, not
where it slid to, stationary and ghosted for 2.5 s, and the lap is spoiled. The slide
comes off `car.distance`. Without that, a wreck is quicker than braking, because a
strong car regains corner speed in moments.

Roughly, 15 m/s is a 20 degree hit at 70 m/s, a 30 degree hit at 40 m/s, or a head-on
at 45 km/h. In 20 races of six AI cars nobody reached it, while a bot holding full
throttle with no brakes loses to clean driving on every track. `tests/test_race.lua`
checks that on the four tracks where the fences used to be quickest.

Other cars never wreck you. For `SHUNT_GRACE` (0.4 s) after touching a car, a fence
can't either, so nobody can be punted into one. Cars past the flag don't crash, and
each game judges only its own cars. A ghost is sent in the sync packet's flags, or a
stopped car on the racing line would be solid on everyone else's screen.

### Standings and finishing

`rank` sorts finished cars by finish time, then everyone else by `distance`, with
anyone who quit an online race last.

When the player finishes, `finishGrace` starts at 25 s and the player's car goes to AI
control. The phase becomes `finished` when that runs out or every car has finished or
retired. Cars still running then show DID NOT FINISH.

`Race.new` takes `player2` (spec, colour, name) for a second driver at the same screen,
never online, with its own `assist` tier and `manualGearbox`. The AI's grip still goes
by P1's tier. `race.players` lists everyone driven from this machine, P1 first, and
`race.player` stays P1. Both are `isPlayer`. The first of them home starts the 25 s,
and one still out when it runs out gets `timedOut` and the AI. Knocked cones go back
only when neither can see them, and on the lot each resets to their own start spot.

An online race ends differently, so that every screen agrees: 25 s after the first
finish time anyone sends, on the shared clock, whether or not that was this player. A
player still racing then gets `timedOut`, the DID NOT FINISH heading and the AI.

The finish is shown in three stages. Each driver's view has a `finishClock` from their
own line, which drives their banner, and `session.finishClock` starts when the last
of them is home, which drives the results:

| Time after the line | What happens |
| --- | --- |
| 0 s | Sting plays (lower if not first). Chequered banner. HUD and touch controls go |
| 3 s (`hud.FINISH_HOLD`) | Results panel slides up with the race still running, times filling in. Engine noise fades |
| 3.3 s | Panel lands and its buttons appear. Before that, a press can't reach them |

## 10. The race session

`race_manager` (`rm`) owns everything belonging to one running race. The menu's live
background is the same machinery with `demo = true`: an AI-driven race with no HUD,
sound or vibration.

### `rm.start(opts)`

1. Stop any previous session.
2. Use the `Track` passed in, or build one. The menu passes the one its preview
   built, and the editor passes its own. Nothing changes a `Track` once it's built.
3. `Race.new`, which loads the Box2D world and spawns cars.
4. Build the scene with `track_renderer.load` (or `loadApron` for freestyle) and the
   minimap. The particle systems and the skid mesh are made for the first race and
   emptied for each one after.
5. Set each car's lights from the time of day, and generate sprites.
6. Make a view per driver at the screen (see below) and attach their drivers:
   `playerDriver`, a reader's driver for each of two, or an AI for the demo. Time trial
   loads its best lap and ghost.
7. Clear input, reset touch, snap the camera, tune the radio.

All of this runs in one blocking call.

| Track | JIT on | JIT off |
| --- | --- | --- |
| TEMPLE | 56 ms | 274 ms |
| ARDENNES | 75 ms | 326 ms |
| OASIS | 70 ms | 308 ms |

These were measured on this desktop, for a two-car race, when `rm.start` always built
the track, so they include a `Track.new`. A phone will be slower, and the Galaxy A04
hasn't been measured.

### Views

Everything that belongs to one driver lives in a view: their car, their hands, the
camera, toast, pace note, drift score, last gear and finish clock. One driver has one
view, whose hands are the merged keyboard, pad and touch. Two at a screen
(`session.split`) have one each, whose hands are `input.reader`s: one pad goes to P2
and the keyboard to P1, and with two pads P1 has the keyboard and the first. Two can't
start without a pad for the second.

`rm.setToast(text, ...)` shows on every view unless it's given one. Lap times,
starts, crashes and finishes go to their own driver's; the radio and cheat codes to
both. The camera and radio buttons are shared, and either driver can pause. Pulling out
either driver's pad pauses (`rm.usesPad`).

### `rm.update(dt)`

1. Return if paused, unless online. An online race can't stop for one player, so it
   runs on behind the menu with the car coasting: `playerDriver` ignores the keys,
   which are working the menu.
2. `handleControls` per view: horn, lights, camera, reset, next song.
3. Fixed-step loop: `race:step`, impacts, start-light beeps, launch toast.
4. Online: pull the race clock up to the shared one, send the car at most every
   1/20 s, and react to drivers leaving or the connection going.
5. `updateFinish`, then per view the freestyle drift counter, pace note and camera,
   then ghost recording, per-car effects, particles.
6. Radio announcement and toast timer.
7. Unless it's the demo, per view: audio mix (or fade-out behind results),
   vibration, shift sound.

### Camera

The camera eases towards a target at a rate of 4/s:

- **Zoom** comes from window size, the NEAR, MID or FAR setting and speed, tightening
  or falling back with acceleration, and pulling back 14% under boost.
- **Rotation** (chase camera) follows heading plus 55% of the slip angle.
- **Position** looks ahead of the car by a quarter of the screen height.
- **Shake** adds up crash trauma, kerb buzz, high-speed buffet and boost.

The FIXED camera stays north-up and leads by velocity instead.

With two at a screen each view has its own camera on its own half. Zoom comes from
the whole window's size, times 0.88 (`SPLIT_ZOOM`), so a half sees as far ahead as one
driver alone does, from a little further back.

### Ghost

Time trial samples x, y and angle 15 times a second into a flat array during each
lap. If the lap is clean and a record, `settings.submitLap` saves it. Open and clean
rules keep separate records, the open ones under a `/open` key, so a cut lap never
beats a clean one; old records are clean ones. Playback
interpolates between frames, drawn at 35% alpha. The ghost has no physics. A test
drive from the editor keeps its best lap in memory only.

### Pace notes

`updatePaceNote` scans ahead for the slowest point on a speed profile, within
`speed²/14 + 45` metres. If that's below 90% of current speed it shows a direction, a
grade (1 under 18 m/s, 2 under 28, 3 under 40, else 4) and whether to brake now.

## 11. Rendering

The look is flat toy-track colour with crisp edges, on purpose. Nothing is a photo
texture.

### Frame composition

```
 post.begin            bind the full-size scene canvas
   drawWorld           ground, skids, ghost, shadows, cars, particles,
                       lamps, start gantry
 post.drawLights       half-size lightmap: ambient plus floodlights or
                       pools, studs, beams, tail lights (only if env.lights)
 post.drawGlow         half-size emissive pass, blurred at quarter size
                       (skipped on low effects)
 post.present          composite shader to the screen
 hud.draw              straight to the screen, so it's never graded or lit
```

The composite shader runs in this order:

1. Speed blur, on the sides of the frame only. The centre column holds the car and the
   road ahead, which must never smear.
2. Multiply by the lightmap, at dusk and after dark.
3. Add glow. Only lamps, flames and sparks glow, so daylight whites never bloom.
4. Colour grade and saturation.
5. Vignette, deepened under boost.

Canvases are created lazily and rebuilt when the window size changes.

**Two at a screen** run all of that once per view, side by side, each half
`floor(width / 2)` wide so the canvases fit both and are never rebuilt between them.
`post.present` takes the half's x. Anything that culls to the screen reads the size of
the canvas being drawn into (`viewSize` in `track_renderer`), not the window's. Then
`hud.drawView` draws each half's HUD in its own space under a scissor, and
`hud.drawShared` the seam, the timing tower and the minimap over the middle.

On the desktop, under Xvfb's software GL, two views took the draw from 6.1 to 8.9 ms
on MIRAGE by day (`split-*` cases in `--perf`), with twice the draw calls. Phones don't
offer it.

**Low effects** skips glow and speed blur and halves particle emission. The lightmap
stays.

### World meshes

`track_renderer.load` bakes everything that doesn't move:

| Part | How it's built |
| --- | --- |
| Road | One mesh of 4 vertices per sample. Each carries its distance along the lap and its distance from each edge, so the shader paints lines, kerbs, dashes and the start chequers analytically and they stay sharp at any zoom |
| Ground | One quad with a shader: mown stripes, dunes or slabs by theme |
| Gravel | Strips with a polka-dot shader |
| Barriers | Coloured quads, plus an ink outline and a shadow copy |
| Trees, palms, shrubs | Sprite batches. Up to 3000 attempts, kept where clumping noise and the distance from the road allow |
| Containers, grandstand, grid boxes | Baked into rectangle meshes, because drawing them one at a time cost a slow phone more than the rest of the world together |
| Sponsor boards | One rectangle mesh for the panels and one `Text` object for all the lettering. See below |

Scenery uses an RNG seeded from the track's sample count, so a track looks the same
each time.

### Sponsor boards

Hoardings like an F1 circuit's: flat panels on the grass just outside the fence,
20 m long and 2.4 m deep, lettered so the bottom of the text faces the road. They're
only drawn and have no physics. `boards.place` walks each fence from the start line,
the left fence first, and lays a board along any chord a board long that the fence
stays within 0.4 m of. That means straights and gentle bends, never hairpins. The
board is pushed out by however far the fence bows towards it, so the gap stays the
same. A board must sit wholly behind the nearest fence, clear of other boards and of
the grandstand, and the next one comes 50 m on. That gives 19 to 56 boards a lap.
A 10 m gap, about twice as many boards, felt like too much on ARDENNES.
Trees and containers keep 6.5 m clear of every board.

Boards are numbered 1..N in that order, and the number is the board's address:
`sponsors.spots.mirage[3]` is MIRAGE's third board. A board that hasn't been sold
takes `sponsors.pool[(n + offset) % #pool + 1]`, where the offset comes from the
track's name. So each track starts somewhere else in the pool, and no sponsor is on
two boards in a row. The player's own tracks show only the pool. **Changing
`boards.LENGTH`, `DEPTH`, `GAP`, `SET`, `BOW` or the walk renumbers every board**,
so once a spot is sold they stay as they are.

A sponsor is up to 16 characters from A-Z, 0-9, space and `. - & ! '`, a `#rrggbb`
board colour, and an optional `#rrggbb` ink colour. Without ink, the text is black
or white, whichever reads better. `sponsors.check` validates an entry, and the tests
run it over every entry. `SPPPD_SPOTS=1` labels each board with its address instead
of its sponsor, and `love . --visual boards` with `SPPPD_TRACK` and `SPPPD_BOARD`
parks beside one board.

Freestyle's `loadApron` is a separate small scene: one huge quad and painted bays
drawn around wherever the camera is, with the playground from `sim/lot.lua` in the
middle. The playground is a donut pad around a tyre stack, a slalom of cones, an S
of wall to slide along and two blocks of containers for figure eights. The wall
and containers are baked meshes. The cones move, so they're drawn each frame,
only near the screen.

In physics, the wall, containers and tyre stack are barriers, so a hard hit
wrecks the car as a fence does. With no road to go back to, the car restarts
4 m out from where it hit, pointing along it. Cones are light Box2D bodies with
`{ prop = true }` as user data. `postSolve` keeps them out of fence hits, car
contact and dents, and reports them only as a knock and a puff of dust. A
knocked cone goes back to its spot once the player is 60 m away, and all of them
go back on RESPAWN. Freestyle on a circuit counts laps silently and never shows
WRONG WAY.

### Time of day

| TIME | Ambient | Floodlit | Headlights | Notes |
| --- | --- | --- | --- | --- |
| DAY | White | No | Off | No lightmap |
| DUSK | Warm | Yes | Low beam, 74 m | Menu demo uses this |
| NIGHT | Blue, 0.3 | Yes | Low beam, 74 m | Floodlight every 55 m |
| MIDNIGHT | Near black, 0.08 | No | High beam by default, 72 m (low 48 m) | Beams end on screen, so the road runs out into the dark. Road studs, amber left and white right, sit in the lightmap every 15 m. Only the start line has a lamp |

The lamps never move, so the first lit frame bakes them, floodlights or pools of
light, into one sprite batch, as the studs are.

Each of the three themes (meadow, desert, marina) sets ground and road colours, the
scenery type and barrier colours.

### Cars

`car_sprites.get(spec)` draws a car once into three canvases at 22 px per metre:

- **`paint`** is white, so one sprite can be tinted any colour.
- **`detail`** has glass, lamps, panel lines and body-style extras.
- **`shadow`** is a soft blob.

There are 12 body styles, each a half-outline that's mirrored and smoothed with
Chaikin corner cutting. OPEN WHEELER's `formula` style has its own drawing code,
because its wheels show.

`car_view.draw` adds wheels that turn with the steering, a pixel or two of body roll
and pitch, slipstream wisps and the boost warp. `car_view.updateFx` emits tyre smoke,
dust, skid marks and backfires per frame.

`rm.drawScene` works out each car's pose for the frame once. A car further from the
middle of a view than half its diagonal plus 20 m isn't drawn there (plus 125 m for
its beams in the lightmap), so the boost warp trailing behind a car still shows.

### Particles and skids

| System | Buffer | Used for |
| --- | --- | --- |
| Smoke | 700 | Tyres |
| Dirt | 500 | Loose ground |
| Sparks | 400 | Impacts |
| Pop | 60 | Backfires on upshift |

Skid marks are a ring buffer of 6000 quads in a single mesh, so thousands of marks
cost one draw call. It's a `dynamic` mesh, not `stream`: LÖVE 11 sends a stream
mesh's whole buffer (480 kB) whenever any of it changes, and a dynamic one only the
range that changed. Only the quads written this race are drawn.

## 12. Sound

No audio files ship with the game. Everything is synthesised once and cached.
`SOUND.md` is the style guide, with the levels a new sound has to meet, and the
measurements behind them.

### Three ways of making sound

| Kind | Sounds | How |
| --- | --- | --- |
| sfxr presets | beep, go, click, select, lap, scrape | The `SHOTS` table |
| Filtered noise | road, loose, wind, scrub, boost, turbo boost, grind | `bandNoise`, `grindData` |
| Physical models | Engines, startup, shift, blow-off, crashes, turbo, supercharger, motor, squeal, horn, finish | Written in `audio.lua` |

`bandNoise` is sfxr's filters on white noise without its eightfold oversampling. At
the scrub's and boost's settings that oversampling changed nothing measurable and took
over a fifth of the first launch. Its settings are the `ROAD`, `WIND`, `LOOSE`, `SCRUB`
and `BOOST_GAS` tables. Nothing steady keeps much energy over 2 kHz, because noise held up
there for seconds is static whatever it's meant to be. `wander` and `swell` move each
one over its loop, and that movement is what tells them apart.

### The engine model

A piston engine isn't a tone. `audio.engineData` runs a small model sample by sample:

```
 firing order  ──▶  gas bursts  ──▶  four exhaust resonators  ──▶  soft saturation  ──▶  shelf above 300 Hz
 (cylinders,        (noisy decay,     (92, 265, 710, 1900 Hz        (atan)
  per-pulse level)   not a click)      scaled by engine size,
                                       plus the bursts' noise as a rasp)
```

Up the revs the bursts run together, so fresh noise would be a steady hiss on top of
the note. The rasp always uses a grain of noise that repeats every engine cycle, and
the bursts use more of the same grain the higher the loop is rendered. Repeating noise
has the engine's pitch, so it counts as part of the note.

Each loop then sets its own level from what it has above 300 Hz (`LOOP_LEVEL`), with
`LOOP_PEAK` as a ceiling. That part reaches every speaker, so every car is as present
on a phone, and the bass goes on top for anything with a woofer. The saturation stays
before the shelf so the extra top end adds no fuzz. The tone is aimed at the startup's
flare: compare octave by octave at the same rpm before changing `presence` or `rasp`.

`audio.voice(cylinders, race)` derives the parameters. More cylinders means rougher,
against real physics, by choice. The V8 keeps its original hand-set firing table.
`raceExhaust` ignores all that for dead-even firing through short pipes, which is why
OPEN WHEELER's V6 differs from ROCKET's.

Each distinct voice renders **six loops**: three steady speeds, one throttle-closed
overrun, one rev limiter and one idle. Seven voices (4, 5, 6, 8, 12, 16 and race 6)
make 42 engine loops. Every loop is a whole number of engine cycles and crossfaded, so
it joins cleanly.

`crossfade` takes how much of a sound is unrelated noise. Noise adds by power, so a
straight fade dips by 3 dB halfway and the loop breathes. Engine cycles line up across
the join, so a fade by power would swell. The motor is half and half.

### The live mix

`audio.update` runs each frame for the player's car and the nearest rival:

| Layer | Follows |
| --- | --- |
| Exhaust speeds | Hands over between the two nearest loops by rpm, each pitched to match, so the note moves instead of being pitched up from one sample. Shares add by power, and the handover is narrow (`BLEND_WIDTH`) |
| Idle | Takes over from the speeds with the throttle shut, near idle |
| Overrun | Opens as the throttle closes |
| Limiter | Only when `model.limiting` is set |
| Turbo | Pressure lags the throttle (`spoolStep`). Whistle pitch follows pressure |
| Blow-off | One shot when power comes off with pressure over 0.55, which includes every upshift. Race engines skip it |
| Supercharger | Follows revs at once |
| Motor | CYBER only, a rough whine with a narrowed pitch sweep |
| Scrub, road, loose, wind | Slip, speed, surface and slipstream. Speed mostly raises their level and how fast their texture goes, and barely their brightness |
| Squeal | A note, not noise: detuned sawtooths, over the scrub once a tyre is well past its limit |
| Grind | `car.scraping` and speed |
| Boost | Sounds like what feeds the engine, through `audio.boost`, which swells in, sighs out over about 0.3 s, and sags as the tank empties. An NA car plays the gas. A supercharger or motor gets louder and climbs. A turbo car has its loop driven to full pressure, plus `turboboost<n>` above the exhaust, the exhaust ducked 18% and a blow-off when the bottle shuts off, except on a race engine |
| Horn | Pitch from car mass, so heavy cars are lower |
| Rival | One engine loop, motor or horn, within about 42 m |

Sound isn't positional. The rival only changes volume with distance. Only one car's
engine loops play, so the number of voices costs memory but nothing per frame.

**Two at a screen** each have a channel: every loop above but the rival's. The first
channel is the `audio` module itself, so one driver alone sounds exactly as before.
`audio.split(true)` clones a second the first time (clones share their samples), puts
each channel's mono sources 30 degrees to its own side and takes both down to 80%.
`audio.update`, `audio.impact` and the engine duck take the driver's seat. Nobody
hears a rival, because the other driver's engine is already there.

Downshifts are silent, because a hard stop would rattle through every gear.

### Crashes

`race_manager` takes the hardest contact of each physics step, so one crash is one
sound. Strength is `impulse / 9000`, and runs from about 0.2 to 27, so `impactLevel`
works on its logarithm: a graze under 0.15, then three sizes of `crashData` from 0.15,
0.6 and 3, each with its own volume range. Inside `IMPACT_GAP` only a bigger hit gets
through. The two larger sizes pull the engine down briefly (`duck`). Pitch follows mass
(`impactPitch`), and each hit varies by 6%.

### Cache

`sound_cache.lua` stores each render as a WAV under `soundcache/<md5>/`. The hash
covers `src/audio.lua` and `src/lib/sfxr.lua`, so changing either re-renders
everything and clears older folders. A `complete` file is written last, so an
interrupted first launch doesn't count. Any cache failure only costs time: the sound
is rendered as normal.

On a first launch the cores share the work. `audio.jobs()` lists every cached sound
by name, engine loops first as they're slowest. `audio.prerender` puts the names on a
channel and starts one `sound_worker.lua` thread per core but one, up to 6. Each takes
names until the channel is empty and writes the WAVs into the cache folder, while the
loading coroutine yields so the splash keeps drawing. `audio.load` then reads them
like any cached sound, and renders anything a failed thread left out. `cache.get`
trusts a WAV in a folder that isn't `complete`, because `cache.open` empties such a
folder first, so only this launch's threads can have written it. Every render is
seeded, so a thread makes the same sound the main thread would, apart from sfxr's
noise, which was never seeded (the scrape).

On the Galaxy A04 a full render took about 14.5 s and a cached launch 2.3 s
(2026-11-01). That was before the crashes, squeal, grind and idle loops were added.
On 2026-11-09, wall time from start to sounds ready: 18.1 s on one thread, 5.1 s on
the A04's threads, 1.6 s from the cache.
With the JIT off on the desktop the render is about 14% longer now, because moving the
scrub and boost off sfxr paid for most of them.

If `audio.load` fails, the game carries on silently and `audio.ready` stays false.

### Radio

`radio.lua` streams the player's own files from the `music` folder, in freestyle only.
MP3, OGG, FLAC and WAV are supported, shuffled so a new order never opens on the last
song. A file that won't open is skipped. Dropped files are copied in. Filenames become
titles, with non-ASCII replaced, because printing invalid UTF-8 raises an error.
`rm.start` is the only place that tunes it, and `rm.stop` leaves it alone so a restart
doesn't cut the song. Phones don't have the radio, because their save folder can't be
reached.

## 13. Input, touch and vibration

### Input

`input.lua` merges keyboard and pad into named actions, with two ways to read them:

- `input.isDown(action)` for anything held.
- `input.consume(action)` is true once per press. A tap shorter than one frame still
  registers.

`input.applyTo(car.input, manual)` fills the car's input table each step.

For two at a screen, `input.reader(keyboard, pad)` reads one driver's hands only:
the keyboard, one pad or both, with its own presses (`keyPressed`, `padHeld`,
`padPressed`) beside the merged ones. `input.gamepads()` lists pads oldest first, and
`input.splitReaders()` deals them out. Steering
sets `keyboard = true` unless an analogue axis is active, which picks the wind-on
filter in `dynamics`. The stick has a deadzone of 0.08 and a curved response.

These are the defaults:

| Action | Keys | Pad |
| --- | --- | --- |
| Steer | A D, arrows | Left stick |
| Gas, brake | W S, arrows | RT, LT (analogue) |
| Handbrake | Shift | RB / R1 |
| Boost | Space | LB / L1 |
| Shift up, down | E, Q | X, A (Square, Cross) |
| Reset | R | Y / Triangle |
| Camera | C | Back / Share |
| Next song | N | D-pad right |
| Horn | H | B / Circle |
| Lights | F, G | None |
| Pause | Esc, P | Start / Options |

The pad layout borrows R1 handbrake and L1 boost from Need for Speed: Most Wanted on
PS2, with the triggers kept for analogue control. The keyboard is deliberately left as
it always was.

#### Changing keys and buttons

Players change them on CONTROLS > KEYBOARD and CONTROLS > PAD. Each action has one
key of the player's (`input.DEFAULT_KEYS`) and maybe one fixed key
(`input.FIXED_KEYS`: the arrows, right Shift and Esc), which can't be taken, so
nobody can lose the way to drive or pause. On the pad, the stick and triggers are
fixed, and each action in `input.PAD_ACTIONS` has at most one button
(`input.DEFAULT_BUTTONS`). Gas and brake have none by default; a button set there is
full on beside the trigger. The guide button is never offered.

`input.rebindKey` and `input.rebindButton` swap: the action that had the key takes
the changed action's old one, so no action is left without a key. A pad action can
be left without a button that way, except pause, which always keeps one.
`input.setBindings(keys, buttons)` takes what was saved, only the changes from the
defaults (`false` for a pad action with none), and puts a device back to its
defaults if anything clashes or isn't a real button. `settings.keys` and
`settings.padButtons` hold those changes, and `main.lua` applies them at start.

The pad's choices apply to every pad, so both drivers at a split screen get them.
The keyboard is only ever P1's.

While a row waits, `menu.takeKey` and `menu.takeButton` get the press before
anything else, so it doesn't also move the menu or type a cheat code
(`menu.textTaken`). Esc, a click, a tap or six seconds lets go. A keyboard row lets
go on any pad button. A pad row ignores keys other than Esc, and needs a pad plugged
in. The screens name a pad's buttons by its family (`menu.padFamily`: PlayStation by
name, anything else Xbox), or both without one.

### Touch

`touch.lua` layers over `input`. A touch on the left half places a stick under the
thumb, and the base follows a thumb dragged past the edge, so turning back acts at
once. Each axis is independent, so full lock costs no brake.

The on-screen buttons press keys of their own (`touch:<action>`) through
`input.press`, so a touch is just another pair of hands, whatever keys the player has
set. Their hit radius is 25% larger than drawn, and
the nearest button wins. Each look of a button (its colour, held or not, size and
opacity) is drawn once into a canvas and kept, because redrawing the circles each
frame cost the A04 more than the rest of the HUD.

With AUTO GAS on, the car accelerates by itself and the stick only brakes. Stick up
revs at the lights, past a deadzone of 0.3. Touch always forces the automatic gearbox,
because there are no shift buttons.

TOUCH STEERING (`settings.touchSteer`) swaps the stick for buttons. The left and right
arrows press the steering actions as keys do, so they wind on through the same filter
as the arrow keys. A thumb anywhere on the left half steers towards its side of the
line between the arrows, and can rock across without lifting. BRAKE sits above DRIFT,
out of the dash's row, which is too narrow on 16:9 phones. Without AUTO GAS, GAS takes
the corner and BOOST moves beside BRAKE. An action held by two fingers is let go only
when the last one lifts. `layout.buttons[1..5]` keep their order in both layouts
(boost, drift, pause, reset, horn), because `tests/flow.lua` picks them by index.

STEERING FEEL (`settings.touchFeel`, `touch.FEEL`) sets how sharply touch steers. On
the stick it's the bend of `input.curve`: 1.0, 0.6 or 0.25 for LOW, MEDIUM and HIGH,
where MEDIUM is the pad's. On the arrows it scales how fast the wheel winds on: 0.75,
1 or 1.35, passed to `dynamics` as `input.steerRate`. Keys and pads keep their own.

`touch.shown()` is true when the setting is `on`, or when it's `auto` and a touch has
been seen. A key press or pad button in a race hands back.

### Vibration

`rumble.lua` reads what the car is doing, never the input.

- **Pad:** heavy motor for crashes, boost and grass. Light motor for gears, boost,
  kerbs and slip. Messages go at most 30 times a second, each lasting 0.2 s, so a
  stall can't leave the motors running.
- **Phone:** one crude buzzer, so only crashes and boost lighting, with a 0.15 s
  minimum gap.

Each driver has a seat with its own motors and timers. `rumble.assign(seat, pad)` gives
it a pad, `false` for none, or nil for the first seat to follow the last pad used, as
one driver alone does.

## 15. Track editor and catalogue

### Model and view

`editor_model.lua` is the document, with no drawing, so it's tested directly.
`editor.lua` is the screen.

A document holds name, title, theme, scale, nodes, start point, and undo and redo
stacks. `model.checkpoint` snapshots nodes and start before a change, up to 100 steps,
and dragging calls it once on mouse down. Every width is held between 18 and 140 file
units, and a track keeps at least 4 nodes.

After an edit, `changed()` starts a 0.12 s timer, then `model.build` runs `Track.new`
inside `pcall`, and `validate` supplies the warnings. A layout that can't build is
reported and never throws. The editor draws the real kerbs, barriers and racing line
from that built track.

`T` starts a time trial on the built track without saving. It passes the `Track`
directly, and the document survives the trip, so the player comes back to their work.

Built-in tracks can be opened, and boundary tracks convert through `Track:toNodes`.
Saving a built-in makes a `_edit` copy and never replaces it.

### Catalogue

`catalog.lua` returns built-ins in a fixed order, then anything in the save folder's
`tracks/`, sorted by name. The saved list is read once and kept until a save, a
removal or the game regaining focus, because the menus ask for it every frame. User
tracks are Lua files loaded with `setfenv(chunk, {})`, so they can't reach anything.

## 16. Online play

Online is two to four players through a dumb UDP relay. The relay seats them in a room
and then forwards packets. It understands nothing about the race.

### Trust and authority

Each client is the only authority over its own car and simulates nothing for the
others:

- It sends its pose, progress and finish time at 20 Hz through the relay.
- Another driver's car (`car.remote = true`) has no tyre model running and is positioned
  by `RemoteDriver`.
- Each client counts its own laps. Nobody works out anyone else's.

There's no shared simulation and no referee. A client could lie about its finish time,
which is fine between friends and is why ranked play needs more (see `ROADMAP.md`).

`menu.ONLINE_NOTES` tells players this on the ONLINE screen, along with the other limits
they can run into: no way back after about 30 s away, late cars on a slow connection, and that
the server sees their IP address. Other drivers don't, because everything goes through
the relay. Keep those notes true when any of this changes. The pause menu's title says
RACE STILL RUNNING online, since nothing stops.

### Seats and the leader

The relay gives each client a seat, 1 to 4. Seat 1 is the host. The **leader** is
whoever is in the lowest seat, and it's the one with a job to do: it publishes the race,
hands out the track, answers clock pings and calls each start. If the host leaves a
race, the next seat becomes the leader and everything carries on, because everyone
already holds what's needed to race again. A lobby is different: the race is the host's
to set, so the relay closes the room if the host leaves before the first start. A quick
match's lobby isn't: its race is the relay's, so the next seat leads (see Quick match).

Grid order is seat order with the gaps closed. Other drivers show by their driver
name (see Drivers), or as P1 to P4 if they have none.

### Nothing waits for an answer

There are no acknowledgements. Every client repeats its state four times a second, and
the relay repeats each room's state once a second, so a lost packet costs a moment
rather than a retry and there's only one path through the code. `make test-online` runs
a track transfer with 15% of packets dropped in each direction.

### Packets

All packets are `|`-separated text, at most 2048 bytes. The relay stamps whatever it
forwards with the sender's seat, as `2|sync|...`, so a client can't pose as another.

| Packet | Direction | Purpose |
| --- | --- | --- |
| `event\|host\|5\|CODE\|cookie\|\|features\|account\|proof\|padding` | Client to relay | Create a room. Repeated until answered. Padded to 64 bytes. `account` and `proof` sign the seat in as a driver, and are empty without one |
| `event\|join\|5\|CODE\|cookie\|\|features\|account\|proof\|padding` | Client to relay | Join a room. The same |
| `event\|back\|5\|CODE\|cookie\|token\|features\|account\|proof\|padding` | Client to relay | Take my own seat back, from whatever address I have now |
| `event\|queue\|5\|\|cookie\|\|features\|account\|proof\|mode\|data\|padding` | Client to relay | Find me a race. `mode` is `quick`. `data` is empty, kept for ranked |
| `event\|kick\|seat\|` | Client to relay | My vote to remove the driver in `seat` from a quick match |
| `event\|lock\|` | Client to relay | The race has started, so take nobody new |
| `event\|leave\|` | Client to relay | Leaving |
| `event\|cookie\|cookie` | Relay to client | Ask again with this. The answer to a request without a good cookie |
| `event\|room\|seat\|CODE\|seats\|locked\|token\|away\|names` | Relay to client | Your seat, who's here, your token, which seats are away, and `seat:NAME,…` for seats signed in as drivers (3.2 relays on). On any change, and every second |
| `event\|match\|kind\|track\|laps\|time\|startIn\|online\|votes` | Relay to client | After each `room` in a quick match: the relay's race, whole seconds until it stops filling (`-1` while alone), drivers on the relay, and `seat:count,…` votes |
| `event\|error\|reason` | Relay to client | Refused entry, or refused a seat back |
| `event\|closed\|reason` | Relay to client | Removed: a closed room, a ban, a restart |
| `hello\|car\|paint\|have\|ready\|vote\|features\|handling\|gearbox` | Everyone | Who I am, whether I hold the track, the round I'm ready for, the round I've asked for, my `FEATURES`, and the handling and gearbox I drive with (3.0 stops after `features`) |
| `setup\|round\|hash\|chunks\|laps\|time\|startAt\|title\|needs` | Leader | The race, when it starts, and the `FEATURES` it needs |
| `ping\|t`, `pong\|seat\|t\|leaderTime` | Clients and leader | Finding the leader's clock |
| `need\|hash\|1,2,3`, `chunk\|hash\|n\|text` | Clients and leader | Fetching a track |
| `sync\|round\|seq\|x\|y\|a\|vx\|vy\|steer\|rpm\|throttle\|brake\|gear\|flags\|slide\|distance\|finish` | Everyone | Car state, about 100 bytes, 20 Hz |

`paint` is an index into `PAINTS` in `menu.lua`, so that list's order is part of the
protocol. `flags` holds the horn, reverse, boost, the two beams and whether the car is a ghost.

### Versions and compatibility

`network.PROTOCOL` goes in `host`, `join` and `back`. The relay keeps the host's number
with the room and refuses a joiner with a different one, with a message saying so.
Otherwise it only reads it to tell protocol 5 and later, which earn their seats with a
cookie, from older games, which don't. A client from before protocol 2 sends no number
and is told to update, and `-min-proto` tells older ones the same.

All of 3.x is protocol 5, and stays that way. 3.x releases add to the protocol without
changing `PROTOCOL`, by these rules:

- **Fields only go on the end of a packet.** A field's meaning never changes, and
  none is ever taken away. `chunk` is the exception: its text runs to the end, so it
  can't take more fields.
- **Readers take the fields they know and ignore the rest.** `head(str, n)` gives the
  first `n` fields for an anchored pattern, so a packet with more still matches. A
  packet missing a field the reader needs is refused.
- **Unknown packets and events are ignored**, by games and by the relay.
- **Behaviour older 3.x games can't follow is gated by `network.FEATURES`.** A
  release that adds such a thing raises it by one. Each `hello` carries it, so
  `network.roomFeatures()` is the most everyone in the room can do, and the host offers
  only what that allows. A race that needs more sets `needs` in its setup: the host
  can't start it until every driver's `FEATURES` reaches it, and an older game that
  hears it fails with "The host's race needs a newer version of the game".

A field made only of `.` is an older game's padding, and the relay reads it as empty.
So a 3.0 game's `host` reads as `features` 0.

| `FEATURES` | Adds |
| --- | --- |
| 0 | 3.0 |
| 1 | Quick match, and each driver's own handling and gearbox online |

**Change `PROTOCOL` only for a break those rules can't cover**, which is a new major
version.

During a race the connection going doesn't stop anything. `network.lost` holds why, the
others are marked as gone, and the player can finish alone.

### Starting together

Everyone counts down on the leader's clock. Each client pings the leader and keeps the
last eight answers: `offset = leaderTime + rtt / 2 - now`. It uses the one with the
quickest ping, because that's the one least held up on the way. Clients need three
answers before they count as ready.

The grid holds with the lights dark, saying WAITING FOR THE OTHER DRIVERS, until every
client reports the round built. The leader then sets `startAt` to 1 s plus the lights
from now, and each client converts that to its own clock once and keeps it, so a late
packet costs nothing. `Race` takes `startIn`, the seconds left, and sets its timer from
it each step, so a client that loaded late joins part way through the lights instead of
starting late. The leader gives up on a client after 20 s.

`network.startIn()` keeps counting below zero once the race is on, which makes it the
race clock too. `Race:syncClock` pulls `race.time` up to it once a frame. A phone below
15 fps runs its simulation slowly, and without this it would also get a flattering
time. It never runs back, so lap times stay whole. Measured through a real relay with
one client's clock 1234.5 s out, the two starts agreed to within 30 ms on loopback. On
a real link the error is half the difference between the two directions' delay.

### Results

Every client sends its own `distance` and `finish` in each sync, so these need no
special delivery. `RemoteDriver` copies them onto the car, and `updateProgress` stops
early for a remote car, so nothing estimates another car's laps from a smoothed
position. Finish times are all on the shared clock, so sorting them gives the same order
on every screen, down to seat number on a dead heat.

The banner at the line can say YOU WIN for the fraction of a second before a closer
rival's time arrives. The results panel, 3 s later, is right.

### Remote cars

`RemoteDriver:update` runs every fixed step:

1. Take the latest state and its age in seconds. Past 0.25 s the driver has stopped
   sending, so treat their speed as zero.
2. Extrapolate: `target = position + velocity × age`.
3. Move the body a fraction of the way there, `1 - exp(-dt × 12)`, or all of the way
   if it's over 25 m out.
4. Copy steering, rpm, pedals, gear, reverse, boost, tyre slide, horn and headlights
   into the car, then progress and finish.

The remote car is still a real Box2D body, so the local car bounces off it. Its
velocity and pose are overwritten each step, so collisions only push the local car.
`slipstream.wake` reads its velocity, so each player can draw a tow from the others.

`seq` numbers each sync, so a late packet can't move a car backwards. `round` numbers
each race, so a straggler from the last one can't appear in a rematch.

### Sharing tracks

Tracks are matched by shape. `catalog.fingerprint` hashes the text form of a track, so
two tracks are the same exactly when their hashes match, whatever they're called, and a
saved track of the same name but a different shape is simply a different track.

A joiner who has the hash uses their own copy. Otherwise they fetch it: every 0.25 s
they name up to eight chunks they're missing, and the leader sends those, 1000 bytes
each, which stays under a typical path's MTU. The whole text is checked against the
hash. Anyone else who needs the same chunks takes them as they pass.

Track files are Lua, which is fine for a player's own but can't be run from a stranger:
`setfenv` doesn't stop a loop that never ends, and LuaJIT loads bytecode. So `wire.lua`
sends plain text, and `wire.decode` refuses anything outside its limits before it can
reach `Track.new`:

| Limit | Value |
| --- | --- |
| Text | 64 kB |
| Nodes | 4 to 1500 |
| Points in all, and in one Bézier curve | 3000, and 64, because a curve's cost grows with the square |
| Coordinates | Within ±100000 |
| Widths, scale, runoff | 1 to 400, 1 to 8, 2 to 30 |
| Lap length | 20 km |
| Title | 24 printable ASCII characters. The font has no more, and invalid UTF-8 raises an error |

`Track.new` still runs inside `pcall`. A shared track stays in memory and isn't saved,
and an online race doesn't touch the player's saved track, laps or time.

The same care applies to everything from another player: `unpackState` refuses
infinities, NaN and absurd positions, and clamps pedals and gears. An unknown car falls
back to the first one.

### Rematch

REMATCH on the results sets `vote` to the next round. When everyone still in the room
has asked, the leader starts it, using the same room, track and cars. Each client tears
down the old race and builds the new one, and the start works as it did the first time.
It needs at least one other driver left.

### Getting back in

A phone that changes networks gets a new address, and one that goes to the background
stops sending. Both used to cost the race. Now:

1. Each seat has a **token**, 16 random bytes that the relay tells only that seat's
   game, in its `room` events.
2. A game that hears nothing for 2.5 s in a room starts **getting back in**: it drops
   its socket without sending `leave`, opens a new one to the relay's address, and
   sends `back` with its token. It opens a fresh socket every 2 s while it tries, in
   case the network changed again, and it uses the address it resolved when it first
   connected, so it never waits on a name lookup. The race goes on meanwhile, and a
   toast says CONNECTION LOST, then BACK ONLINE.
3. The relay marks a driver in a shared room **away** after 5 s of silence. Their seat
   stays theirs, but nothing is forwarded to them. The others see their car as a
   ghost, because `RemoteDriver` ghosts any car silent for over 1 s, and a toast says
   they lost their connection.
4. A `back` with the right token takes the seat at the new address, and the room goes
   on as before: same seat, same leader, same round. A packet from the old address
   also ends being away, with no token needed.
5. After 30 more seconds (`-away-timeout`) the seat is gone, and the others see the
   driver leave. A `back` after that gets "Your place in that room has gone", and the
   game finishes the race alone. It gives up by itself after 35 s.

A host who is away from a lobby holds it open for those 35 s rather than closing it,
and the host can't start a race while anyone is away. Games before protocol 5 have no
token, so the relay drops them after 5 s, as before.

### Leaving

- `event|leave|` makes the relay send everyone the new room at once. Silence does too,
  after 5 s for games before protocol 5, and after 35 s for later ones, which are
  away in between.
- A driver who'd already finished only went home, so their car goes to AI and no toast
  shows.
- A driver who quit mid-race takes their car off the road, or it would sit there as a
  wall. They stay in the standings as LEFT THE RACE, behind everyone else.
- A closed room arrives as `event|closed|` with its reason, and the toast says that,
  not that someone left. So does a relay restart for games before protocol 5. Later
  ones aren't told: the relay keeps their rooms through it (see The temporary store),
  and they get back in as after any lost connection.
- 6 s of hearing nothing at all means a game before protocol 5 has lost the relay.
  Later ones try to get back in first.

### Quick match

QUICK MATCH on the ONLINE screen sends `queue` instead of `host` or `join`, with no
code. `server/match.go` seats the driver in the oldest room still filling that has a
free seat, the same protocol, nobody this address is kept apart from, and nobody gone
quiet for over 2 s; otherwise it makes a room with an 8-character code (the game's are
6, so they never clash) and picks its race: a built-in track, skipping the last two
picked, laps for about three minutes from the AI's ARCADE lap times, and a random time
of day. `join` with that code is refused: sharing it lets nobody in.

The second driver starts a 15 s countdown (`-quick-fill`; the online tests use 2 s),
which a full grid of four cuts to 3 s, and `match` carries it. The leader builds the
setup from the match, on its own copy of the built-in track, so nobody downloads
anything, and when the countdown runs out calls `startRace` itself once `canStart` holds.
Every game ignores a setup whose hash isn't the match track's, so a leader can't swap
it. The leader repeats `lock` until the room event shows it, because past its fill time
a room leaves the filling list, and one still unlocked a minute later is closed with
"The race didn't start". A game hearing that before its first race queues again by
itself. Dropping back to one driver before the start stops the countdown, and the room
fills again.

REMATCH works as in any room. FIND ANOTHER on the results leaves and queues again with
the same car and setup.

**Voting out.** In a quick match of three or more, VOTE OUT in the pause menu lists the
others, and `kick` is repeated for up to 3 s until the count in `match` goes up. Every
game, the target's too, shows `P3 MAY BE VOTED OUT (1/2)`. Two votes remove the target
with `event|closed|The other drivers voted you out`; in a room of two there's no vote,
because one driver could remove the other. The target's IP then can't queue for
2 minutes, doubled for each vote-out that UTC day up to an hour, and each voter's IP is
kept apart from it in matching for 30 minutes, unless they share an IP, which would bar
that address from every room with itself in it. Neither map outlasts a restart, and both
are capped at 65536 entries, evicting at random.

### The relay

`server/main.go` holds this state behind one mutex:

| Field | Meaning |
| --- | --- |
| `clients` | Everyone, keyed by `ip:port`, with their seat's token and whether they're away |
| `rooms` | Rooms by code, with their seats. A code is taken until the room empties |
| `banned` | IPs ignored until restart |
| `perIP` | Connections from each IP |
| `buckets` | Rate limit state for each IP |
| `events` | Last 200 lines for the dashboard |
| `filling` | Quick match rooms still taking drivers, by kind, oldest first |
| `cooldown`, `avoid` | IPs voted out, and pairs of IPs kept apart after a vote |
| `total`, `perSecond`, `dropped` | Traffic counters |

**`Handle(data, addr)`** runs for every packet:

```
 count it
 banned?               ignore
 too big, over rate?   drop and count
 refresh LastSeen, and if it was away, it's back: tell the room
 not an event?         stamp with the seat and forward to the rest of the room,
                       except anyone away
 unknown client?       register if it's host, join, back or queue, otherwise ignore
 event|leave           remove the client and tell the room
 event|lock            lock the room
 event|kick            count a vote in a quick match
 event|host/join/back/queue  resend the room (the answer may have been lost)
```

**`register`** checks a request from an unknown address. From protocol 5:

```
 under 64 bytes?       ignore: an answer mustn't be bigger than the request
 no good cookie?       answer event|cookie|… and nothing more
 older than -min-proto, bad code, too many from this IP?   refuse
 back                  give the seat whose token matches its new address, or refuse
 host or join          as before, with a new token for the seat
 queue                 unknown mode, FEATURES under 1, cooling down?   refuse
                       otherwise seat it in a quick match (see Quick match)
```

The cookie is HMAC-SHA-256 of the address and port and the current 30 s window, cut
to 16 bytes, with a key made at startup. It works for one to two windows. It costs the
relay no memory, and only someone who receives packets at that address can repeat it,
so a forged source can't take a seat, and gets one answer no bigger than what it sent.
Games before protocol 5 skip all of it and register as they always did.

Forwarding doesn't parse anything, which keeps the relay independent of the game
protocol. `event|` packets are never forwarded, so a client can't fake one from the
relay. `refuse` stays out of the log, because anyone can send those as fast as they
like. It counts them, and the sweep writes one dashboard line a second that sums them
up, so a flood can't push everything else off the activity list.

**`Sweep`** runs once a second: it computes traffic rates, marks clients in a shared
room away after 5 s of silence and drops them 30 s later (games before protocol 5 go at
5 s), drops anyone alone in a room after 60 s, repeats each room to the clients heard
from in the last 2 s, takes quick matches past their fill time off the filling list and
closes those a minute past it, sums up the refusals, and clears old rate buckets,
cooldowns and pairs kept apart. A game sends at
least four times a second, so only an address that has stopped sending, or never
was, misses the repeat.

Concurrency is simple: one goroutine reads the socket, one sweeps, HTTP handlers run
on their own, and all of them hold `mu`. `Sender` is a function, so tests run the
whole relay with no socket.

### Abuse protection

The relay is public, so it limits what any one address can cost:

| Limit | Value | When reached |
| --- | --- | --- |
| Packets from one IP | 300 a second, burst of 600 (`-rate`) | Dropped and counted on the dashboard |
| Packet size | 2048 bytes | Dropped and counted |
| Connections from one IP | 16 | Refused |
| Players on the relay | 2000 (`-max-players`) | Refused |
| Rooms open, waiting or racing | No limit by default (`-max-rooms`) | Hosting is refused; joining an open room still works |
| Rate buckets | 65536, cleared after 10 s idle | A random entry is forgotten to make room, so forged sources can neither grow memory nor shut newcomers out |
| Room codes | 1 to 16 letters and numbers | Refused |
| Seats, from protocol 5 | Only for a request that repeats the cookie sent to its address | Forged sources can't hold seats at all |
| Game versions | `-min-proto`, 2 by default | Older games are told to update. Set it to 5 once games before 3.0 are gone, and every seat needs a cookie |

Four players on one connection use about 130 packets a second. Room codes from the game
are 6 characters from 32, so about a billion, and the rate limit puts guessing one out
of reach. The longest refusal is about five times the size of what prompted it, but a
forged source gets the same rate limit, which caps that at under 20 kB/s. A forged
`host` gets one answer, not one a second, because the sweep only repeats rooms to
addresses still sending. So the relay isn't worth abusing as a reflector.

### Drivers

`server/drivers.go` and `src/account.lua`. A driver is a name, with no email and no
password. Picking one on PROFILE makes two random 16-byte keys: a device key and a
recovery key. Both go to the relay once, in the sign-up, and the game keeps them in
`account.lua` in the save folder, one driver per server address. After that it
proves it holds a key without sending it:

```
proof = base64url(HMAC-SHA-256(key, intent .. "|" .. cookie))[1..22]
```

The cookie is the relay's: bound to the address and a 30 s window, and only that
address sees it, so a proof can't be replayed from elsewhere or later. `host`, `join`,
`back` and `queue` carry `account` and `proof`, and a good proof puts the driver's
name on the seat. A missing or wrong one only leaves the seat unnamed, and a banned
driver is refused. The Go and Lua tests share one test vector, so the two HMACs can't
drift apart. Random keys come from `/dev/urandom` where there is one (Linux,
Android), and elsewhere from clocks, table addresses and timing jitter stirred
through SHA-256.

The recovery code is the driver's number and the recovery key in base32,
`1042-K7Q2M-…`. COPY RECOVERY CODE puts it on the clipboard, and I HAVE A RECOVERY
CODE starts filled in when the clipboard holds one that reads. Typed or pasted into
PROFILE on another device, it signs that device in with a device key of its own; the proof covers the new key, so it can't add a different one.
Ten devices at most: past that, the one used least recently is dropped.

| Packet | Direction | Purpose |
| --- | --- | --- |
| `event\|signup\|5\|cookie\|NAME\|key\|recovery\|label\|padding` | Client to relay | Make a driver. `label` is `love.system.getOS()`. Asked again with the same name and keys, it answers again |
| `event\|recover\|5\|cookie\|id\|key\|label\|proof\|padding` | Client to relay | Add this device. The proof is made with the recovery key over `recover\|cookie\|key` |
| `event\|profile\|5\|cookie\|id\|proof\|padding` | Client to relay | My name, since when, and how many devices |
| `event\|rename\|5\|cookie\|id\|proof\|NAME\|padding` | Client to relay | A new name, once every 30 days |
| `event\|signout\|5\|cookie\|id\|proof\|padding` | Client to relay | Remove this device's key |
| `event\|forget\|5\|cookie\|id\|proof\|padding` | Client to relay | Delete the driver |
| `event\|driver\|id\|NAME` | Relay to client | You're driver `id` (sign-up, recover, rename) |
| `event\|profile\|NAME\|since\|devices\|id` | Relay to client | The answer to `profile` |
| `event\|signedout\|id`, `event\|nodriver\|id` | Relay to client | This device isn't signed in to `id`, or there's no such driver. The game forgets it |
| `event\|denied\|intent\|reason` | Relay to client | Turned down: a taken or refused name, a rename too soon, too many tries |

Requests go from their own socket, so a refusal can't end a race, and are repeated
four times a second until answered, like everything else.

Names are 3 to 12 of `A–Z 0–9 - _`, in capitals, unique. The relay refuses a short
reserved list, `DRIVER` and a number (what the dashboard renames someone to), and the
words in `blocked_names.txt` anywhere in the name once look-alikes are folded. The game
checks only the shape.

The relay holds every driver and key in memory (`accounts`, `names`), so checking a
proof never touches the disk. Changes are made in memory under the lock and handed to
one writer goroutine on a buffered channel (`driverWrites`, 256). When it's full, the
request is dropped unanswered and the game asks again. Numbers start at 1001 and are
never given twice, deleted or not (`AUTOINCREMENT`). Sign-ups are limited to 3 an hour
from one address; recovery tries to 10 an hour from an address and 10 for a driver.

The dashboard's Drivers section finds a driver by name or number, shows each device's
label and days, and can reset a name to `DRIVER` and the number, ban or unban.

### The store

`store.go` keeps what has to outlive a restart in one SQLite file (`-db`, default
`spppd-relay.db`; empty keeps it in memory). The driver is `modernc.org/sqlite`, pure
Go, so the static `CGO_ENABLED=0` build still works. There's one connection, in WAL
mode, with temporary data in memory, because the container's root is read-only.

| Table | Holds |
| --- | --- |
| `bans` | IP, when, and which dashboard user |
| `users` | Name, bcrypt hash, when added |
| `sessions` | SHA-256 of each login token, its user, expiry (7 days) |
| `meta` | Nothing now. Older relays kept the analytics key here; it's moved out on start and the row is wiped with `secure_delete` |
| `daily` | One row of totals per UTC day, `backs` included since the relay that added getting back in, `quick_races` since quick match, and `signups` since drivers. `migrate` adds the columns to an older database |
| `visitors` | Day and keyed IP hash, deleted after `-analytics-days` |
| `races` | Start, end, drivers, protocol and `kind` (`quick` or empty) of each room that raced |
| `drivers` | Number, name, recovery key, made, last day seen, last rename, banned |
| `driver_keys` | Each device's key, label ("Android") and the days it was added and last seen |

The analytics key is in a file of its own next to the database, `relay.db.key`
(mode 0600), so a backup of the database can't be used to undo the IP hashes.
Losing it costs nothing that matters: a new key is made, and visitors are counted
per day.

Nothing touches the disk while the relay holds `mu`. `Ban` changes the map under the
lock and saves after it; `AttachStore` loads the bans at startup.

### The temporary store

`server/temp.go`. The rooms and the dashboard's recent activity outlast a restart in a
second SQLite file, `-temp-db` (`relay-temp.db` on the official server; empty for
none). It's apart from `relay.db` because it holds addresses and seat tokens that
aren't worth backing up, and the backup only copies `relay.db`.

| Table | Holds |
| --- | --- |
| `events` | Seq, time and text of each activity line. Clean-up keeps the newest 200, none older than 7 days |
| `rooms` | One row: the rooms from protocol 5 on, as JSON (code, protocol, times, locked, racers, a quick match's kind, race and fill time, and each seat's slot, address, token and `FEATURES`), and when they were saved. Votes aren't kept |

The relay never waits on it. `record` hands each line to a channel of 1024 without
blocking, and counts a line it can't hand over in `tempLost` rather than wait. One
goroutine, `persist`, does all the writing: lines in a batch every second, the rooms
every 2 s (copied under `mu` by `saveRooms`, written after; unchanged rooms only move
the time on), and the clean-up every minute.

On SIGTERM, `Shutdown(true)` closes only the rooms before protocol 5, with "The server
is restarting", then `persist` writes the last lines and rooms. On start, `LoadTemp`
brings back the lines, numbering new ones after them so an open dashboard adds to its
list, and the rooms if they were saved within `-race-timeout` plus `-away-timeout`
(35 s), which is how long a game tries to get back in. Each driver is seated at the
address they had and seen just then. A game whose socket survived carries on; one
that has started getting back in sends `back` from its new socket, with the token it
already holds. The usual timeouts drop anyone who doesn't come back. A crash keeps the
rooms as they were up to 2 s before.

### Analytics

Off unless the relay starts with `-analytics`. Then `r.tally` counts one UTC day in
memory, and the relay's hot paths only bump integers:

| Counted | Where |
| --- | --- |
| Visitor | `register`, for any host or join, as HMAC-SHA-256 of the IP with the random key in `relay.db.key` |
| Room, join | `register`, once seated |
| Refusal | `refuse` |
| Seat taken back | `rejoin` |
| Race, racers | `lock`, the first time a room locks, and a quick race if the relay made it |
| Finished race | `dropRoom`, when a locked room empties or closes |
| Peak players | `seat` and `Sweep` |
| Traffic | `Sweep`, from the per-second rates |

The relay reads nothing it forwards, so it can't see single races: a room's rematches
are one record. `Sweep` starts a new tally at midnight UTC. `FlushAnalytics` hands the
tallies over and writes them once a minute, at shutdown, and before the dashboard shows
or exports them. A visitor hash is inserted with `INSERT OR IGNORE`, and only a new row
adds to the day's `unique_ips`, so a day's count survives its hashes being pruned. A
tally holds at most 65536 visitors, so forged sources can't grow it.

### The dashboard

`-dashboard addr` serves an HTML page, embedded in the binary. htmx polls `/live`
every 2 s and swaps in fresh tables. Recent activity polls `/activity` on its own, and
the page adds only lines with a higher `Seq`, so the list keeps its scroll position.
Neither redraws while text is selected, because that would lose the selection, and the
header says it's paused. Ctrl+A over the list selects just the list. Analytics, when
on, poll `/analytics` every minute. A quick match carries a QUICK badge, and the time
left to fill until it starts.

| Route | Method | Action |
| --- | --- | --- |
| `/` | GET | Full page |
| `/live` | GET | Live section |
| `/activity` | GET | Recent activity lines |
| `/analytics` | GET | Analytics section, with `-analytics` only |
| `/export/daily.csv`, `/export/races.csv` | GET | Downloads, with `-analytics` only |
| `/htmx.js` | GET | Embedded script |
| `/login` | GET, POST | Login form |
| `/logout` | POST | End this login |
| `/close` | POST | Close a room or race, telling the drivers |
| `/ban` | POST | Ban an IP and remove its clients |
| `/unban` | POST | Remove a ban |
| `/users/add`, `/users/password`, `/users/delete` | POST | Manage dashboard users |

Who gets in:

- **With users**, everyone logs in, even on loopback. A login sets an HttpOnly,
  SameSite=Strict cookie holding a random token; only its hash is stored, so the
  database alone can't be used to log in. An expired login sends htmx polls to the
  form through `HX-Redirect`. Ten wrong passwords lock an address out for 15 minutes.
  Behind Docker every connection can share one address, so there it locks out
  everyone, which is still better than allowing guesses.
- **Without users**, only this machine: the connection must come from loopback, and
  the `Host` must be loopback too, which stops a page using DNS tricks through a local
  browser. Forging `Host` from another machine gets nowhere. Adding the first user
  from the page logs you in as them.
- Either way, Go's `http.CrossOriginProtection` refuses a non-GET request that a
  browser marks as from another site (`Sec-Fetch-Site`), or whose `Origin` doesn't
  match, so another site can't make a browser post to it, or log it in.

Every answer says it can't be framed (`frame-ancestors 'none'`, `X-Frame-Options`) and
mustn't be sniffed. A form body over 64 kB is cut off, and the server times out slow
or idle connections.

Changing your password ends your other logins. Nobody can remove themselves, so
there's always a user who can get in. If every password is lost, `relay -db FILE user
passwd NAME` sets one from the command line.

At startup, `SPPPD_ADMIN_PASSWORD` (or the older `SPPPD_DASHBOARD_TOKEN`) adds the user
`SPPPD_ADMIN_USER` (default `admin`) if there are no users yet. It never changes an
existing user, so a password changed on the dashboard survives a deploy.

### Deploying

The relay runs as a Kamal accessory on the official server: `alpine:3.24` with the static
binary uploaded beside it, so there's no image to build or registry to push to. It runs
on a read-only root with every capability dropped, `no-new-privileges`, 256 MB of
memory and 128 processes at most, as the deploy user, so it can write
`~/spppd-relay/data`, which Kamal mounts at `/data` for the database. `bin/relay-deploy`
looks up that user's IDs over SSH. UDP 8080 is public, and the dashboard is published
on the server's loopback only. Docker's published ports go past UFW, as 80 and 443 do,
so the firewall needs no rule. The official server runs with `-analytics`, and its
Docker log, which holds IP addresses, is capped at 10 MB, as `PRIVACY.md` promises.

Never point the network tests at the official server. Each run makes dozens of rooms
and races from one address, and they land in its analytics and the dashboard's
activity as if people had played. `tests/relay.lua` skips them for any address that
isn't loopback or private. `make check-relay` (`relay probe HOST:PORT`) checks the
server instead: it asks for a seat without a cookie, which only gets a cookie back,
so it counts no visitor, writes no activity and makes no room.

```
make deploy-relay                                          # first run makes the password
make check-relay                                           # does it answer? Deploys run this too
ssh -L 9090:127.0.0.1:9090 $SPPPD_SSH_USER@$SPPPD_HOST     # then http://localhost:9090
kamal relay-users                                          # list the dashboard users
```

#### Backups

Litestream (`config/litestream.yml`) runs as a second accessory, `backup`, and copies
`relay.db` to an S3-style bucket within seconds of each change, with a full copy daily
kept for 7 days. It shares the relay's data folder and user, and the bucket's details
and key come from `.env` (`SPPPD_BACKUP_*`, `LITESTREAM_*`). It's off unless `.env`
has `SPPPD_BACKUP=on`. Then `make deploy-backup` starts it, and `make deploy-relay`
starts it first. Turning it off doesn't stop a running backup; `kamal accessory
remove backup` does.

The first time, deploy the relay before turning backups on: an older relay kept the
analytics key in the database, and the new one moves it out on start, before
Litestream ever copies the file.

The order matters on a new server. A fresh, empty database started under Litestream
is backed up over the good copy, so the backup container first restores the database
if there's none (`restore -if-db-not-exists -if-replica-exists`) and only then starts
copying, and `bin/backup-deploy` waits for it to say `replicating to` before the relay
is started. If the restore fails, nothing is copied and the relay isn't touched.

To restore by hand, with the relay stopped and the bad database moved aside, start
the backup again with `make deploy-backup`. The key file isn't backed up, so a
restored server makes a new one.

The server's details come from `.env` in the repository root, which isn't in git:
`SPPPD_HOST`, `SPPPD_SSH_USER` and `SPPPD_DOMAIN`, and optionally `SPPPD_OLD_DOMAINS`:
earlier names, comma-separated, which kamal-proxy also serves and Caddy redirects to
`SPPPD_DOMAIN`, path and all. `bin/relay-deploy` adds the first
user's password to it as `SPPPD_DASHBOARD_TOKEN`; the user is `admin`. Deploying restarts the relay, and anyone
racing is told. Bans, users, logins and analytics survive it.

### Server status

`spppd.xyz/status/` tells players whether the official relay is up, with how many
drivers are online and races running. `-status addr` serves those counts as JSON at
`GET /api/status`, with `looking`, the drivers in quick matches that haven't started;
if it answers, the relay is up. On the official server it listens
on `:8081` on the kamal network only, and the website's Caddy passes `/api/status` to
`spppd-relay:8081`, so a stopped relay shows as down. In `make site-dev`, Vite passes
it to `127.0.0.1:8081` (`SPPPD_STATUS` to change that).

### The website

`site/` is an Astro site, served at `https://spppd.xyz` from the same name
as the relay: the relay takes UDP 8080, and kamal-proxy, which already serves the
server's other sites, takes HTTPS. It's the Kamal app in `config/deploy.yml`: a Caddy
image (`site/Dockerfile`, built from the repository root) behind kamal-proxy, which
does the TLS. Caddy logs no requests.

It has no copy of anything the repository already says. The changelog page is
`CHANGELOG.md` split at each `## version (date)` heading, leaving out `Unreleased`, and
the privacy and terms pages are `PRIVACY.md` and `TERMS.md`. The status page is the one
page with data from outside the build: see Server status. Their links to each other
become links to the pages (`siteLinks` in `site/src/lib/repo.ts`). The version comes
from `src/config.lua`. The downloads link this version's GitHub release, so the site's server
doesn't carry them. `make site-downloads` writes their sizes from `dist/` into
`site/src/downloads.json`, and the build stops if one is missing or the file is for
another version. Caddy redirects old `/download/` links to the release. Blog posts are Markdown in `site/src/content/blog/`.

The clips and stills in `site/public/media/` come from the real game:
`site/scripts/record-clips.sh` runs `--visual` scenes in a copy of the game, stepped
1/60 s per frame, and saves every frame for ffmpeg. Visits are counted with the
self-hosted Umami at `stats.hblabs.xyz` (`site/src/site.config.ts`), only on the real
domain, and the page loads nothing else from elsewhere. Caddy's Content-Security-Policy
holds it to that, so the build keeps scripts and styles in files, not inline.

```
make site-dev       # http://localhost:4321
make site           # site/dist
make deploy-site    # builds, then bin/site-deploy
```

## 17. Saved data, builds, tests and performance

### Saved data

Everything lives in LÖVE's save folder for the identity `spppd`, or `spppd-test` for
test runs.

| Path | Contents | Written by |
| --- | --- | --- |
| `settings.lua` | Preferences and the last race setup | `settings.save` |
| `records.lua` | Best lap and ghost per track and car, keyed `track/car` | `settings.submitLap` |
| `tracks/*.lua` | Editor tracks | `catalog.save`. A track shared online isn't saved |
| `music/` | The player's songs | `radio.addFile`, or by hand |
| `soundcache/<md5>/` | Rendered WAVs | `sound_cache` |

`settings.load` only accepts keys that already exist with the same type as the
default, and both data files run in an empty environment. A corrupted file is ignored
without any error reaching the player. `settings.car` and `settings.hue` are list
positions, hence "new cars go on the end".

### Builds

| Target | Produces |
| --- | --- |
| `make run` | Runs the game |
| `make server` | `dist/relay` |
| `make relay-linux` | `dist/relay-linux`, static, for the server |
| `make deploy-relay` | Tests the relay, deploys it, then checks it answers. See [Deploying](#deploying) |
| `make check-relay` | Checks the official relay answers, without showing in its stats |
| `make site` | The website in `site/dist`, with this version's builds to download. See [The website](#the-website) |

| `make zip` | `dist/spppd-3.5.0.love`. Tests stay out |

| `make apk` | APK signed with a local key, application id `xyz.spppd` |

| `make apk-perf` | APK that runs `--perf` at launch |
| `make all` | `clean` first, which wipes `dist/`. Releases use `make zip win64 win32` |

The first `make apk` compiles LÖVE 11.5 for Android (about 1 GB). After that only the
`.love` inside the APK is swapped, then it's realigned and resigned. Changing the
version or `android/prepare.sh` compiles it again.

`prepare.sh` brings love-android 11.5 up to what Google Play asks: target API 36, and
64-bit libraries on 16 KB memory pages. That takes NDK r27, which goes no lower than
Android 5.0 (API 21), and Android Gradle Plugin 8.10.1 on Gradle 8.11.1. It also patches
what r27 and the newer R8 broke: `-Wno-register` for libmodplug, `ALooper_pollOnce` in
SDL's sensor code, and keep rules for the `love` library, whose shrinking otherwise
strips the constructor Android starts `GameActivity` with. `apk.sh` aligns with
`zipalign -P 16`. Check a build with `zipalign -c -P 16 -v 4` and `readelf -lW` on its
`lib/arm64-v8a/*.so` (LOAD alignment `0x4000`).

From API 35 Android draws apps edge to edge, and LÖVE already lays a fullscreen game
under a camera notch. `ui.safeArea` reads `love.window.getSafeArea()`, and the HUD,
the touch controls and the menus are drawn inside it while the race and the menu's
backdrop fill the screen. Touches are moved into the same space in `main.lua`. On the
A04 the notch takes 24 units on one side. `SPPPD_SAFE=left,top,right,bottom` fakes one
on a desktop.

The version lives in `config.lua`, and `Makefile` and `android/prepare.sh` read it from
there. `VERSION_CODE` beside it is the Android version code, major * 10000 +
minor * 100 + patch; a test checks the two agree. F-Droid builds each new `v*` tag
from source and offers it only if the code went up, and shows
`fastlane/metadata/android/en-US/changelogs/<VERSION_CODE>.txt` as its notes. There is no CI.

Things to know about the harness:

- `tests/run.lua` calls `jit.off()`, matching the Galaxy A04.
- A debug hook fails any test that runs past its time limit (`SPPPD_TEST_LIMIT`, 120 s
  by default), so a hang gives a traceback.
- `--test` has no audio or graphics, so `audio.ready` is false and a test guarded by
  it passes silently. It also never builds a track mesh. After drawing changes, a
  `--visual` scene is the real check.
- `LOVE_GRAPHICS_USE_OPENGLES=1 love . --visual flow` runs on real GLES and catches
  shader errors that desktop GL lets through.

### Performance

Mid-range phones with 60 Hz screens are the target. The Galaxy A04 is the floor that
must stay playable, not the thing to tune for, so visuals aren't cut for it unless it
drops below playable.

`love . --perf` drives an AI around nine cases covering day to midnight, low and high
effects, and sustained boost including a 60 s heat test. Each prints fps, frame time
percentiles, draw calls, garbage and time per subsystem. That includes the HUD's
parts (`text`, `panel`, `touchui`, `minimap`) and the simulation's (`sim`, holding
`tyres`, `surfaces`, `ai`, `slip`, `progress` and `box2d`, then `audio`, `carfx`,
`particles`). The parts are also inside their parents' figures, and each timed call
costs a little, so they add up to a bit more than the parents.

Measured on the A04 on 2026-11-01, before the horn was added: every case held about
59.6 fps, with update about 4 ms and draw about 7 ms on high effects. LuaJIT's compiler
is off there, which is LÖVE's state on that phone, and it was never turned on.

On 2026-11-06, the `perf-pass` branch took draw calls down by 20 to 36 a frame, and
the draw time down as below. Every one-driver case now holds about 59.5 fps:

| Case | fps before | fps after | Draw ms before | Draw ms after |
| --- | --- | --- | --- | --- |
| mirage-midnight-boost-high | 54.0 | 59.2 | 10.3 | 8.1 |
| highlands-dusk-high | 57.6 | 58.8–59.5 | 8.9 | 8.1 |
| mirage-night-boost-high | 58.8 | 59.5 | 8.3 | 7.0 |
| harbour-night-low | 59.6 | 59.7 | 6.9 | 6.0 |
| split-harbour-night-high | 38.7 | 41.4 | 16.1 | 15.0 |

Where a race frame goes on the A04, high effects: update about 3.9 ms (tyres 1.0,
wheel surfaces 0.6, AI 0.5, audio 0.3), HUD about 2 ms (text 0.8, touch controls 0.6,
minimap 0.3–0.5), glow 1.6–2.4 ms, ground 0.8 ms.

The choices that matter most: the static world baked into meshes, a single skid mesh,
and half-size lightmap and glow canvases with a quarter-size blur.
