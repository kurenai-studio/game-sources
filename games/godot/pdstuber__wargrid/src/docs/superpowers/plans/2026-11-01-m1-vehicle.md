# M1 — one controllable vehicle implementation plan

> **For agentic workers:** Use `superpowers:executing-plans` task by task. Follow project instructions for test delegation and one final substantive review, then Ponytail review. No reviewer per task.

**Goal:** select one placeholder vehicle on an isometric desert map, issue movement orders around fixed obstacles, and inspect predictable arrival/blocked behavior.

**Architecture:** extend the existing authoritative simulation; use Godot's `AStarGrid2D` for a bounded static grid. A thin Node2D view draws snapshots; input converts viewport coordinates into simulation coordinates before submitting existing commands. Retain the current runner, shell wrappers and CI.

**Executor target:** Sol at Medium, following these contracts rather than designing additional systems. Work task by task in the main session; use test/review delegation only as required by project instructions.

**Tech stack:** pinned Godot 4.7.2, typed GDScript, Compatibility renderer, 30 Hz simulation. No dependencies or assets to download.

**Spec:** [blueprint](../../blueprint.md), M1 and §§2–5. This plan owns concrete M1 contracts. M0 plan remains historical evidence; M1 deliberately replaces its stationary-move expectations.

**Status:** prototype defaults adopted by explicit `prompt.txt` kickoff; M1 automated implementation verified locally. See [verification](../../reference/m1-verification.md) for local review, visible smoke scope and pending remote CI. Defaults are Wargrid choices, not measured Zero Hour behavior.

## Task 1 — projection and static navigation, test first

**Interfaces:** `isometric.gd` extends `RefCounted`, with static `world_to_plane(point: Vector2) -> Vector2` and `plane_to_world(point: Vector2) -> Vector2`.

- World uses square cells of side 1. Cell `(x,y)` occupies `[x,x+1) × [y,y+1)`; center is `(x+0.5,y+0.5)`. Use floor, never truncation, for cell lookup.
- Projection: `(32*(x-y), 16*(x+y))`; inverse: `(plane.x/64 + plane.y/32, plane.y/32 - plane.x/64)`. This gives 64×32 projected tiles. Neither function includes camera transforms or rounds authoritative values.
- Draw only may round pixel coordinates later. No movement/physics calculation in projected pixels.

`grid_navigation.gd` extends `RefCounted`:

```gdscript
const SIZE := Vector2i(16, 16)
func _init(blocked_cells: Array[Vector2i] = [])
func is_walkable(point: Vector2) -> bool
func route(from: Vector2, to: Vector2) -> Array[Vector2]
func snapshot() -> Dictionary
```

- Constructor input is authored scenario data, not an external parser. Copy/deduplicate cells and assert all lie within fixed grid; tests use valid layouts. Sort snapshot cells by `(y,x)`. No map editor/config loader.
- `is_walkable`: finite point with `0 <= x,y < 16`, whose floored cell is not solid. Check bounds before calling A* methods; invalid endpoints return empty route without Godot error logs.
- AStar configuration: region `Rect2i(0,0,16,16)`, unit cells, square cell shape, Manhattan compute/estimate heuristics, `DIAGONAL_MODE_NEVER`, jumping disabled. Call `update()` before setting solids; never update again per route/tick.
- Query `get_id_path(start_cell,end_cell,false)` once per applied move. Empty path means unreachable. Within same walkable cell return `[to]` directly.
- For a multi-cell path, return start-cell center, subsequent cell centers, then exact `to`; remove consecutive duplicates and leading points equal to `from`. Including start center prevents a retarget from cutting through a blocked corner. Do not append a direct target if A* returns empty.
- `snapshot()` returns independent `{"size": [16,16], "blocked_cells": [[x,y], ...]}`. No AStar object/resource in snapshots.

| Cases | Assertions |
|---|---|
| P1 axes/roundtrip | `(1,0)->(32,16)`, `(0,1)->(-32,16)`, `(2.5,1.5)->(32,64)`; inverse roundtrips those plus `(0,0)`, `(-0.25,2)`, `(15.999,0.125)` within `1e-5`. |
| N1 boundaries | `(0,0)` and `(15.999,15.999)` valid; `(-0.01,0)`, `(16,0)`, NaN/INF invalid. Solid `(2,2)` rejects `(2.5,2.5)`. |
| N2 open path | `(1.5,1.5)->(3.5,1.5)` yields `[Vector2(2.5,1.5),Vector2(3.5,1.5)]`; same-cell target `(1.75,1.5)` yields that exact one waypoint. |
| N3 obstacle | Solid `(2,1)`; start `(1.5,1.5)`, target `(3.5,1.5)`. Route nonempty, ends at target; every traversed cell walkable, neighbor cell steps orthogonal; total center-path distance 4. Do not pin arbitrary top/bottom tie choice. |
| N4 disconnected/corner | Wall `(3,y)` for all y: `(1.5,1.5)->(5.5,1.5)` returns empty. With solids `(1,0),(0,1)`, route `(0.5,0.5)->(1.5,1.5)` empty; no diagonal escape. |
| N5 immutability | Mutating constructor array or returned blocked-cell array does not change walkability/snapshot; repeated route calls identical on pinned engine. |

## Task 2 — movement and deliberate M0 test migration

**API:** keep `spawn`, `issue_command`, `step`, `snapshot` signatures. Add only optional simulation constructor `_init(blocked_cells: Array[Vector2i] = [])`, which creates navigation helper; default map has no solids. No stationary compatibility mode.

**Motion rules:**

- Prototype speed is exactly **3 world units/second**, budget `3.0/30.0` per tick. Point-sized ground unit; no footprint clearance or inter-unit collision yet. Label this limit in movement note; do not claim production RTS navigation.
- Spawn now also rejects out-of-map/solid positions with `-1`, consuming no ID. Command target now also must be walkable; otherwise reject immediately with full snapshot unchanged, including current route and sequence. Existing type/ownership/sequence rules stay intact.
- Tick phases: (1) consume due commands in existing canonical order and assign orders, (2) compute routes for final replacement orders only, (3) advance each moving entity in ascending ID order, (4) increment tick. Newly applied move travels in the same tick. Same-tick replacements receive one movement budget, never one per command.
- For unreachable but walkable destination, command is accepted initially; when applied clear previous order/route, set status `blocked`, stay at current position. No retry every tick. A later valid move can recover.
- Advance along waypoints using remaining distance budget. Snap to waypoint when distance <= remaining budget + `1e-5`, subtract distance with remaining budget clamped to zero, pop waypoint and continue. This tolerance covers accumulated Vector2 float arithmetic; never widen it to hide route/speed errors. Loop consumes a waypoint or remaining budget each iteration; no unbounded retry.
- Arrival: exact final target, order null, route empty, status `arrived`. Initial status `idle`. Active order status `moving`. Stationary same-position order arrives immediately. Status persists until a new applied order; invalid commands leave it unchanged.
- Retarget replaces route from actual current position. No teleport, no movement caused by `issue_command` or `snapshot`.

**Snapshot evolution:** keep old keys; add top-level `map` from navigation snapshot. Each entity adds `status` and `route` (remaining waypoints as independent `[float,float]` arrays). Route/state must be included because it affects future steps. Keep exact same-build snapshot comparisons; tolerances only for measured positions/distances.

**M0 migration checklist (do not delete the tests):**

- C1 fresh/entity literals gain map/status/route fields. Existing valid spawns remain valid on default map.
- C2 and C4 replace stationary-position expectations with movement assertions. C3 still waits until due tick, then moves. Preserve exact order target float-type checks.
- C5–C8 preserve rejection, sequencing, type and command-copy checks. C9 additionally mutates nested route/map arrays and verifies isolation.
- C10 remains exact cross-submission-order comparison. C11 final position becomes `[8.0,9.0]`, order null, status arrived, route empty; preserve tick/ID/queue/sequence checks.
- C12 still verifies all IDs in an accepted group receive movement, sorted snapshot IDs and copied targets. Replace its stationary full-state literal with explicit expected fields plus both positions changed by at most one budget. No group collision requirement.
- Explain these changes in verification record as M1 behavior, not weakened M0 assertions. If a test changes for another reason, justify it separately.

## Task 3 — view and controls

**Scene tree:** `Main` Node with existing main script; `WorldView` Node2D with view script; `Camera2D`; `HUD` CanvasLayer containing a Label named `Status`. Keep gameplay out of draw/input nodes.

- Main constructs one static scenario: blocked rectangle x=6..8, y=4..9 inclusive; spawn owner 1 at `(2.5,2.5)`. Navigation constants define dimensions; do not duplicate a second collision map in view. One snapshot drives drawing, HUD and picking.
- View has `set_state(state: Dictionary, selected_id: int) -> void` (copy then queue redraw) and `pick_entity(plane_point: Vector2) -> int` (owned ID or -1). `_draw` renders sand-colored diamond tiles, dark blocked tiles, placeholder vehicle rectangle, selection outline and target cross. Vehicle footprint for drawing/picking is `Rect2(projected_position + Vector2(-12,-16), Vector2(24,16))`; selection uses same bounds. Iterate ground content first, vehicle and marker after. No external images, shaders or taller occluding buildings.
- M1 draws current state at 30 Hz without interpolation. Do not quantize simulation to pixels. Record motion smoothness as a playtest question; interpolation and sprite polish can follow based on observed need.
- Set desktop viewport 1280×720, resizable, canvas-items stretch. Root view texture filter nearest; no claim that fractional zoom gives pixel-perfect finished art. Camera begins at projection of `(8,8)`, smoothing disabled, zoom 1.
- Left press selects vehicle on its rectangle; empty click clears selection. Right press with selection issues existing move command at current tick, player 1 and next sequence. Increment UI sequence only on acceptance. Right press without selection does nothing. Target is exact inverse-projected ground point, not cell-snapped.
- Handle pressed mouse buttons in `_unhandled_input`; HUD Label ignores mouse so it cannot swallow terrain clicks. Convert `event.position` with `WorldView.make_canvas_position_local`, then inverse projection. Do not subtract camera position or apply zoom twice.
- WASD/arrows pan camera along screen-plane axes at 400 projected units/second divided by zoom, using render delta and normalized input vector. Wheel up/down chooses zoom 0.5,1,2, clamped at extremes, centered on camera (not mouse). Escape clears selection. No edge-scroll, rotation or drag-select.
- Main input/camera code exposes only two small testable operations: `pan_camera(direction: Vector2, delta: float) -> void` and `change_zoom(direction: int) -> void`; event/action handlers call those. Camera position clamped to projected map bounding box x=[-512,512], y=[0,512]. No game-state mutation from camera operations.
- HUD shows controls, selected ID or none, tick and entity status; rejected move displays reason, accepted move clears it. Destination cross follows active order; disappears at arrival/blocked. Rejected order leaves old target visible.
- Keep `simulation` property on main for integration checks, plus `selected_id` initialized to -1. `_ready` initializes scenario and view once. `_physics_process` calls `step()` once and refreshes view/HUD. No accumulator or second simulation.

## Primary API references and limits

- [AStarGrid2D](https://docs.godotengine.org/en/stable/classes/class_astargrid2d.html): `DIAGONAL_MODE_NEVER` means “the way will be always orthogonal”; `update()` warns “All point data (solidity and weight scale) will be cleared.” Initialize before setting solids. No cross-version path tie guarantee inferred.
- [CanvasItem](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html): `make_canvas_position_local` “Transforms viewport_point from the viewport's coordinates to this node's local coordinates.” Use inverse isometric projection afterward.
- [Camera2D](https://docs.godotengine.org/en/stable/classes/class_camera2d.html): smoothing/limits can make node position differ from actual screen center. Use canvas transform, not hand-subtracted position, for input.
- [GDScript await](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_basics.html#awaiting-signals-or-coroutines): awaiting an ordinary returned value returns it immediately; async tests can share existing runner with synchronous cases.
