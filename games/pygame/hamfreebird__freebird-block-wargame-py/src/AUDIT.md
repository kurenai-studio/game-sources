## 1. 性能

### 1.1 一页数据

测量方式见 §1.6。左列 128×128 是主力想定（103 单位），右列是合成大地图（412 单位）。

| 项目 | 128×128 | 256×256 |
|---|---|---|
| 想定载入 | 79ms | 0.24s |
| 开局构造 `GameState` | 59ms | — |
| 首帧（含建块） | 110ms（48 块 / 4.9MB） | 167ms（66 块 / 6.8MB） |
| **整帧渲染** | **3.0ms** | **3.4ms** |
| ├ 地形块 blit | 0.4ms | 0.4ms |
| ├ 单位 | 0.4ms | 0.6ms |
| ├ 环境层（色调/雨雪） | 0.5ms | 0.5ms |
| └ 目标/工事/设施/特效 | 各 ≤0.1ms | 各 ≤0.1ms |
| 探测全量重算 | 3.0ms | 10.5ms |
| **AI 一方相位（决策+执行）** | **≈1.7s**（回合 3.4s 的一半） | **29.8s**（单方实测） |
| 一回合（双方 + 弹药结算） | 3.4s | ≈60s（推算） |
| AI 单步 p50 / p90 / p99 / max | 8 / 96 / 519 / 731 ms | 未测（每次 miss 更贵） |
| 距离场查询 / 未命中（每回合双方） | 1553 / 87 | — |
| 距离场查询 / 未命中（单方相位） | — | 5904 / 288 |
| 距离场缓存被清空 | 0 次 | **2 次**（单方相位内） |
| 探测全量重算次数 | **190 次/回合 = 401ms** | — |
| `objective_tiles` 调用 | **369 次/回合 = 475ms** | — |

### 1.2 先排除：渲染不是瓶颈

整帧 3.0–3.4ms，占 60fps 预算（16.7ms）的 18–20%。分块地形 + 精灵缓存 +
整层复用的三件套是有效的：`_draw_units` 在 412 单位下也只花 0.6ms。
**渲染层不需要动**，继续优化它只是在 3ms 里抠 0.2ms。

首帧 110–167ms 是建块的代价，只在地图切换 / 首次缩放时付一次；可以接受，
但如果以后要支持「连续缩放」，这会是掉帧点。

### 1.3 A1/A2：AI 相位与距离场缓存（高）

`cProfile` 单回合（双方）采到的总量（profile 自身有开销，绝对时间会比实测的
3.4s 大，看**比例**即可）：

```
33,650,673 次函数调用             11.0s（profile 开销放大，实测 3.4s）
 _build_field      1347 次  cum 6.03s   ← 55%
 tile_move_cost  1,767,928 次
 iter_tiles      8,634,895 次 yield     ← 约 525 次全图遍历
 objective_tiles   340 次  cum 1.35s
```

两个根因都在这一屏里：

**根因一：缓存容量贴着工作集。** `core/pathfind.py:380` 写的是
`if len(cache) > 96: cache.clear()`——注意是**整表清空**，不是淘汰最旧的。

| 地图 | 峰值条目 | 上限 | 被清空 |
|---|---|---|---|
| 128×128 | 87 | 96 | 0 次 |
| 256×256 | 94 | 96 | **2 次** |

工作集 = 单位机动剖面数 × 目标点数。128 上「87/96」意味着再加一个目标点、
或者多一种载具的机动剖面，就会开始周期性清空——这不是余量，是悬崖。

**根因二：`objective_tiles` 是属性，但每次 O(全图)。**

```python
# core/engine.py:206
@property
def objective_tiles(self) -> list[Tile]:
    return [t for t in self.map.iter_tiles() if t.objective]
```

名字看起来像廉价访问器，实际是 16,384 次迭代（256×256 下 65,536 次）。
AI 每回合调用 369 次，累计 475ms——占 128×128 一回合的 14%。

**改法（已用 monkeypatch 验证收益，未提交）：**

| 256×256 单方相位 | 耗时 | 相对基线 |
|---|---|---|
| 基线 | 29.8s | — |
| + 距离场缓存不清空 | 26.2s | −13% |
| + `objective_tiles` 按 `tile_epoch()` 缓存 | 23.4s | −22% |
| **两者都改** | **19.3s** | **−35%** |

`objective_tiles` 的缓存判据现成：`model.tile_epoch()` 已经在 v3.3.1 里
覆盖了目标点的归属与存在性（`mapview.py:663` 用的就是它），引擎侧照抄即可。

缓存那条建议改成「按需淘汰」而不是「满就清空」：工作集只有几十条，
直接放到 512 条上限成本可忽略（每条是一个 `dict[格, float]`），
或者按 `goal` 分组做 LRU。**注意别把 `map_epoch` 从键里拿掉**——
地形变更必须让场失效。

### 1.4 C1：AI 单步长尾（中）

一回合被拆成 ~49 个「动作」，UI 每 `ai_delay`（0.24s）走一步。中位数 8ms
完全无感，但长尾很难看：

| 分位 | p50 | p90 | p99 | max |
|---|---|---|---|---|
| 单步耗时 | 8ms | 96ms | 519ms | 731ms |

0.7s 的一次动作会让画面**卡住一帧**（16.7ms 预算的 44 倍）。表现是
「AI 思考时偶发顿一下」，玩家未必说得出原因，但会觉得不流畅。

成因是 §1.3 的缓存未命中：一次未命中的 Dijkstra 建场在 128×128 上就要
几十毫秒（取决于落在近距档还是全图档）。**修完 A2/A3，这条通常会一起消失**，
所以不单列工单，只作为验收指标：修完后 p99 应低于 100ms。

### 1.5 两处可以顺手拿掉的开销（低）

**补给线每帧重建签名。** `mapview.py:589` 每帧重新构造
`tuple((u.uid, u.x, u.y) for u in mine)` 与 `links` 的排序键。层本身是缓存的，
但签名的构造成本是 O(单位 + 链路)。实测 `_draw_supply_lines` 占整帧 0.7ms
（23%），比地形层还贵。改成「单位位置版本号 + 链路版本号」两个标量即可。

**探测全量重算每回合 190 次。** `refresh_detection()` 走的是
`build_detection_map()` 全量重算（3.0ms / 10.5ms），一回合被调用 190 次，
128×128 上合计 401ms（12%）。大地图上按比例会到 2s 量级。
`apply_ai_action` 后其实只需刷新受影响单位——`touch_unit()` 已经有世代号机制，
全量重算属于「省事但没必要」。

### 1.6 复现方式

```bash
python tools/perf.py                 # 渲染 / 探测 / 可达集
python tools/perf.py big256          # 合成 256×256
python tools/diag.py 20              # 20 回合推演（含 L26 随机流断言）
```

AI 相位与缓存命中需要临时插桩（本次审计用的就是一次性脚本，未入库）。
若要把这两项变成常驻指标，建议加进 `tools/perf.py`：它能顺手把
「AI 相位耗时」和「缓存清空次数」变成 CI 闸门——这正是 v3.3 对渲染做过的事。

## 2. 视觉与界面

### 2.1 B1/B2：浅色主题下地图信息消失（高）

地图层的文字与符号颜色是**写死的**，不跟主题走：

```python
# ui/mapview.py:698-699  目标点名称
T.draw_text_center_x(surf, t.objective_name, cx, r.bottom + 1, 11, (235, 228, 200))
# ui/mapview.py:727  中立设施符号
col = T.side_color(t.owner, "edge") if t.owner is not Side.NEUTRAL else (170, 176, 186)
```

按 WCAG 相对亮度算对比度（`(235,228,200)` 这类米白在深色主题下是 5.38:1，合格）：

| 前景 | 背景 | 深色主题 | 浅色主题 |
|---|---|---|---|
| 目标点名称 `(235,228,200)` | 地形色（最差：海岸） | 5.38:1 | **1.12:1** |
| 中立设施符号 `(170,176,186)+25%` | 地形色（最差：海岸） | 3.88:1 | **1.01:1** |
| 侦测「已识别」`(150,200,240)` | 面板 | 10.56:1 | **1.72:1** |
| `TEXT_FAINT` | 面板 | 2.75:1 | **3.12:1** |

1.12:1 意味着**和背景几乎没有区别**——不是「不好看」，是这几处信息在浅色
主题下等于没画。目标点名在 `tile ≥ 26` 时出现，而缩放档位一直到 60，
所以正常放大就会撞上。

`ui/inspect.py:27` 是另一处：`_det_color()` 把「已识别」写死成浅蓝，
绕过了主题系统。它属于信息卡的语义色，应该在 `theme.py` 里有一席之地。

**改法**：地图层的**文字与符号**颜色改走主题（加 `MAP_LABEL` / `MAP_SYMBOL`
两个令牌），棋子本体色可以保留——棋子是「实体」，深色底 + 亮色描边在
两套主题下都成立，这是有意的设计，不是遗漏。

### 2.2 B3：地形辨识度（中）

把每套主题里 9 种地形的颜色两两算对比度：

| 主题 | 平均 | 最小 | < 1.3:1 的对数 |
|---|---|---|---|
| tactical | 1.45:1 | 1.03:1（城区 vs 沼泽） | 15/36 |
| **light** | **1.18:1** | **1.01:1（丘陵 vs 城区）** | **29/36** |
| deuteranopia | 1.46:1 | 1.03:1 | 15/36 |
| protanopia | 1.45:1 | 1.02:1 | 15/36 |

地形靠「明度」几乎分不开，实际靠的是色相与点阵纹理。在 128×128 缩到
整图（tile≈6）时，纹理看不见，只剩一片色块——这也是首张想定第一眼
「发灰」的原因之一。

不必把九种地形做成九个亮度层（那会毁掉美术风格）。建议只给**影响规则
的四类**（水域机动、山地防御、城区减伤、沼泽迟滞）各加一档明度差或
一个明确的边界描边，让「能不能走过去」一眼可判。

### 2.3 B4：夜间+雾天把画面压成灰幕（中）

`core/env.py:299` 的合成分两步：时段色与天候色按 alpha 加权混色，
但**透明度直接相加**并截到 150：

```python
return (r, g, b), min(150, t_a + w_a)
```

于是 dawn(46) + fog(74) = 120，而 night(108) + fog(74) = 182 被截到 150（封顶）。
实测画面动态范围（地图区域亮度 min–max）：

| 条件 | 平均 RGB | 亮度跨度 |
|---|---|---|
| 白天 / 晴 | (36,46,47) | 250 |
| 拂晓 / 雾 | (85,91,98) | 132 |
| **夜间 / 雾** | (62,70,80) | **104** |

跨度掉 58%，地形与棋子一起挤进中灰区间。夜雾本来就该看不清，但
「看不清」应该是**暗处看不清、被照亮的仍看得清**，而不是整体蒙一层灰。
建议把 alpha 相加改成 `1-(1-a1)(1-a2)` 之类的合成（雾永远不会比夜更黑），
并给天候单独设上限（如 90）。

顺带：主想定 `strait_confrontation` 开局就是拂晓+雾（alpha 120），
这是玩家对画面的**第一印象**，值得单独调一次。

### 2.4 其他观察（不单列工单）

- 硬编码 RGB 共 45 处（`mapview.py` 32 处，其余零散）。其中棋子本体、
  血条、烟雾等属于「实体外观」，跨主题恒定是合理的；真正该改的是
  §2.1 那几处**文字与符号**。
- `TEXT_FAINT` 在四套主题下都低于 4.5:1（2.70–3.12:1），而它主要用在
  10–11px 的辅助说明上——这个尺寸按 AA 需要 4.5:1。它承担的是「可以
  不看」的信息，所以不算缺陷，但再压暗就没有意义了。
- `ellipsize()` 已用在 37 处、`wrap_text()` 15 处，`check_layout.py`
  还会在三档字号 + 最小窗口下查重叠，长文本这块是**有防线**的。

## 3. 缺陷与代码风险

### 3.1 缺陷清单

| 编号 | 位置 | 现象 | 影响 | 建议 |
|---|---|---|---|---|
| B1 | `ui/mapview.py:699` | 目标点名固定米白，浅色主题 1.12:1 | 信息丢失 | 走主题令牌 |
| B2 | `ui/inspect.py:27` | 「已识别」固定浅蓝，浅色主题 1.72:1 | 信息丢失 | 移入 `theme.py` |
| B4 | `core/env.py:307` | 色调 alpha 相加 + 封顶 150，夜雾 104 跨度 | 画面可用性 | 改合成公式 |
| C3 | `core/mods.py:659` | `user_writable_dir()` 失败时 `pass`，用户模组目录被静默丢弃 | 模组「消失」无提示 | 至少写一条日志 |
| C4 | `core/engine.py:351` | 每次刷新探测都 `invalidate_pos_index()` | 与 v3.3.1 机制相悖；190 次/回合 | 移除，靠 `pos_epoch` 兜 |

C3 的严重性被低估过：模组作者把文件放进用户目录，如果那台机器上
`user_writable_dir()` 抛异常（权限、只读盘、环境变量异常），游戏会
**当作没有模组**正常启动。玩家只会以为「我装的模组没生效」。

C4 的代价很小（重建一次 22µs，190 次 = 4.2ms/回合），但注释写的是
「每回合一次 O(N)」——与实际不符，而 v3.3.1 刚把「手记失效」换成
「写入即留痕」，这里却仍在最热的路径上手动全量失效。属于**自相矛盾**，
建议顺手删掉。

### 3.2 结构性风险

| 项 | 现状 | 风险 |
|---|---|---|
| 单文件规模 | `ui/app.py` 4257 行（次大 `ui/editor.py` 1667） | 与 v3.3 拆 `rules.py` 的理由同源；改任意界面都要在 4k 行里找 |
| 静态检查 | **CI 没有 lint**（无 ruff/flake8 配置） | 85 处未使用导入、34 个文件，全靠人眼 |
| 未使用导入 | 85 处 / 34 文件（`core/rules.py` 的 6 处是 re-export，属误报） | 噪音掩盖真实问题的信号 |
| 异常吞噬 | `core`+`ui` 中 `except Exception` 62 处（tools 另 72 处），其中紧跟 `pass` 的 10 处 | 大部分合理（音频/图标可选加载），C3 是唯一会造成「功能静默消失」的 |
| 调试残留 | `print()` 0 处、`TODO/FIXME` 0 处、裸 `except:` 0 处 | 干净 |

建议：加一条 ruff 的 `F401`（未使用导入）+ `E9`（语法/运行时明显错误）
就够，别一次上全套规则——`rules.py` 的 re-export 需要 `per-file-ignores`。

### 3.3 已核查、确认没问题的部分

写清楚这些，是为了让「报告里没提」不等于「没查」：

- **规则结论**：`diag 20` 三张图 0 错误，L1–L26 全过；`--sim` 与
  `balance_check` 可复现（同种子同结果）。
- **存档**：`test_save` 通过，含随机流整份往返、坏档不崩、迁移链逐版连续。

## 4. 建议的处理顺序

如果只做三件事，按这个顺序：

1. **A3 + A2（AI 相位）**——两项合计已实测 −35%，且没有规则风险
   （缓存只影响速度，不影响结论）。验收：256×256 单方 < 20s，
   AI 单步 p99 < 100ms。
2. **B1 + B2（浅色主题可读性）**——把地图层文字/符号与侦测色接入主题，
   加一条对比度自检（阈值 4.5:1，跑四套主题），从此不再靠肉眼。
   验收：四主题 × 关键前景色全部 ≥ 4.5:1。
3. **C2（lint 闸门）**——ruff `F401`+`E9` 进 CI，清理 85 处未使用导入。
   验收：CI 新增一步，全绿。

其余（B3 地形辨识度、B4 夜雾合成、C3 模组日志、C4 冗余失效）都是
「改一处、看得见」的小活，适合穿插在版本之间。

## 已知的机制边界（有意简化，不是缺陷）

以下都是抽象取舍，改动它们等于换一套真实度—复杂度配比，需要社区反馈来定优先级。
**完整清单以 [GAME_GUIDE.md](GAME_GUIDE.md#19-已知限制) §19 为准**，这里只留会影响
规则结论的那几条，避免两份列表越走越远。

- 卫星轨道为匀速直线地面轨迹，未建模轨道倾角、变轨与真实过顶几何
- 中段反导已支持上升段 + 中段两轮 + 破片打残；仍不模拟动能碰撞几何与碎片场
- 烟幕已随风漂移（8 方位、0–3 级）；仍不分格内浓度梯度，未建模山谷/城区绕流
- 工事已改为工时制；堑壕 / 掩体 / 雷场仍共用一套工程量
- 航空兵油量是抽象值（剖面只影响倍率），未区分副油箱
- 拦截按「一次齐射一次交战」结算，未做逐发物理模拟
- 同格共存按「域容量」近似，未建模实际空间占用
- 大型想定的 VP 为累计制，天然偏向防守方
- AI 是启发式规划，不做多回合搜索
- 战役模式只支持「胜利后进入下一关」，无分支剧情
- 设施被占领后立即易主，不建模破坏/修复的中间状态
- 想定包导入时不校验版本兼容性
