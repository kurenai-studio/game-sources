## 2. How the game was driven

- One driver script, `%TEMP%\numbersgame_qa\driver.gd` (a SceneTree script), nothing added to the repo. Godot runs it from the absolute path, so nothing had to live under res://. Command: `godot --path . --resolution 540x1200 --script <driver> -- --mode=<mode> --folder=user://qa_p4_<mode>/`. With `--script` the project's main scene is not loaded on its own (checked: the root had no children at start).
- The driver instances the real `res://scenes/main.tscn`, sets `save_folder` on its App child before it enters the tree, then adds it to the root.
- Save folder: SaveService refuses any folder outside user:// (src/save/save_service.gd:55), so the temp folder could not be in %TEMP%. Each mode used its own `user://qa_p4_*` subfolder. Bart's real files were never touched: user://run.json and user://profile.json do not exist, before or after. I deleted every `qa_p4_*` folder when done.
- Input: real events through `Input.parse_input_event`, positions mapped from canvas to window pixels with the root's final transform. Chains are InputEventScreenTouch and InputEventScreenDrag at tile centers from the board view's `cell_rect` (3 frames per tile). Every button (menu, HUD pause, Pause, Settings close, sound toggle, skin chips, booster bar, offer buy and End run, end screen) was pressed by a touch tap, which reaches it through Godot's touch to mouse emulation. No `pressed.emit()` shortcuts. One chain was driven by real InputEventMouseButton and InputEventMouseMotion events (device 0), the Windows mouse path, which the board accepted.
- Chains were picked from the live session board with `CoreRules.joinable_cells` (longest chain up to 7 tiles), so previews, clicks and scores could be predicted and checked.
- Waits: on `session.is_waiting_for_view()` and `board.is_animating()`.
- Console: each process's stdout and stderr went to a log, and an `OS.add_logger` Logger recorded every error and warning, with source, while the game ran.

## 8. Findings

### QA4-01. Medium. When a run ends at once because nothing is usable, the player is not told that no moves were left

- Owner: ui-systems-dev (src/ui/end_panel.gd), with the senior-graphic-designer for the copy and placement (DESIGN_SYSTEM.md 7.6 has no slot for it).
- Rule: GDD 12.2 step 3: "If none is usable, the run ends at once (12.3). The player sees that it ended because no moves were left." The contract carries the flag for exactly this: `RunSummary.no_moves_left`, "the run ended because nothing was usable (12.2 step 3)" (docs/ARCHITECTURE.md section 4).
- Actual: `EndPanel._fill` (src/ui/end_panel.gd:61) never reads `summary.no_moves_left`, and nothing else shows it. A run that dies with nothing usable goes from the last chain straight to a "Run over" screen that looks the same as after End run. The offer, the only place that says "Out of moves", never opens in this case.
- Steps: save Board D at score 0 and open the game (in real play: a board with no move early in a run, while nothing is affordable). Expected: the end screen says the run ended because no moves were left. Actual: "Run over", final score, records, no reason (e3_dead_on_load.png).
- Why Medium, not High: the run itself ends correctly and AT-50 passes as written, since it does not ask for the message. It happens mostly early in a run or after heavy spending. Raise it if you read the GDD line as a rule that works wrong.

### QA4-02. Medium. Every committed move drops a frame, because the save runs inside the commit frame

- Owner: ui-systems-dev (src/ui/app.gd:209 to 218 `_on_save_requested` and `_save_all`, src/save/save_service.gd:216 `_write_atomic`).
- Measured: all 40 of 40 commit frames took over 20 ms on this PC, 35 ms on average and up to 43 ms (60 Hz budget 16.7 ms), while drag and animation frames sit at 16.6 ms. Inside the commit frame, the App's save takes 15.3 ms mean, 21.4 ms p95, against about 4 ms for everything else (section 6). The same two writes repeated in a tight loop take 4.4 ms a pair, so the first write after a pause costs much more here, possibly file system or antivirus work. Each move does two atomic writes in that frame: run.json and profile.json, each written to .tmp, read back, compared and renamed. The profile is written on every move even when no record changed.
- Expected: the game holds 60 fps through a move (brief section 4). Actual: one dropped frame at the start of every merge on a fast desktop; on a mid range phone the same file work is likely slower.
- Steps: play any chain and time the frame after the lift.
- Note for whoever fixes it: D-33 wants the move saved before its animation ends, not inside the same frame, so moving the write off the commit frame (or skipping the unchanged profile) still meets the rule. Please confirm the size of the hitch on the phone in Phase 5 before deciding.

### QA4-03. Low. A long chain holds input longer than the design system says

- Owner: senior-graphic-designer to confirm the intent (DESIGN_SYSTEM.md 3.6 and 4.6), board-input-dev for the sequence (src/board/board_controller.gd `_run_stage`, the CHAIN stages 2 and 3).
- Measured: Gumdrop 1.23 s mean for chains up to 7 tiles against "about 0.9 s" (4.6), Nova 1.03 s against "about 0.8 s"; two tile chains are close to the stated figures (section 6). The board waits for the whole fall before the spawn starts, and the spawn stagger adds 0.03 to 0.04 s per new tile, so the more tiles a chain clears, the longer input waits. DESIGN_SYSTEM.md 3.6 says "then `fall` and `spawn` together (new tiles start as the falls land ...)", which can be read either way.
- Question: should spawns overlap the fall, or should the stated settle times change? Under D-35 every extra 0.3 s is time a fast player waits between moves.

### QA4-04. Low. "New best" shows under a final score that is lower than the Best score on the same panel

- Owner: senior-graphic-designer and lead-game-designer (DESIGN_SYSTEM.md 7.6); code in src/ui/end_panel.gd:70.
- Seen: final score 6,430 with a "New best" badge right under it, and "Best score 6,706" two rows below (p40_end_screen.png). The run set the record at 6,706 and then spent on boosters, so the badge is correct by the written rule ("if this run set the Best Score", and the live rule D-16), but it reads as "6,430 is a new best".
- Question: move the badge next to the Best score row, or word it "New best this run", or keep it?

### QA4-05. Low. While the offer is open there is no on-screen way to Pause or Settings

- Owner: senior-graphic-designer (DESIGN_SYSTEM.md 7.5).
- Seen: the offer replaces the HUD, and the HUD's pause button with it (p30_offer_1.png). On Android the back button still opens Pause (flow 10, checked in tests). On Windows there is no back button, so Pause, Settings and New game cannot be reached until the offer closes or the run ends.
- Question: is that intended for v1, given Windows is only the development platform?
