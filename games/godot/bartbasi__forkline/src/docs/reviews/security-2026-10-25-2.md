## New findings

### Low

**L5. Menders at the load ceiling freeze the game.** Owner: sim-engineer (src/sim/battle.gd). Contract: ARCHITECTURE 5.6.

Where: `_heal` (battle.gd:752 to 768) checks every creature on the map for every Mender, and lists every creature it healed in its event. `_check_crowd` caps how many creatures there are, not what kind.

Steps:

1. Take an r1_l2 save one tick into wave 1.
2. Replace `battle.enemies` with 4,000 Menders on one road cell, each with `health` 1, `max_health` 1,000,000,000 and `heal_at` the saved tick plus 1. Set `next_id` to 4,000, and `lives` and `start_lives` to 1,000,000.
3. Write it as game_level.json and load it with `SaveStore.load_games`. It stays under the 1 MB cap and loads in 429 ms.
4. Step the battle with events on, as the game does.

Result on the dev PC: one tick takes 9.9 s. That tick holds 4,000 heal events with 15,996,000 ids, and static memory goes from 52 MB to 548 MB. The Menders never fill up, so the same tick comes back every 40 ticks (2 s of play). The worst of the three in 90 ticks took 11.0 s. With 240 Menders among 3,760 Scamps, a heal tick still takes 0.75 s, with 959,760 ids.

Play stays far below this. The most Menders in one campaign wave is 7 (r4_l2, wave 10), run packs use groups of up to 4, and genuine play peaked at 10 Menders on the map or still to come.

Why it matters: it is L1 again in another shape. Every field is in range, and the total is under the ceiling, but the game freezes. On the phone, expect an "app not responding" dialog or an out of memory kill each time the game is resumed. A resumed game opens paused, so the player can leave it and start that mode over.

Fix: on load, refuse more than a small number of creatures that heal, live or still to come from releases, the way `MAX_SUMMONERS` works (for example 40). N8 explains why the saved level's waves need the same bound. Capping the ids in one heal event would also cut the memory: the map shows at most `HEAL_MARKS` (6) of them (map_view.gd:27).

**L6. A wave save can still seal every road for the next build phase.** Owner: sim-engineer (src/sim/battle.gd). Contract: ARCHITECTURE 4.4 and 5.6.

Where: the seal check (battle.gd:1716) uses `closed_cells()`, which leaves out broken gates, and every gate while `gates_open` is true (battle.gd:535 to 542). When the wave ends, every gate mends and closes (battle.gd:987 and 988). tests/save/test_load_limits.gd:142 asserts that such saves load.

Steps, campaign: take the round 1 L2 save (r1_l2 right after wave 1 starts, the saved level giving 2 gates, gates on both sockets) and mark one gate `broken`. It loads. 420 ticks later the wave ends, the build phase begins with both gates closed, and they seal. A save in that build phase is written, and the next launch refuses it and deletes the game. Campaign gates are not fixed, so the player could lift one first. `start_next_wave` does not check for a seal and answers `done`.

Steps, run: take run seed 3 at wave 7. Swap one pick for Iron Gate and rebuild the kept effects, so the N1 tie holds. Set `gates_added` to 2, and put fixed gates on the sealing pair (1, 6) and (5, 7), one of them broken. It loads. 561 ticks later the build phase is sealed, `move_gate` answers `fixed_gate`, and the next launch deletes the run. The next wave starts anyway (`start_next_wave` answers `done`). The same works with no broken gate and `gates_open` true, with no Gateless Night among the picks.

The mutation run found this twice on its own: at iterations 124 and 910 a mutated campaign wave save loaded, and the save made after playing on was refused with "gates: seal every road".

Why it matters: the L2 fix exists to refuse saves that leave the map sealed. This is the same outcome, one wave later. Same threat model as L1 and L2.

Fix: in both phases, run the seal check on every placed gate, broken or not, whatever `gates_open` says. In play the placed gates always come from a build phase, where placing or moving a gate never seals, so play never fails this. I counted it in the genuine play run: 0 of 11,361 saves would fail it, among them 670 with broken gates and 344 with `gates_open`. Optional: in a run, refuse `gates_open` unless a risk pick holds `gates_open`.

### Note

**N7. The crowd ceiling does not count what live creatures can still let out.** Owner: sim-engineer. Contract: ARCHITECTURE 5.6.

A Pumpkin Catapult with 4,000 Puffballs at 1 health stacked on one cell in its reach: one shot defeats them all, and 12,000 Puffs follow (peak 12,001, worst tick 137 ms). With 4,000 Old Tusks at 1,501 of 3,000 health instead, one shot starts 4,000 releases of 4 Dusk Moths. That gives 20,004 creatures for about 7 s of play, at 60 to 77 ms a tick (worst 167 ms) and 99 MB. It clears by itself as they reach the village. MapView adds one node per creature (ARCHITECTURE 9.3), and towers that hit flyers check all 16,000 of them. I did not measure the map. Suggestion: count each live or queued creature with what it can still let out, for example a Puffball as 4 and an Old Tusk that has not released as 5.

**N8. `MAX_SUMMONERS` holds only at load. A saved level's waves can bring more.** Owner: sim-engineer, with the architect for 2.4 and 5.6.

A saved level is checked only by `LevelData.check`. Its spawn bound counts splits but not bosses or Menders (level_data.gd:352 to 362). I loaded a campaign save under the real id r1_l2 whose level has a 55 cell road and 40 waves of 120 Grumblesacks at strength 1000. With two waves at a time it reached 4,268 creatures (worst tick 43 ms). By tick 100 the save the game would write was already one its own check refuses (101 creatures, nearly all Grumblesacks), so the next launch would delete it. The same route can bring 240 Menders, which is L5's second case. Suggestion: refuse a saved level whose waves hold more bosses or healers than any real level or pack. Or tie the saved level to the bundled one and the run map to its seed (the untied half of round 1's N1, Bart's call).

**N9. The guard test still misses some loaders and exits.** Owner: DM (tests/project/test_security_rules.gd). A scratch file in src/ passed it with `decode_var(0, true)`, `JSON.to_native(x, true)`, `ClassDB.instantiate`, `Expression`, `GDScript` `source_code`, `ProjectSettings.load_resource_pack`, `OS.shell_show_in_file_manager` and `OS.request_permissions`. So did a .tscn with an embedded GDScript that calls `decode_var`, and the header test skips .tscn files too. None of these is used anywhere in the repo today (`git grep`). Suggestion: add these words, widen the links rule (line 69) from `shell_open` to `shell_`, and refuse `type="GDScript"` sub-resources in .tscn and .tres files.

**N10. `check_apk.sh --release` passes values it does not know.** Owner: release-engineer (scripts/check_apk.sh). `debuggable_state` (line 161) calls anything but `=true` or `0xffffffff` false. Fed by hand, `(type 0x12)0x1` and a resource reference such as `@0x7f050001` both come out "false". Godot writes a plain boolean today, so this is hardening. Suggestions: in release mode accept only an absent attribute or `=false`. When release signing is set up (ask first), also fail an APK signed with the Android debug certificate.

**N11. build/forkline-debug.apk predates the round 1 fixes.** Owner: release-engineer. It was rebuilt at 12:34 on 2026-10-25, before 279500b, d8ccfde, aeed462, 91da93a and c5d36b8. Its compiled links.gd, battle.gd and run_session.gd differ from a fresh export of HEAD. It still passes check_apk.sh (exit 0). Rebuild it before the next install on the phone.
