## Observations (not rated)

1. **The score wall (GDD D-37, by design).** If the score is so close to 2^63 that even the smallest touching pair's points no longer fit, then:
   - `has_valid_move` still says play, so the offer does not open;
   - `can_join`, the joinable highlight and the preview still offer the chain;
   - `commit_chain` refuses it with `invalid_chain`.

   **Reproduction:** Board D with cells 35 and 36 at 2^53, score "9223372036854775807", format 2 with every free booster used.
   - In the App, the joinable cells from (0,7) are [(1,7)] and the preview reads 2^54.
   - The commit is refused, the phase stays PLAYING, and the offer never opens.
   - Hammer, Swap and Shuffle are usable at 2^53.

   From a 2^61 pair at score 0, 30 seeded runs out of 30 reached this state. The three I printed got there after 59, 63 and 64 chains, and in those three and in the App, Hammer was affordable. That is what GDD line 170 promises: such a score is at least 2^62, so Hammer, Swap and Shuffle are affordable and the run is never stuck.

   **Impact:** none for security. Only a hand edited save gets here, because real play never comes near 2^62 (D-37). The remaining gap is feedback. The player can drag a chain and see its result, lifts, sees nothing happen, and gets no offer pointing at the boosters. GDD line 172 says the joining rule and the move check must agree with the refusals, and for this one refusal they do not.

   **Owners:** lead-game-designer (D-04, D-15, D-37) and core-logic-dev, if the DM wants it changed. Two possible changes: let `can_join` and `has_valid_move` also check the score's room, or keep the rule and accept it as documented.
2. **On a hand made board the suggested rescue can spend every free booster on Shuffles that cannot help.**
   - **Setup:** after one Hammer on an all 2^62 board, 39 tiles of 2^62 remain plus one smaller tile.
   - Shuffle counts as able to act, because the board holds two different values. It is the suggested rescue (D-42), but no arrangement can ever make a move.
   - My driver followed the suggestion and spent all 17 free boosters that way.

   It ends normally, with no loop. Only a hand edited save gets here. **Owners:** lead-game-designer and boosters-dev, for awareness.
3. **A profile temp file with one bad field and no real profile gives defaults.**
   - **Setup:** no profile.json, and a profile.json.tmp whose best_tile is 99.
   - The new `load_profile` (save_service.gd line 261) deletes that temp file and loads defaults.
   - Round 1's code applied the valid parts.

   The game never writes such a file, and a missing real profile only happens in the Windows rename gap. So this needs two unlikely events together. **Owner:** ui-systems-dev, for awareness.
4. **The live viewport tap check can hang the suite or pass without checking.** tests/design/test_tap_input.gd line 126 runs scenes/design/tap_check.tscn through `OS.execute` (blocking, no time limit). I tried two injected errors in the scratch copy:

Term 2's last clause, "must not suggest that Bart Basi made or endorses the changes", reaches toward endorsement, which reads closer to 7(d) (publicity use of the authors' names) than to 7(c) (misrepresentation of origin). Section 7 lets a recipient remove a term that is not permitted. This is a wording point for Bart, not a security matter, and not legal advice. **Owner:** DM.

## What I checked and found clean

### 1. Save system (src/save/, read in full at ff167cf)

**Reading rules, unchanged and still clean.**
- JSON only, through `JSON.new().parse`.
- No str_to_var, bytes_to_var, bytes_to_var_with_objects, get_var, ConfigFile, ResourceLoader or load() in src/save/.
- File names are constants, and every file lives in the SaveService folder, which is user:// in the game.
- Limits before parsing: 1 to 65536 bytes, no NUL, nesting of at most 16.

**Format 2 hostile files through the real SaveService.** A driver in the session scratchpad wrote each run.json next to a good profile.json, each in its own user://sec2_save/case_NNN folder. 113 run cases: 98 refused and 15 accepted. Every load took 0.9 to 23 ms, and the profile stayed intact in all 113.

Refused, with the run discarded:
- **Damaged files:** round 1's set, rebased on format 2. Zero bytes, whitespace, cut off files, random bytes, 5 MB, 65537 bytes, 30000 nested arrays, 2000 nested objects, 17 levels inside free_used, the invalid UTF-8 trick, UTF-16, a NUL after valid JSON.
- **Wrong shape and bad values:** wrong shapes, bad cells, run_highest 63 or below the board, bad score strings, a bad snapshot, an unknown key, and 5000 keys.
- **free_used:** -1, 1 when 0 were earned, 0.5, 1.5, "0", null, true, false, 1e400, -1e400, NaN, Infinity, [0], {}, 9007199254740993, 2^63 minus 1 and 1e18. Also 2 with run_highest 2^14 (1 earned), 18 and 1e3 with run_highest 2^62 (17 earned), and a duplicate key whose last value is 99. So a file can never claim more free boosters than its run_highest earns.
- **best_at_start:** "-1", "", "007", "+5", " 5", "5 ", "1e3", "0x10", "9223372036854775808", 20 nines, an Arabic-Indic digit, a full width digit, an embedded NUL, a 60000 digit string, and the numbers 5, 5.0 and -1, null, true, ["5"] and {}.
- **Mixed format keys:**
  - format 2 missing free_used, missing best_at_start, or missing both;
  - format 1 with free_used, with best_at_start, or with both;
  - format 3 with format 2 keys, format 0, format "2" and format 1.5;
  - free_used inside the snapshot;
  - format 2 keys with a duplicate format key whose last value is 1.

Accepted, all valid by the format:
- both control files (format 2, and format 1, which loads with free_used 0 and best_at_start -1);
- exactly 65536 bytes;
- a UTF-8 byte order mark;
- format 2.0, and free_used 0.0 and -0.0 (both load as 0);
- free_used equal to the number earned (1 at 2^14, 17 at 2^62), and a duplicate free_used whose last value is 0;
- best_at_start "0", the maximum, or above the score. These only change whether the New best badge shows.
- run_highest 2^62 on a small board with free_used 0: 52 stars and 17 free boosters. A hand edited save can grant them, as it can set any record (round 1 observation 4). No security effect.
- a format 1 file with run_highest 2^62: 17 free boosters on load, as GDD 15.1 says.

Profile cases were unchanged in behaviour. A damaged or format 2 profile gives defaults, and the file is kept. A bad skin, best_score or best_tile falls back on its own. Run keys inside the profile are ignored. The run is untouched in every case.

**Write side.**
- save_run and queue_run both refuse a state with best_at_start -1, and the last good file stays.
- save_run refuses free_used 18 at 2^62 and free_used -1.
- The extremes round trip exactly: 2^62 tiles, score and best_at_start at 2^63 minus 1, free_used 17.
- A format 1 run resumed by GameSession takes the loaded Best Score as best_at_start and is written back as format 2 with exactly the nine format 2 keys.

**The temp wins rule (QA6-07).** Each case was loaded twice, by two fresh services, as two app starts.

The run file:
- A good run.json plus a complete newer temp loads the newer run, renames it into place, and leaves no temp file.
- A good run.json plus any of these temp files loads the good run and deletes the temp: half written; free_used 99; best_at_start -1; zero bytes; 5 MB; 30000 levels deep; holding a NUL; a top level array.
- A valid format 1 temp beside a format 2 run.json wins, because by the rule it is the newest.
- No run.json, or a broken or zero byte one, plus a valid temp recovers the temp. Plus a broken temp, neither loads and both files are deleted.
- A folder named run.json.tmp makes save_run fail and keeps the last good file. Same as round 1: only something with access to the app's private folder can make one.

The profile:
- A valid newer temp wins.
- A temp with one bad field, an unknown key, format 2, half written or 5 MB is deleted, and the real profile loads (observation 3 covers the case with no real profile).
- A temp with an unknown but well formed skin id counts as valid, and the App then falls back to the default skin, as in round 1.

**A crafted temp file grants nothing new.** It can only win when it passes every check, so it is no more powerful than writing run.json directly, which needs the same access.

**A stale temp cannot win.**
- Every write opens the temp file for writing, which empties it, before anything else. A failed write or check deletes it, and a successful rename removes it.
- So a temp file that passes the checks always holds the newest save.
- I found no path that leaves an older valid temp beside a newer run.json. The kill test below never left one in 80 rounds.
- After stale temp files for both files, save_run and save_profile left no temp file behind.

**Held files (another program holding a file open, Windows).** A probe confirmed what Godot does:
- While run.json is held, it cannot be deleted or renamed over, but it can be opened to write.
- While the temp file is held, a rename deletes run.json and then fails.

The cases:
- **run.json held while saving:** save_run reports false, the temp file holds the new run, and a fresh load returns it. After the release, the next save renames it into place.
- **The temp file held while saving:** run.json is gone and the temp holds the new run. A fresh load returns it. After the release, flush moves it into place.
- **delete_run while run.json is held:** it empties the file (0 bytes). Loads return nothing, during and after the hold, and the next load deletes the empty file.
- **A stuck rename, then delete_run, with run.json held:** the run does not come back.
- **A stuck temp, then delete_run, with the temp held:** the temp is emptied and the run does not come back.
- **The profile with profile.json held:** a fresh load returns the new best score, and after the release it is in place.
- **20 queued writes with run.json held:** `is_idle()` came back true after each failed rename, 141 ms of waiting in total, so the show gate cannot freeze the game on a failing disk. After the release and a flush, the newest of the 20 loads.

**Stress.** 600 random steps on one folder: save_run, queue_run with flush, delete_run, holding or releasing run.json, holding or releasing the temp file, and 98 restarts with a fresh service. After every restart the load returned exactly the last state saved, or nothing after a delete. 0 mismatches.

**Hard kills.** A second Godot process saved the run and the profile in a loop: save_run, queue_run, or queue_run with flush, in turn. The orchestrator ended it by its own PID (`OS.kill`) at a random 1 to 400 ms after its first save, then compared what loaded with the newest valid file on disk. 80 rounds, 0 bad. Files at the kill:

| Files | Rounds |
|---|---|
| run.json and its temp, plus profile.json | 38 |
| profile.json and its temp, plus run.json | 22 |
| No temp file | 12 |
| Only run.json.tmp: the Windows rename gap for the run | 4 |
| Only profile.json.tmp: the rename gap for the profile | 4 |

Whenever a temp file was valid, it was the newer file and it won.

**Save folder guard.** Still refuses `C:/Windows/Temp/...`, `res://`, `user://../x`, `user://a/../../x`, `USER://x`, `/tmp/x` and the empty string.
