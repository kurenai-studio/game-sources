01 / FOUNDATION

The Loop Owns Nothing But You

open: Program.cs · BreakoutGame.cs

The single most important thing to understand about MonoGame: it is a library, not an engine. An engine owns a world — a scene tree, an editor, objects that update and draw themselves — and calls your scripts when it feels like it. MonoGame is a library with a heartbeat: your executable starts, you construct one Game object, and Run() pumps a loop until you call Exit(). Nothing exists unless your code creates it; nothing appears on screen unless your code drew it this frame.

Program.csthe entire entry point
using var game = new Breakout.BreakoutGame();
game.Run();

The using var guarantees the window and GL context are torn down when Main exits — cleanup an engine would do invisibly, written out in plain sight.

The four lifecycle overrides

OverrideRunsYour job inside it
Initialize()once, after the graphics device existsnon-content setup — and base.Initialize() is what calls LoadContent()
LoadContent()oncecreate the SpriteBatch, load fonts / textures / sounds
Update(GameTime)every tick (60 Hz here, §02)read input, advance the simulation
Draw(GameTime)every frameredraw the entire world from scratch — nothing persists on screen between frames
GOTCHA

The base.* calls do real work. Delete base.Initialize() and LoadContent() silently never runs. These are not the polite-but-optional super calls of many frameworks — here base is load-bearing.

DESIGN NOTE

BreakoutGame is deliberately thin — it owns the window, the loop, the SpriteBatch and the virtual screen, then delegates to GameStateManager. It is also the only class nothing else references: the application shell knows about gameplay, gameplay never knows about the shell. Search the repo for BreakoutGame — it appears only in Program.cs. That property is worth defending in any codebase.

02 / TIME

Fixed Timestep & Delta — Why Both

open: BreakoutGame.cs (constructor, Update)

With IsFixedTimeStep = true (the default, stated explicitly in the constructor on purpose), MonoGame calls Update() on a fixed 60 Hz clock: the simulation ticks at a steady, predictable rate no matter how fast the machine renders, which is what keeps physics deterministic — the ball takes the same path on every PC. So why does every movement line still multiply by delta?

BreakoutGame.csextracting delta from GameTime
float dt = (float)gameTime.ElapsedGameTime.TotalSeconds;
_states.Update(dt, _input);

Two reasons. First, when a frame runs long, MonoGame runs catch-up Updates, and ElapsedGameTime stays honest about real elapsed time. Second, position += velocity * dt keeps working if the tick rate ever changes — hardcoding per-tick speeds couples gameplay to the clock, and "the ball moves 5 px per Update" becomes a bug the day the game runs at 144 Hz.

GOTCHA

ElapsedGameTime is a TimeSpan, not a float. The cast (float)…TotalSeconds is the idiom; forget it and the compiler reminds you, use .Seconds (an int!) and it silently breaks.

WORTH KNOWING

Many frameworks hand you a bare delta float. MonoGame hands you a GameTime object carrying both ElapsedGameTime (your delta) and TotalGameTime (time since launch — handy for pulsing effects, see PowerUp.Draw which tracks its own age instead).

03 / RENDERING

SpriteBatch & the 1×1 Pixel Trick

open: Source/Systems/SpriteBatchExtensions.cs · any Draw method

All 2D drawing goes through SpriteBatch: call Begin(), queue textured quads, call End(), and the batch submits them to the GPU efficiently. There is no retained canvas — and there is also no draw_rect. MonoGame draws textures, full stop. The universal workaround: a one-pixel white texture, stretched and tinted.

Source/Systems/SpriteBatchExtensions.csthe whole trick
_pixel = new Texture2D(device, 1, 1);
_pixel.SetData(new[] { Color.White });

public static void DrawRect(this SpriteBatch spriteBatch, Rectangle rect, Color color)
    => spriteBatch.Draw(_pixel, rect, color);

The GPU does not care that the source texture is one pixel — sampling it at any size yields flat white, and the tint color does the rest. Every paddle, brick, ball, particle and letterbox bar in this game is that one texture. The whole game ships with zero image files.

GOTCHA

SpriteBatch.Begin() defaults to linear filtering. Scale anything up and it smears. This project passes samplerState: SamplerState.PointClamp at both Begin sites (world pass and present pass) — that's the "crisp pixels" switch.

MENTAL MODEL

In a scene-graph engine, a rectangle node persists in a tree and draws itself forever. Here, if Draw doesn't issue the call this frame, the thing does not exist on screen. Drawing is a verb, never a noun.

DESIGN NOTE

Premultiplied alpha: Color.Black * 0.65f (the game-over dim layer) and p.Color * life (particle fade) multiply RGB and A together, which is what SpriteBatch's default blend state expects. Setting only the alpha channel by hand is the classic "why does my fade look wrong" bug.

04 / ASSETS

Two Ways to Load a Thing

open: Content/Content.mgcb · Content/Fonts/Hud.spritefont · Source/Systems/LevelLoader.cs · Breakout.csproj

This project deliberately demonstrates both asset routes, because choosing between them is a real decision you'll make on every MonoGame project.

Route 1 — the Content Pipeline (the font)

The pipeline compiles assets at build time into .xnb binaries: textures into GPU formats, fonts into rasterized glyph atlases. Content.mgcb is its plain-text manifest (the MGCB Editor is just a GUI over it). Asset names are path-without-extension relative to Content/:

BreakoutGame.csloading a compiled asset
_font = Content.Load<SpriteFont>("Fonts/Hud");
GOTCHA

There is no "just draw text" in MonoGame. Hud.spritefont is an XML description (font family, size, character range) that the pipeline bakes into a glyph atlas. No SpriteFont, no DrawString.

Route 2 — runtime loading (the levels)

The level grid gains nothing from being compiled, and keeping it plain text means editing a level requires no rebuild. So it bypasses the pipeline entirely:

Source/Systems/LevelLoader.csplatform-safe runtime file access
using Stream stream = TitleContainer.OpenStream("Content/Levels/level01.txt");
using var reader = new StreamReader(stream);
GOTCHA

The pipeline only copies what it builds. Runtime-loaded files need their own CopyToOutputDirectory entry in the .csproj — without it the game works on your machine right up until you wonder why a fresh clone crashes.

MENTAL MODEL

Every big engine has an asset import step; most hide it behind drag-and-drop and a cache folder you never open. The Content Pipeline is that step made visible and put under your control — and TitleContainer is the escape hatch for files you want raw.

05 / INPUT

Input Is a Snapshot, Not an Event

open: Source/Systems/InputHelper.cs

MonoGame has no input events, no signals, no action map. Keyboard.GetState() returns a snapshot of which keys are down right now, and that's all you get. "Is the key down" is trivial. "Was it just pressed" requires memory:

Source/Systems/InputHelper.csthe current/previous pattern
public void Update(VirtualScreen virtualScreen)
{
    _previousKeyboard = _keyboard;
    _previousMouse = _mouse;
    _previousGamePad = _gamePad;
    _keyboard = Keyboard.GetState();
    _mouse = Mouse.GetState();
    _gamePad = GamePad.GetState(PlayerIndex.One);
    // ...
}

// the heart of WasActionJustPressed, for each key bound to the action:
if (_keyboard.IsKeyDown(keys[i]) && _previousKeyboard.IsKeyUp(keys[i]))
    return true;

Down now + up last frame = pressed this frame. That two-line comparison is exactly what any engine's built-in "just pressed" query does internally. Every polling-based codebase grows this wrapper; the discipline is calling Update() exactly once per tick, before anyone reads input.

DESIGN NOTE

MouseX returns virtual coordinates (§08 transform applied) so gameplay never learns the window size exists — but MouseMoved compares raw window positions, because the virtual transform rounds to ints and that rounding could register phantom movement. Two coordinate spaces, each used where it's correct.

WORTH KNOWING

There is also no action map — no built-in layer that turns "the jump action" into "Space or W or gamepad A". This project builds one on top of this same helper: ActionMap is a dictionary from GameAction to Keys[], and gameplay only ever asks IsActionDown / WasActionJustPressed — no gameplay file names a key. It began as an Appendix C exercise; its commit shows how little the whole layer costs.

06 / SIMULATION

AABB Collision & the Paddle That Aims

open: Source/Systems/CollisionHelper.cs · Source/States/PlayingState.cs · Source/Entities/Ball.cs

No physics engine, no collider components, no collision events — just Rectangle.Intersect and arithmetic. The interesting question in Breakout is never whether the ball hit a brick, but which side it hit, because that decides which velocity component flips.

Minimal penetration

Source/Systems/CollisionHelper.csthe shallower overlap axis is the impact axis
Rectangle overlap = Rectangle.Intersect(moving, target);
if (overlap.IsEmpty)
    return HitSide.None;

if (overlap.Width < overlap.Height)
    return moving.Center.X < target.Center.X ? HitSide.Left : HitSide.Right;

return moving.Center.Y < target.Center.Y ? HitSide.Top : HitSide.Bottom;

If the overlap rectangle is wider than it is tall, the ball came in vertically, and vice versa. Relative centers disambiguate which of the two sides. After detection, CollisionHelper.ReflectAndSeparate pushes the ball out by the overlap and sets the velocity sign (rather than negating it) — setting is idempotent if a collision ever resolves twice. It lives in the helper, not in a playing state, because all three rule sets share it: how a ball leaves a brick is physics, not rules.

DESIGN NOTE

This discrete test is only safe because the numbers say so: max ball speed 560 px/s ÷ 60 Hz ≈ 9 px per tick, against 20 px bricks — tunneling is impossible. Crank the speed past ~1200 px/s and you'd need a swept test. Professional code isn't code without simplifications; it's code whose simplifications are justified and written down.

The aiming paddle — the game-feel heart

Source/Entities/Ball.cswhere you hit decides where it goes
float offset = (Position.X - p.Center.X) / (p.Width / 2f);
offset = MathHelper.Clamp(offset, -1f, 1f);

float angle = offset * MaxBounceAngle;   // 60° from vertical at the edge
Velocity = new Vector2(MathF.Sin(angle), -MathF.Cos(angle)) * Speed;

The exit angle ignores the incoming angle entirely — it's a pure function of where the ball struck the paddle. Center: straight up. Edge: 60°. This single mapping turns the paddle from a wall into an aiming device, and it's the knob of the whole genre. Also note the two anti-stick guards: paddle bounce only triggers while the ball descends, and brick resolution handles one brick per tick.

TRY IT

Change MaxBounceAngle to MathHelper.Pi / 6f (30°) and play a round. Then try 75°. Feel how the game changes from "passive" to "twitchy" with one constant — that's game feel living in a single number.

07 / ARCHITECTURE

States Without Scenes

open: Source/States/*.cs · Source/GameSession.cs

Ready → Playing → LifeLost → GameOver, with Pause and LevelCleared joining the loop where needed. Engines ship a scene system or a state machine node for exactly this; MonoGame ships neither, so you write the pattern yourself — about 30 lines — and in exchange you see exactly what a "screen change" is: swapping which object gets the Update and Draw calls. Two refinements worth tracing: PauseState keeps the state it interrupted and swaps it back without re-running Enter(), and the FreezesEffects flag lets pause stop even the particles every other state animates.

Source/States/GameStateManager.csa scene changer is just a field assignment
public void ChangeState(GameState next)
{
    _current = next;
    next.Enter();
}

public void Update(float dt, InputHelper input)
{
    if (!_current.FreezesEffects)
        Session.UpdateEffects(dt); // effects run in (almost) every state
    _current.Update(dt, input);
}

The crucial split: data vs. behavior

GameSession owns the world — paddle, balls, bricks, score, lives, level index, particles. States are modes of operating on that world. That's why the ball sits frozen mid-air on the game-over screen and the HUD stays visible during the life-lost flash: switching states never copies, rebuilds, or hides the world. "New game" is one line: Session = new GameSession(mode).

Rule sets are states too

The payoff of that split arrived with Classic 1976 mode — the original arcade rules, reconstructed from Atari's operation manual, living alongside the modern game. No if (classicMode) sprinkled through gameplay: the entities stay shared and dumb, and a "mode" is simply which state objects drive them — ClassicReadyState/ClassicPlayingState instead of ReadyState/PlayingState, chosen in one place (GameStateManager.CreateServeState). Read the two playing states side by side: discrete four-step speeds vs. a continuous ramp, four fixed paddle exits vs. continuous aiming, one-brick-per-trip vs. chew-through — the diff between two files is thirty years of design history. The pattern got its stress test when Super Breakout (1978) arrived as three rule sets at once: the physics the sequel's games share live in one abstract SuperPlayingState, and each variant (Double, Cavity, Progressive) is a subclass small enough to read in a sitting — what varies hangs off five virtual hooks. TitleState is the other lesson: the first state that exists before a session does, which is exactly what forced StartNewGame to take parameters (mode, starting level) instead of assuming them.

MENTAL MODEL

Engine scene switching usually destroys the old scene — which is why carrying a score across screens pushes you toward global singletons. Here persistence is the default and you opt out by constructing fresh, which is the less bug-prone direction.

DESIGN NOTE

Notice what this project deliberately does not have: no ECS, no DI container, no event bus. Breakout doesn't need architecture; it needs clarity. Knowing how much structure a game does not need is a professional skill.

08 / PRODUCTION RENDERING

The Virtual Screen

open: Source/Systems/VirtualScreen.cs · BreakoutGame.cs (Draw, OnClientSizeChanged, ToggleFullscreen)

The single most instructive piece of "real project" infrastructure. Gameplay thinks in 800×480 forever; the window can be anything. The trick is a two-pass draw:

BreakoutGame.csrender to target, then present scaled
// Pass 1: the whole game, into the 800x480 render target.
_virtualScreen.BeginDraw();          // SetRenderTarget(target)
GraphicsDevice.Clear(ClearColor);
_spriteBatch.Begin(samplerState: SamplerState.PointClamp,
                   transformMatrix: _states.Session.Shake.TransformMatrix);
_states.Draw(_spriteBatch);
_spriteBatch.End();

// Pass 2: the render target onto the real back buffer, letterboxed.
_virtualScreen.Present(_spriteBatch); // SetRenderTarget(null) + draw scaled

A RenderTarget2D is a texture you can draw into; passing null to SetRenderTarget means "the actual back buffer". DestinationBounds scales by the smaller axis ratio (so the image always fits) and centers — the leftover area is the black letterbox bars.

The inverse problem: the mouse

The OS reports the mouse in window pixels; the game thinks in virtual pixels. Every scaled-rendering setup must apply the inverse transform — VirtualScreen.WindowToVirtual — exactly once, in one place (InputHelper.Update). Forget this and your paddle drifts away from the cursor the moment someone resizes the window.

MENTAL MODEL

In most engines this whole section is one project setting with a name like "stretch mode: keep aspect". Building it by hand once means that setting will never be magic again — and you'll know exactly why mouse coordinates go wrong whenever scaled rendering is misconfigured, in any engine.

GOTCHA ×2

1. DesktopGL does not resize the back buffer when the user resizes the window — OnClientSizeChanged does it manually, with a re-entrancy guard because ApplyChanges() re-fires the event. 2. Fullscreen here is borderless (HardwareModeSwitch = false): instant, flicker-free, alt-tab friendly. Exclusive mode only earns its pain when you need every millisecond of latency.

09 / GAME FEEL

Juice: Shake, Sparks, Square Waves

open: Source/Systems/ScreenShake.cs · ParticleSystem.cs · AudioBank.cs · MusicPlayer.cs

Trauma-based screen shake

Impacts add trauma (0–1, capped); displayed intensity is trauma²; trauma decays linearly. The squaring is the magic: small hits barely register, big hits kick, and stacked hits compose naturally. The shake is applied as a translation matrix in SpriteBatch.Begin — the world draws shifted, the world's data never moves.

Particles without garbage

Source/Systems/ParticleSystem.csstructs: read, modify, write back
for (int i = 0; i < _particles.Count; i++)
{
    Particle p = _particles[i];   // List<T> indexer returns a COPY of a struct
    p.Velocity.Y += Gravity * dt;
    p.Position += p.Velocity * dt;
    p.Age += dt;
    _particles[i] = p;            // ...so write it back
}

Particles are structs so emitting hundreds allocates nothing the GC must chase. The copy-mutate-writeback dance is the price; C# won't let you mutate a struct inside a list in place, and knowing why (the indexer returns a copy) inoculates you against a whole family of "my changes don't stick" bugs.

SFX from raw PCM

SoundEffect happily accepts a byte buffer of 16-bit PCM — so AudioBank synthesizes every sound at startup: square waves with a 2 ms attack (kills the click) and linear decay, frequency sweeps for the life-lost fall, the power-up rise and the short zip that announces an arcade speed-ladder step. The normal route is .wav files through the pipeline; this is the "asset-free retro" route, and it teaches what a sound is.

GOTCHA

SoundEffect is for fire-and-forget polyphonic SFX. Music is a different API entirely: Song + MediaPlayer, streamed, one at a time. Loading music as a SoundEffect decompresses the whole file into RAM. Don't mix them up.

Music is nothing but the handle

MusicPlayer pushes the PCM trick one step further: eight bars of Am–F–C–G — square bass, 25%-duty arpeggio, noise hats, mixed by literal addition into one 16-second buffer — played through a SoundEffectInstance. That's the half of the audio API the SFX never needed: Play() returns no handle, so a fired SFX can't be stopped or re-volumed; CreateInstance() returns the handle you keep — IsLooped, Pause(), and a live Volume, which is how the pause screen ducks the track instead of stopping it. (A real three-minute track would still be Song + MediaPlayer — whole-file PCM in RAM only works because the loop is seconds, not minutes.)

TRY IT

Press F3 in game and watch the particle count while you break a brick. Then open PlayingState.HandleBrickCollision and raise the emit count from 18 to 200 — watch the count spike and the FPS not care. That's the struct pool earning its keep.

10 / HABITS

Production Habits Hiding in Small Diffs

open: GameSession.DrawHud · ScreenShake.Update · BreakoutGame.Update · Source/Screen.cs

HabitWhereThe lesson
GC awareness GameSession.DrawHud $"SCORE {Score}" allocates a string. At 60 fps that's garbage the collector must sweep — so the HUD caches and rebuilds only when the value changes. Contrast: DebugOverlay allocates every frame on purpose and says why (debug tool, off by default). Same operation, two judgment calls.
Pure getters ScreenShake The RNG rolls once per tick in Update(); TransformMatrix just reads stored state. A getter returning different values on consecutive reads means two consumers in one frame silently disagree — a real bug class, not style pedantry.
Focus pause BreakoutGame.Update MonoGame keeps calling Update when the window is unfocused — pausing is your job. The IsActive early-out means nobody loses a ball while alt-tabbed. base.Update still runs for framework housekeeping.
Dependency direction Source/Screen.cs Screen constants used to live on the Game class, so a Brick depended on the application shell to learn the screen width. Now they're plain constants in their own type, and the shell is the only class nothing references.
Graceful degradation AudioBank.Initialize No audio device? Catch NoAudioHardwareException, leave the properties null, and play through ?.Play() or a null-tolerant PlayVaried (which rolls its pitch before the null check, so the simulation's RNG draws never depend on hardware). The game runs silent instead of crashing. MusicPlayer.Initialize makes the same promise: a null instance turns every music call into a no-op.
Honest naming BreakoutGame.cs The template's Game1 is a placeholder, not a name. (Stardew Valley famously shipped with it — nothing breaks; it's still the first thing professionals rename.)
STILL OPEN — ON PURPOSE

Two known smells are left as discussion pieces: the static AudioBank/SpriteBatchExtensions (convenient at this scale; the alternative is passing them as dependencies — ask to see the comparison) and LevelLoader's total trust in well-formed files (production code would validate and report line numbers). Knowing a tradeoff exists beats pretending the code is finished.

11 / DESIGN HISTORY

Two Manuals, Three Games

open: Source/Systems/ClassicRules.cs · SuperRules.cs · ClassicWall.cs · SuperWall.cs · the three playing states

The arcade modes are not "retro flavored" — they are reconstructions. Classic plays the rules in Atari's 1976 Breakout operation manual; Double, Cavity and Progressive play the sequel's 1978 manual (TM-118). Each manual became one rules file and one wall file, written so the code reads like the document it came from — and the diff between the three playing states is two years of design history in a split view:

Breakout 1976Super Breakout 1978Modern (house rules)
Ball speeds 4 discrete steps: 4th hit, 12th hit, instant max on orange/red 5 discrete steps: 4th/8th/12th paddle return, instant max on a 5/7 brick continuous ramp, +8 px/s per brick
Paddle rebound 4 fixed exits by struck quarter, tightening as speed rises the same 4-exit law, one rung longer continuous angle from hit position (§06)
Brick law one brick per trip — a dis-armed ball rebounds, the brick survives pass-through — an unreturned ball sails through; after a kill it bores for four rows (the ball draws translucent while immaterial) chew through everything; multi-hit tiers
Half-paddle penalty on breaking out behind the wall, for the rest of the volley on touching the top boundary, until the next serve only as the debris hazard's timed shrink
Serve materializes mid-screen, already falling at you launched off the paddle, aimed cone
Scoring by row, 1/1/3/3/5/5/7/7 — exactly two walls, 896 maximum row (or zone) value × balls in play; endless walls tier × 10; power-ups, multiball
Source/Systems/ClassicRules.csfour exits, and never a vertical ball
float degrees = MathF.Abs(offset) < 0.5f
    ? InnerAngles[speedLevel]   // inner quarters: steep
    : OuterAngles[speedLevel];  // outer quarters: wide

// A dead-center hit still exits at the inner angle — to the right, by
// convention. Math.Sign would return 0 and make the ball vertical,
// which the original hardware never allowed.
float side = offset >= 0f ? 1f : -1f;

That second half is the 1976 manual's strangest law: the ball is never allowed to travel exactly perpendicular to the paddle, the bricks, or any boundary. The reason is mechanical, not aesthetic — a vertical ball over a gap bounces forever without the player, and the game plays itself. Forty-nine years later the same law protects this codebase from the same softlock.

METHOD

The manuals state laws, but rarely numbers: the rebound figure is a diagram with no angles, and "hit" is never defined for the speed-up counters. Every reconstructed value is flagged as such in the rules files, with the chosen reading defended ("we count destroyed bricks"; the 1978 file counts paddle returns — both defensible) and the price of certainty written down (cycle-exact values would need the TTL schematic). That is the transferable habit: name your sources, flag your guesses, record what a better answer would cost.

DESIGN NOTE

The sequel's premise is "more balls": Double serves two for one credit, Cavity frees captives into play, and scores multiply by balls in the playfield — but only the served ball costs a serve when lost. Watch SuperPlayingState identify the life-bearer by reference (ball == _serveBall): no flag on the Ball class, because "which ball matters" is 1978 law, not a property of balls.

TRY IT

Play one serve of Classic, then one of Modern. The 1976 paddle routes (four exits, pick a lane); the modern paddle aims (continuous angle). Then open ClassicPlayingState and PlayingState side by side — every feel difference you just noticed is a visible diff.

12 / GENERATION

Boards from a Seed

open: Source/Systems/BoardGenerator.cs · LevelLoader.cs · GameSession.cs (GenerateBoard)

The level select's RANDOM slot plays endless generated boards — and the generator never touches a Brick. It emits the same plain-text grid the .txt levels use, and LevelLoader.Parse cannot tell (and never learns) whether its text came from a file or from code. The format is the contract; a generator is just another producer of it. The output is even legal to paste into a level file if a generated board turns out to be a keeper.

Source/Systems/BoardGenerator.csdifficulty as four small curves
int rows = Math.Min(5 + boardNumber / 2, 8);
int tierCap = Math.Min(2 + boardNumber / 2, 5);
int tierBudget = 35 + boardNumber * 10;
float unbreakableDensity = Math.Min(0.012f * boardNumber, 0.10f);

Three decisions carry the design. A budget, not a fill chance: the generator spends hit-points brick by brick, which bounds the board's total work — "how long does a board take" scales predictably even though every layout differs. Mirroring: only the left half plus the center column is generated; the right half is a reflection. Humans forgive randomness far more readily when it has structure — and symmetry halves the space the generator can get wrong. Unbreakables last: they fill leftover holes after the budget is spent, so they are obstacles to route around, never a substitute for bricks to clear — no board can generate unwinnable.

GOTCHA

Random placement stalls once the grid fills: the spend loop pairs its budget with a stall counter instead of trusting luck. Every loop fed by randomness needs an exit that does not depend on the dice — while (tierBudget > 0) alone is a hang waiting for the right seed.

DESIGN NOTE

All randomness comes from the caller's Random — in play, the session's seeded stream (§13). That one parameter is what makes generated runs replayable: the replay re-seeds the same stream, so it re-rolls the same boards. The tests pin exactly the properties everything else relies on: determinism, the format contract, mirroring, and winnability, swept across 50 seeds × 15 boards.

TRY IT

Set unbreakableDensity's cap to 0.5f and play a few RANDOM boards — feel how obstacles stop being seasoning and start being the dish. Then run dotnet test: the winnability sweep still passes, and knowing why (unbreakables only fill leftover holes) is the lesson.

13 / DETERMINISM

The Run Is a Pure Function

open: Source/Systems/Replay.cs · InputSnapshot.cs · Source/States/GameStateManager.cs · GameSession.cs (Seed, Rng)

Replay.cs is twenty-odd lines, and stores nothing about the world: no ball positions, no scores, no events. A replay is a mode, a start level, an RNG seed, and one input frame per simulation tick — because given those, the run is a pure function. Press R on the game-over screen and the game does not rewind; it re-simulates, feeding the recorded frames through the very states that consumed them live.

Three habits make that possible, each cheap on its own: the fixed timestep (§02), so tick N means the same amount of time in every run; one named Random — new Random() was always going to be "random from some seed", and naming that seed is the one-line change that turns random into reproducible; and all per-tick gameplay input behind one snapshot type:

Source/Systems/InputSnapshot.csthe whole replay format is "keep these in a list"
// Only the actions the simulation reads are recorded. Everything else —
// Pause, the menus, the shell shortcuts — deliberately stays live during
// playback: the viewer can still pause, rebind, or quit the *movie*
// without those presses ever having been part of the *run*.
private static readonly GameAction[] RecordedActions =
{
    GameAction.MoveLeft, GameAction.MoveRight, GameAction.Launch,
    GameAction.P1MoveLeft, GameAction.P1MoveRight,
    GameAction.P2MoveLeft, GameAction.P2MoveRight,
};

The alignment rule is one flag: GameState.IsSimulation. The recorder keeps one frame per simulation tick; the player feeds one back per simulation tick; the two streams stay aligned exactly because both sides agree on which ticks count. Pause is the instructive case — its ticks are not simulation, so the recorder's pauses vanish from the movie and the viewer can pause the movie at will, both for free, from one bit.

GOTCHA

Almost for free. The pause-entry tick is the trap: the state transitions and returns without simulating, but the manager has already spent that tick on the tape — recorded a frame the run never simulated, or consumed one that never ran. One tick of drift, compounding forever after. GameStateManager.Update ends by un-spending such a tick (pop the frame / rewind the index); the commit that added it tells the debugging story. Off-by-one is the native bug class of every tape format.

THE INVARIANT

Everything stochastic in a run draws from Session.Rng — launch angles, drop rolls, SFX pitch, screen shake, generated boards — so the seed reproduces all of it. The corollary with teeth: RNG consumption must never depend on output devices. AudioBank.PlayVaried rolls its pitch before its null check, so a machine with no sound card consumes the identical stream. Determinism is less a feature than a discipline about who may roll dice, and when.

WORTH KNOWING

This same machinery — seed + inputs, re-simulate — is how arcade attract modes, fighting-game replays, RTS lockstep netcode and desync bug reports all work. "Record causes, re-derive effects" scales from these 26 lines to shipped engines unchanged.

TRY IT

14 / POST-PROCESS

Shading the Whole Frame

open: Content/Shaders/Crt.fx · Source/Systems/VirtualScreen.cs (SetCrtEffect, Present)

A post-process wants exactly one thing: a moment when the whole frame is a single texture. The virtual screen (§08) created that moment — the present draw — so the CRT pass costs one Effect on one draw call, shading every pixel of the frame. F9 toggles it, because any effect that changes the entire image must be the player's choice.

Crt.fx is the Content Pipeline's other major asset type: HLSL source in, compiled platform blob out, at build time. For DesktopGL the source is translated to GLSL by MojoShader — but the first step runs Direct3D's shader compiler, which is Windows-only, which is why effect builds on Linux run it under Wine (the CI workflow shows the exact recipe). At runtime, Content.Load<Effect> just uploads the blob.

Content/Shaders/Crt.fxmask and scanlines, branchless
// Past the curved edge there is no image — mask to black. step() instead
// of an if/discard: branchless is the native dialect of pixel shaders.
float inside = step(abs(centered.x), 1.0) * step(abs(centered.y), 1.0);

// Scanlines: cos(pi * row) alternates sign every virtual row. Using
// VIRTUAL rows keeps the lines locked to game pixels at any window size.
float wave = 0.5 + 0.5 * cos(uv.y * VirtualSize.y * 3.14159265);
color.rgb *= 1.0 - ScanlineStrength * (1.0 - wave);

The curvature is the classic cheap barrel: push each sample point outward in proportion to its squared distance from center, and the image bows inward at the edges — curved glass. The vignette rides the same r²: corners sit furthest from the electron gun, so they get both the bend and the dimming.

DESIGN NOTE

The technique compiles a pixel shader only — SpriteBatch's own vertex shader stays bound, which is exactly what a SpriteBatch post-process wants. And the tuning parameters are set once in SetCrtEffect, not per frame: Effect parameters persist on the object, so you never re-send what never changes.

GOTCHA

Post-process strength is resolution-relative. At the default window size the game presents at exactly 1×, where the scanline period is a single physical pixel — a value that looks like gentle phosphor at 2× reads as a dark comb at 1×. This repo's strength was halved for exactly that reason; tune yours at the size players actually use.

TRY IT

Set Curvature to 0.4f in SetCrtEffect for a fishbowl, then 0f for flat glass with scanlines only. One uniform each — that immediacy is why post-processing is the highest juice-per-line system in the repo.

THE SEAM LESSON

HighScores.Record touches a real file under ApplicationData — a test must never do that (it would corrupt your actual scores, and CI machines shouldn't write profile data at all). So the pure ranking core exists as its own method, InsertScore, and the tests exercise that. When code is hard to test, the professional move is usually a seam — split the decision from the disk — not a mocking framework.

WHAT'S DELIBERATELY UNTESTED

States, draw code, feel. They change for design reasons, and a test that breaks on every design change teaches a team to delete tests. Play-testing is testing too — with the right oracle for the job: a human who can feel that the paddle went mushy. The skill is knowing which oracle each behavior needs.

WORTH KNOWING

CI runs the suite on Windows and Ubuntu, plus a dotnet format gate — the README badge is green because checks run, not because someone says so. A learning repo earns trust the same way a shipping one does.

APPENDIX C

Where to Go Next

The original seven exercises that lived here — second level, pause state, multiball, pitch variation, integer scaling, ball trail, action map — are now implemented in the codebase, one commit each. That makes the git history a second study guide: git log --oneline is the index, and each diff shows exactly how much (or little) one real feature costs. Read the multiball commit in particular to watch a single-to-many assumption ripple through every consumer. From the round below, music has since joined them (the asset-free variant: a synthesized chip-tune loop on a looping SoundEffectInstance, MusicPlayer.cs), and so has the title screen — with mode select on top of level select, because it arrived together with Classic 1976 mode: the original arcade rule set, reconstructed from Atari's operation manual, running as a parallel pair of states (see §07 and ClassicPlayingState.cs).

The second round is now implemented too, one commit each (2026-06-10): brick entrance (tween without a tween library), gamepad support (one more dictionary, zero gameplay changes — the action layer's promise, kept), the rebinding screen (poll GetPressedKeys() diffs; note the CapturesAllInput flag that keeps Esc from quitting mid-bind), high scores (read-only TitleContainer vs. a real writable path under ApplicationData), and local co-op (the paddle's turn for the multiball treatment: Session.Paddle → Session.Paddles).

From the third round, the Super Breakout variants are now implemented (2026-06-10): Double, Cavity and Progressive, reconstructed from the sequel's operation manual (TM-118) the way Classic was from the 1976 one. The stress test paid off — the three games share one abstract SuperPlayingState (five-speed ladder, the pass-through rule, shrink on top contact, score × balls in play) and differ only in a subclass each. Two entity "assumptions" fell on the way, both worth reading: Brick lost "bricks never move" (Progressive scrolls the wall and re-prices it by screen zone), and Paddle's row became constructor data (Double stacks two on one set of controls, one of them one-sided — an effect of the plain rule "a rising ball never meets a paddle"). §11 lays the three rule sets side by side.

The rest of the round is now implemented too, one commit each (2026-06-10), closing the appendix. Falling debris rode the PowerUp pipeline with the sign flipped — the spawn/fall/catch machinery never knew it was carrying prizes, so the hazard is one enum member, one switch arm, and an inverted look (dark center, ember edge, tumbling silhouette). The replay system is the determinism lesson made executable: name the Random seed, keep one InputSnapshot per fixed 60 Hz tick, and a whole run becomes a pure function you can re-run from the game-over screen (R) — note in GameStateManager how little machinery "playback" really is, and how pause stays live on both sides because its ticks were never part of the run (§13 walks the whole contract, off-by-one trap included). Procedural boards (the RANDOM slot in level select) cash in the level format a second time: LevelLoader split into Load/Parse, and BoardGenerator is just another producer of the text the parser already reads — drawing from the seeded session stream, so replays re-roll identical boards (§12 has the design). And the CRT shader opens the pipeline's other asset type: Crt.fx compiles at build time (on Linux, via Wine — see the CI workflow) and applies at the single draw where the whole frame is one texture, VirtualScreen.Present. F9 toggles it; §14 reads the shader line by line.

When you've read everything: delete a system — the shake, the particles, the speed ramp — run the game, and feel what's missing. Then put it back. That's the fastest way to convert read knowledge into owned knowledge.
