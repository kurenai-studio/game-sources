[Blueprint](../../blueprint.md) §7 M4.1 owns scope and exit gate; [M4 design](2026-11-03-m4-combat-design.md) owns the rules this changes; [M4 plan](../plans/2026-11-03-m4-combat.md) "Code anchors and pitfalls" applies unchanged.

## Intent

Fix the five notes from the first M4 playtest (2026-11-03) so the skirmish plays closer to Zero Hour. User's priority: **stay close to the real game going forward**; the current compact map is acceptable for this milestone. Success: an early raid on the opponent's base gets answered, production never stalls, and every on-screen object can be inspected.

Non-goals: bigger map (M6), AI moods (deferred to M8, see below), new units, fog, retaliation-when-hit beyond the scan rule, Zero Hour exit-path geometry, multiplayer. Anti-goal: an opponent made "active" by a hand-tuned rule with no source basis, or a benchmark that passes because a budget moved.

## Approaches

- **A. One milestone, simulation first (chosen by user).** Task 1 measures the cost of idle scan and rally moves against the [performance ledger](../../reference/performance.md); then simulation changes, one scenario recalibration, presentation, one exit gate.
- B. Split into presentation-only M4.1a and simulation M4.1b: earlier visible wins, but double exit-gate cost for about a tenth of the work.
- C. Opponent-only scan in the opponent script: cheaper and safer on the benchmark, but the human side behaves unlike Zero Hour. Rejected; it is the fallback to bring to the user only if Task 1 shows A cannot meet budget.

## Simulation changes (change replay traces)

### 1. Idle target scan (shared combat rule, both sides)

Zero Hour source `0a05454`: idle units (`AIIdleState::update`) and attack-move (`AIAttackMoveToState::update`, `AIStates.cpp:3641`) call `getNextMoodTarget` (`AIUpdate.cpp:4495`), whose search radius is `getAdjustedVisionRangeForObject(obj, OWNERTYPE | MOOD)` (`AI.cpp`): vision range × guard-outer modifier by controller. Retail root `INIZH.big` (pinned SHA-256, see [installation](../../reference/installation.md)), `AIData.ini`: `GuardOuterModifierHuman = 2.2`, `GuardOuterModifierAI = 1.333`; `AmericaInfantryRanger VisionRange = 100`, `AmericaTankCrusader VisionRange = 150` (equal to their weapon ranges; 4 and 6 cells at 25 units per cell).

Rule: a unit in `guard` or `attack_move` with no valid target acquires the nearest enemy unit or building (existing `_targets`/`_nearest` candidates and tie-break; collectors excluded as today) within **vision × controller modifier**: human infantry 8.8 / tank 13.2 cells, AI infantry 5.332 / tank 7.998 cells. Today's in-range acquisition is the special case radius = weapon range, so in-range behaviour is unchanged. If the target is outside weapon range, the unit moves to a firing cell using the existing `_firing_cell`/held-cell logic and fires when in range, **without leaving its mode** (my call: `guard`/`attack_move` stay the mode; `attack_move` keeps `combat.goal`). The scan radius applies to acquisition only: the target is kept until it dies, is removed or changes owner (user ruling 2026-11-03, from source: `AIAttackState::update` in `AIStates.cpp` ends only on victim death, non-enemy or ammo/weapon loss, and OpenRA `AttackMoveActivity` commits to the attack activity once a target is found; a radius drop made `attack_move` units oscillate at the edge); the unit then stays where it stands in `guard`, or `attack_move` re-paths to `combat.goal` and resumes its leg. A `move`, `stop`, `attack` or `attack_move` command issued during a chase replaces it as commands do today.

- Per-player **controller** (`"human"` / `"ai"`) is new authoritative player state set at `add_player`, included in snapshots. Skirmish: P1 human, P2 AI. Scenes without a match default to human.
- Vision ranges go into combat definitions next to weapon range, labelled source-supported; modifiers as named constants citing `AIData.ini`.
- Explicit `attack` orders are unchanged.
- Builder's call: scan cadence. Retail `MoodAttackCheckRate` is 250 ms for infantry (about 8 ticks); keep or tighten the existing staggered `REPATH_TICKS = 15` cadence based on the Task 1 cost spike, and record the departure if 15 stays.

Deferred to M6: compare retail 1v1/8-player map sizes with our 48×32 cells before choosing the full-scale map (user asked whether a bigger map would help; answered: M6 scope). Deferred: AI moods (`MM_Mood_Sleep` returns 0, `AlertRangeModifier 1.1`, `AggressiveRangeModifier 1.5`) are recorded for M8 bots, user request 2026-11-03.

### 2. Opponent base defence (opponent script rule)

Zero Hour skirmish base defence lives in AI scripts, not read; this is a Wargrid rule, provisional. At every 30-tick decision, before and after `ATTACK_TICK`: if any enemy unit (non-collector) is within **10 cells** (provisional, my call) of any opponent building footprint, every opponent combat unit in `guard` with no target is sent with one explicit `attack` on the nearest such intruder (ID tie-break, grouped per target as `_attack` does). Defence takes priority over the attack wave for idle units; units already attacking, and units still moving to a rally point (mode `move`), are not overridden (my call). After its target dies an explicit attacker returns to `guard` where it stands (M4 behaviour); the next decision re-applies defence if intruders remain, otherwise the wave rule after `ATTACK_TICK`. An unreachable intruder follows existing `attack` behaviour (`blocked`).

### 3. Rally point per producer

- New command `set_rally {building_id, cell}`: owner's barracks or factory (completed or under construction), cell inside the map; rejects otherwise with a command result. Setting again replaces it; no clear command (user 2026-11-03). Rally is authoritative building state in snapshots.
- **Default rally** when none is set, so production never stalls: a deterministic cell 3 cells beyond the footprint edge facing the map's horizontal centre, on the footprint's centre row, clamped inside the map. Exact formula is the builder's call; it must be mirrored for P1/P2.
- The default rally is stored on the building when it is created, so the snapshot field is always present (`rally: [x, y]`, my call); `set_rally` overwrites it.
- On spawn, a produced infantry or tank receives an internal move (mode `move`, no command sequence) to its producer's rally cell through the existing move assignment and destination allocation, one unit at a time as it spawns, so units spread instead of stacking; it ignores enemies until it arrives, then is in `guard` (my call, same as a player move today). If the rally cell is blocked, a building, or in another navigation component, existing allocation picks the nearest reachable free cell; if none exists the unit stays at its spawn cell in `guard` (old behaviour). Collectors keep M3 behaviour.
- `controller` is an optional `add_player` argument defaulting to `"human"`, so existing callers are untouched; changed snapshots mean replay traces are regenerated and compared, not migrated.
- Controls: building selected + right-click ground sets rally; marker drawn while the building is selected. Opponent uses the default rally only.
