## New findings

### SEC-04 (Low): a main file that exists but cannot be opened falls through to the older .bak, and records can roll back for good

**Owner:** ui-systems-dev (src/save/save_service.gd).

**Code.** `_read_json` (line 338) returns UNREADABLE when `FileAccess.open` fails or the read comes up short. `load_run` (lines 212 to 226) and `load_profile` (lines 305 to 315) then skip the main file without deleting it and go on to the .bak. The header comment of `load_run` says a file that cannot be opened "is left alone, because the cause may not last". The file is left alone, but the older copy is used anyway.

**Steps to reproduce (done, in user://sec3_lock).**
1. Through SaveService, save the run with score 100 and then 200, and the profile with Best Score 1000 and then 2000. Result on disk: run.json 200, run.json.bak 100, profile.json 2000, profile.json.bak 1000.
2. From a PowerShell process I started, open run.json and profile.json with `FileShare.None` and keep them open for 25 seconds.
3. While they are held, start the real App on that folder. It warns "using the last good copy" twice, holds the run at score **100**, and shows Best Score **1000**. Back on the splash saves the profile: the rename fails, so the profile at 1000 stays in profile.json.tmp.
4. After the hold ends, a fresh load returns run 200 (the run was never written, because Play was not pressed) but Best Score **1000**: the valid temp file wins, as the temp wins rule says. Best Score has dropped from 2000 to 1000 for good.

If Play had been pressed in step 3, the run would have continued one move behind and its next saves would have replaced the newer run.json.

**The same window shows up after a process ends.** In my hard kill test (below), the orchestrator's own first read of a save file failed in 9 of 240 rounds, within milliseconds of the killed process being reported as ended. The files were valid moments later, and SaveService's read, a little later still, loaded the newest file in every round I could check. So on this Windows machine a save file can be briefly unopenable right after a process ends, which is the case this finding is about.

**Why it matters.** A .bak can win over a newer valid file, which the brief asks about directly. The damage is one move of the run, or a Best Score and Best Tile rolled back by one save. It needs another program to hold the file open without read sharing, or a failed open, at the moment of launch. That happens on Windows (backup, sync or antivirus tools, or the short window above). On Android, no other app can open SumUp's private files, and open() on its own file fails only on errors such as running out of file handles or an I/O error. Windows is the development platform, not a target, so the rating is Low.

**Not new, and the .bak makes it smaller.** Before SEC-02, an unreadable profile.json loaded defaults and the next profile save wrote them back, so the records went to zero. An unreadable run.json gave no run, so Play started a new one over it.

**Possible fixes.** Treat UNREADABLE as "do not decide now": skip the .bak while the main file exists but cannot be read, and do not write that file in this session. Or retry the open a few times before falling back.

### SEC-05 (Low): a save file full of invalid UTF-8 is slow to refuse, and the .bak adds one more such file

**Owner:** ui-systems-dev (src/save/save_service.gd).

**Code.** `_read_json` line 362 calls `bytes.get_string_from_utf8()` on up to 65,536 bytes. For every invalid byte, Godot logs a "Unicode parsing error" line. The NUL check and the nesting check run first, but bytes from 0x80 to 0xFF pass both.

**Measured (headless, this PC, one 65,536 byte file of bytes from 0x80 to 0xFF):**

| Output | One load_run |
|---|---|
| Discarded (`>/dev/null`) | 0.57 s with random high bytes, 1.18 s with all 0xFF |
| Written to a log file through a Bash redirect | about 90 s per file |

With all six files (run and profile: temp, main and .bak) filled this way and the log written to a file, `load_profile` took 260 s and `load_run` 368 s, 628 s in all, with 238,068 log lines. The result was correct: no run, defaults, every bad file deleted except profile.json. A broken profile.json is kept by design, so it costs the same again at the next launch until a profile save replaces it.

**Why it matters.** At launch this runs on the main thread before the splash shows, so on the phone it could last long enough for Android to report the app as not responding. I could not measure it on the phone, and how fast logcat takes these lines there is unknown. Making such a file needs write access to the app's private folder (root, or run-as on a debuggable build), or storage damage that writes high bytes rather than zeros, which is rare. Someone with that access can delete the saves anyway, so the impact is availability only. The .bak adds a third file per save that can be read.

**Possible fix.** The game writes pure ASCII (digits, keys and lower case skin ids), so refuse any byte at 0x80 or above before decoding, as is already done for NUL. A UTF-8 byte order mark is accepted today, so allow those first three bytes if they should stay valid.

## Earlier findings

### SEC-02: fixed

**Owner:** ui-systems-dev (done).

What the code now does (src/save/save_service.gd at e2e2904):
- `_write_file` calls `file.flush()` before `close()` (line 525). The comment there is right that this is not an fsync, because Godot exposes none.
- `_move_into_place` (line 543) renames the current main file to `.bak` only when it holds exactly the bytes in `good`. `good` is set only by a rename into place (line 554) or by a load that found the main file valid (`_set_good`, lines 216 and 307). A load from the .bak never sets it.
- Loading order for both files: a valid temp, then a valid main, then a valid .bak. The .bak goes through the same `_read_json` limits (1 to 65,536 bytes, no NUL, nesting of at most 16) and the same SaveCodec checks. A run .bak that parses but is invalid, or is broken, is deleted (lines 227 and 228), and so is a profile .bak (lines 316 and 317).
- `delete_run` (line 237) clears `written`, `stuck` and `good` for the run, then discards the temp file, then the .bak, then the main file.
- `has_run` counts the .bak. Shipped code never calls `has_run`; only tests do.
- ARCHITECTURE.md section 10 and GDD 15.1 (LG1 to LG4, SP8, SP9, AT-154) describe the same behaviour.

How I checked it is in sections 1 to 3 below. What I could not check is a real power cut on the phone: whether a renamed or deleted file comes back after a crash depends on the phone's file system. See observation 2.

## Observations (not rated)

1. **A profile.json with one bad field loses to an older but fully valid .bak.** For example, profile.json holds Best Score 2000 with `sound_on: "yes"`, and the .bak holds 1000: the profile loads 1000. That is what ARCHITECTURE.md section 10 specifies. The game never writes such a file, so only damage or editing gets here, and a held run's score is then folded back into the records. **Owner:** ui-systems-dev, for awareness. If wanted, the records could take the larger of the two values.
2. **Power loss after a run ends.** `delete_run` removes the three files without any sync. If a power cut undid those deletes and also emptied the newly renamed run.json, the .bak would bring back the run one move before its end. A player could then replay that last move, nothing more. It cannot be tested without the phone, and no security property depends on it.
3. **A folder named run.json, profile.json or one of their temp names** makes saves fail. The newest save then stays in the temp file and wins the next load, or the last good file stays. Same as in round 2: only something with access to the private folder can create one.
4. **Round 2 observation 4 (the tap check could hang the suite) is addressed.** tests/design/test_tap_input.gd now starts the child with `OS.create_process`, waits with a deadline, and ends only that child with `OS.kill(pid)`. Its comment says the child exits 0 only when every expected check ran. I read the code but did not inject errors this round.
5. **Round 2 observations 1, 2, 5, 6 and 7** (the score wall, Shuffle spending free boosters on a hand made board, the NOTICE wording, the 256 KB license cap, the duplicate provider authority) are unchanged, and nothing this round touched them.
6. **The debug manifest declares `android:permission="android.permission.DUMP"` on a receiver.** That is androidx's ProfileInstallReceiver from Godot's template. It is a permission that callers of the receiver must hold, not one the app requests. **Owner:** platform-dev, for awareness.

## What I checked and found clean

### 1. The save combinations, through the real SaveService

A driver in the session scratchpad wrote every combination into its own user://sec3_save folder. For each case it loaded with two fresh services (two launches), then ran save_run or save_profile, loaded again, and for the run called delete_run and loaded once more.

**Run: 1,280 combinations, all run.**
- run.json.tmp: none, valid (score 300), empty, cut in half, free_used 99, valid plus NUL, 5 MB, a folder.
- run.json: none, valid (200), empty, cut in half, 2000 random bytes, valid plus NUL, free_used 99, a top level array, 30,000 `[`, a folder.
- run.json.bak: none, valid (100), valid with a higher score (777,777), valid padded to exactly 65,536 bytes, empty, cut in half, random bytes, 5 MB, 65,537 bytes, 30,000 `[`, 17 levels, valid plus NUL, free_used 99, a top level array, UTF-16, a folder.

Results:
- **Every case without a folder (1,120) passed.** The load was always the first valid one of temp, main and .bak, in that order, and the same on the second launch. A .bak with a higher score never beat a valid temp or main.
- No temp file was left after a load.
- The next save loaded back.
- **After delete_run: no file left, `has_run` false, nothing loads.** That includes every case where a valid .bak or a hostile "higher" .bak was present before.
- The 160 cases with a folder named run.json behaved as observation 3 says: save_run reports false and the new run stays in the temp file, which loads.
- The 160 cases with a folder named run.json.tmp: save_run fails and the last good file stays.
- No script error.

**Profile: 696 of 756 combinations.** The kinds were as for the run, with a "bad field" profile whose sound_on is a string, and a .bak whose Best Score is 9,000,000,000,000,000,000. My 900 second time limit stopped the driver early, mainly because of the logging cost in SEC-05. The 60 cases not run all have a folder named profile.json.tmp; 66 such cases did run, and they behaved like the run's.
- Every case without a folder passed: valid temp, then fully valid main, then fully valid .bak, then the valid parts of the main file, else defaults.
- A hostile high .bak never beat a valid main or temp.
- No temp file was left.
- The next save loaded back.

**Size and depth on the .bak path.** The .bak goes through `_read_json` like the other files. 5 MB and 65,537 bytes were refused without being read. 30,000 `[` and 17 levels were refused before parsing. Exactly 65,536 bytes was accepted. Apart from SEC-05, every load took under 35 ms.

**Rotation.** After a load from the .bak, the next save writes run.json and leaves the .bak as it was, because `good` is unset. Only a later save moves that new run.json to the .bak. A file changed on disk after it was loaded is never moved to the .bak. The tests in tests/save/test_save_backup.gd cover the same points and pass.

### 2. Hard kills during the two renames

A child Godot process saved the run and the profile in a loop: save_run, queue_run, or queue_run with flush, in turn. Every 2 to 8 saves it called delete_run and started a new "run" with higher scores. The orchestrator ended the child by its own PID at a random 1 to 600 ms after it started saving. It then compared what loaded with the files on disk.

- **240 rounds in two batches of 120, and no wrong load.**
  - In batch 2, which had full diagnostics, all 4 flagged rounds were cases where the orchestrator's own first read of a file failed and the file was valid 1.5 seconds later. SaveService loaded the newest file every time. This is the window in SEC-04.
  - Batch 1 had 5 flagged rounds with the same pattern. For the two run.json cases in batch 1 I cannot tell whether the load came from run.json or from the .bak, because that batch printed no diagnostics.
- **The kill left these files (batch 2), and every combination was handled correctly:**
  - all three run files;
  - temp and main;
  - main and .bak;
  - the temp alone (the Windows rename gap);
  - temp and .bak (a kill between the two renames);
  - main alone;
  - none (a kill after delete_run);
  - and the same for the profile.
- **A valid .bak alone, with no main and no temp, never came up in any round**, so a kill never makes the game go back one move.
- A valid temp file was always the newest, a valid main was always newer than a valid .bak, and a deleted run never came back.

### 3. The splash flow, in a real App (user://sec3_app)

- **A damaged run.json with a valid .bak.**
  - The .bak run is held, its score is folded into Best Score, and the damaged run.json is deleted.
  - None of these changed any run file, byte for byte: app pause, focus out and close request, Settings with a skin switch and a sound switch, Info, About with a license text opened and closed, and back on the splash, which quits.
  - On restart the .bak run is held again, and Play resumes it at the same score.
- **An ended run (Board D1024, nothing usable) only in the .bak:** Play ends it at once, every run file is deleted, and a restart holds nothing.
- **The ended run in run.json with a playable older run in run.json.bak** (a kill between the last move's save and delete_run): the ended file loads, Play ends it, and both files are deleted. The playable .bak never comes back.
- **A hostile set at launch:**
  - run.json.tmp of 30,000 `[`;
  - a 3 MB run.json;
  - a run.json.bak with free_used 99;
  - a profile.json.tmp with best_tile 99;
  - a profile.json.bak of 20 levels.

  The App started in 25 ms. It held no run, kept the real profile's records and deleted every run file.
- **A damaged profile.json with a valid older .bak (Best Score 400) and a run at 500:** Best Score is 500 after the fold.
- **A run held from the .bak, then Play:** the resume writes run.json, and the newest save loads.
- **Code review of src/ui/app.gd.**
  - `_held_run` is only read in `_on_play`, cleared in `_on_play`, `_start_new_game` and `_go_home`, and never written to disk by the App.
  - `_save_all` and `_on_save_requested` save the run only while `session.is_run_in_progress()`, which is false in Phase NONE (the splash before Play) and ENDED.
  - The only `delete_run` call is in `_on_run_ended`.
  - Back on the splash calls `_save_all` and quits, so a held run's files stay exactly as they were.
  - `load_profile` runs before any listener is connected.
