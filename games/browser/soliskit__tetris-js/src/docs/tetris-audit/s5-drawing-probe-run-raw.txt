Semantics: EVERY attempted fill call is recorded BEFORE forwarding, as
{t, c}; the armed call is recorded as {t, c, threw} and is NOT forwarded
(it paints nothing). Counts are therefore attempted calls, not verified
paints. Storage writes are recorded by key (no values kept). t is
milliseconds from instrumentation install.

Terminology: a "frame group" below is a group of attempted fill calls
sharing a timestamp (or timestamps 1 ms apart). The recorded throw and
the later calls are distinct timestamped records. Actual
animation-frame boundaries are unmeasured: these groups are labeled by
their timestamps, not established as single requestAnimationFrame
callbacks.

What the trace does and does not establish:
- Observed: in both trials, the recovery frame group contains
  attempted fill calls to all three next previews (next0/next1/next2,
  4 calls each) alongside the board calls.
- Not measured: queue identity, engine state, and frame boundaries.
  Module state is unreachable from the page console; the frame groups
  above are timestamped groups of attempted calls, not instrumented
  requestAnimationFrame callbacks; and the fill wrapper records each
  call BEFORE forwarding it to the native method, so counts are
  attempted calls, not verified paints.
- Unexplained: trial A's first in-window frame drew 9 board fills. Under
  the source painting model (drawBoard script.js:167-202 fills once per
  occupied locked cell and once per active-piece cell through drawBlock
  :140-143; the ghost piece is stroked only, :153-163) a board-drawing
  frame's fill count is locked-cells + 4, which cannot yield 9 in this
  trial's first in-window frame.
  Because the trace itself contains a count the model cannot explain,
  no count-based exclusion is made: whether a lock occurred on either
  errored tick is not established here, and a lock would shift the
  next queue and paint the previews for the ordinary reason.
- Established independently of the counts: no resize event and no
  canvas width/height attribute mutation was recorded in either trial
  window, so the two resize-path cache-clearing routes (ResizeObserver
  script.js:400-406; pixel-density :411-414, both through sizeCanvas)
  did not fire; and no input was sent during the windows, so no hold
  action occurred.
