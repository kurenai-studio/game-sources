## 1. Findings

### Minor

**m1. Killing the app in the foreground mid-wave undoes the wave in a run.** Owner: ui-engineer (src/ui/battle_screen.gd), with a contract change to ARCHITECTURE 5.1 through the DM.

- Steps: start a run, pick a card, tap Start wave 2, wait 9 s, then `am force-stop io.github.bartbasi.forkline` with the game in front. Relaunch, Play, Continue.
- Result: the run comes back in the build phase before wave 2 (tick 629, 75 gold, wave 2 not started). The save written at the kill moment does not exist. The player can move towers and gates and play the wave again. Screenshots `19_w2_before_kill_s.png` (mid-wave, 7 Scamps on the map) and `21_resumed_after_fgkill_s.png` ("Start wave 2", Pause menu). Save snapshot `saves\s19_w2_fgkill\game_run.json`.
- Cause: starting a wave is not a save point. The saves are at `build_started` (battle_screen.gd:816), a card pick (1128), `pause()` (330) and the Paused strip's Menu (338). ARCHITECTURE 5.1 lists no save at wave start.
- Why it matters: ARCHITECTURE 6 says "Killing the app undoes nothing, so it cannot dodge a run loss or retry a daily." That holds only when the kill comes after a focus loss. Every normal way out (Home, recents, swiping the app away, Force stop in Settings) causes a focus loss first, and that path came back exact (section 2). So this needs a crash, an out of memory kill in the foreground, or adb. It is the same cause as q1 of 2026-10-26, but in a run or daily it replays a wave, not just a few seconds.
- Suggestion: also save when a wave starts. That is one write per wave, and a kill would then come back at the wave's start with its setup locked in. Bart decides whether that is worth it.
