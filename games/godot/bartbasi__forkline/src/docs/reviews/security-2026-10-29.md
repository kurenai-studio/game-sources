## New findings

### Low

**L7. A published test build is built from the working tree, which other agents use for uncommitted work.** Owner: release-engineer (scripts/build.sh, scripts/build_release.sh, docs/release.md), with the DM, who runs the release steps.

Where: docs/release.md:239 builds the GitHub APK with `bash scripts/build.sh`, which exports from the repo root (scripts/build.sh:19 and 74). scripts/build_release.sh exports the AAB and the release APK from the same root (line 118). Neither checks that the tree matches a commit. check_apk.sh compares the APK with the data/ folder of the same tree, so it passes a build made from a dirty tree.

Steps: today the working tree holds 9 changed and 8 new data files (stats, cards, run.json, packs, the segment index, campaign.json, r7_l1 to r7_l6 and two new segments). Following docs/release.md now would publish region 7 and the changed stats and cards under a tag at ed0ff35, which has none of them. The coupling shows in reverse too: the repo's check_apk.sh failed my clean APK of ed0ff35 with 8 "missing from the APK" lines, all of them the working tree's uncommitted files. The same script inside the clean copy passes it.

No past release was affected. I downloaded v0.1-test3 (its checksum matches the published one) and compared it with its tag, 913b19a. All 52 data files are byte for byte those of the tag, and 289 of its 294 assets, every compiled script among them, are byte for byte a fresh export of a clean copy of 913b19a. The other 5 differ only in the project name (my copy's rename) and import time ids.

Why it matters: Forkline is GPL software, and testers install these builds. The source of a published binary must be its tagged commit. Uncommitted work has not passed the suite, a review or the DM's integration. The same steps will build the Play bundle.

Fix: build release files from the same clean `git archive` copy the suite passed on. Or make build.sh and build_release.sh stop when `git status --porcelain` lists anything (at least under src/, scenes/, data/, icons/, project.godot, export_presets.cfg, LICENSE and NOTICE), and print the commit they built, for the release notes.

**L8. Three numbers that play makes grow load right up to their ceilings.** Owner: sim-engineer (src/sim/battle.gd). Contract: ARCHITECTURE 5.6.

Where:
- `next_id` loads up to 2^31 (battle.gd:2588), and each new creature adds 1 (battle.gd:2191).
- `tick` loads up to 10^9 (battle.gd:2528), and each step adds 1 (battle.gd:283 and 288).
- A tower's `spent_now` and `spent_before` load up to 10^9 (battle.gd:2720 and 2721), and each purchase adds its price (battle.gd:2030 to 2034, and 463 when a wave starts).

None of them is clamped in play, the way gold is. These load checks have not changed since round 1.

Steps, each on a real r5_l3 save (Relaxed, two waves running, tick 300), through text and `SavedGame.from_data`:

1. `next_id` set to 2,147,483,648. It loads. 400 ticks later the save the game writes holds creatures with ids from 2^31 up and `next_id` 2,147,483,666, and its own check refuses it: "next_id: must be 0 to 2147483648".
2. `tick` set to 10^9, with `wave_start` and every absolute timer moved by the same amount. It loads. After one tick the next save is refused: "tick: must be 0 to 1000000000".
3. One tower's `spent_before` set to 10^9. It loads. One upgrade makes it 1,000,000,110, and the next save is refused.

Each time, the next launch deletes the saved game. The mutation run found the first case on its own, twice, both in a daily (mutations 1,204 and 2,416 of seed 20261029). No id is stored in a 32 bit array anywhere, so nothing wraps.

Why it matters: it is round 2's L6 in another shape. A save that loads leads, one save later, to a game the app deletes. Same threat model: only someone who can write the app's private files. No real game comes near these numbers.

Fix: the rule the contract already uses for progress counters (5.5): the game never writes a value its own check refuses. Clamp `spent_now` and `spent_before` at 10^9 the way gold is (`mini(..., BIG)`). For `next_id` and `tick`, a load ceiling alone cannot do it, because play keeps adding: stop at the ceiling instead, for example by spawning no new creature once `next_id` would pass 2^31 and ending the battle as lost once `tick` would pass 10^9. Only a tampered save can get there, so nothing changes for players.

### Note

**N12. A save can name a content tier above the player's.** Owner: roguelite-engineer (src/run/run_session.gd) and sim-engineer (src/save/daily_record.gd). Contract: ARCHITECTURE 14.7 and 14.8. As the contract says.

Where: run_session.gd:210 reads `tier` from 0 to run.json's tier count. daily_record.gd:59 keeps a daily.json tier from 0 to `RunData.MAX_TIERS` (4). Neither is compared with `Progress.tier()`. app.gd:328 to 338 takes the saved daily's tier, else the record's tier for today, else the player's, clamped to the tier count. On Restart, app.gd:769 starts that day's daily again at the saved tier, and app.gd:1007 records it.

Steps: a real tier 0 run, two waves in, with `tier` set to 2 and the four tier 1 and 2 cards added to its pool, loads. A daily saved at tier 0 and relabelled tier 2 the same way loads too. Its map stays the tier 0 map, because a saved map is not tied to its seed (round 1, N1). Restart then starts the real tier 2 daily of that day, and `record_finish` stores tier 2 for the day, so the Daily button offers tier 2 for the rest of the day. A daily.json with today's day and tier 2 does the same with no game file. Refused, as they should be: a run tier of 3 (run.json has 2), -1, 1.5, "1", null, true and 1e300, and a save with no `tier` key whose pool holds a tier 1 card. A daily.json tier of 4 is kept, then clamped to 2 at every use, so nothing breaks.

Why it is a Note: it is offline cheating with real content, the same class as round 1's N1. Nothing crashes and nothing leaves the phone. Suggestion: keep it as it is. Do not tie a saved tier to `Progress.tier()` at load: in a launch where progress.json is locked, progress falls back to its defaults (tier 0), and such a check would delete every honest run and daily saved above tier 0.

**N13. The privacy policy's settings line predates the music switch.** Owner: release-engineer (docs/store/privacy-policy.md:15 and docs/store/site/privacy-policy/index.html:38); the DM publishes gh-pages. Since 7b661fb settings.json also holds the music switch. The published policy still says "Your settings: whether sound is on." The switch is not personal data and never leaves the phone, so nothing is wrong in substance. Suggested line: "Your settings: whether sound effects and music are on." daily.json now also holds the day's content tier, which is not personal and needs no mention.

**N14. The upload password reaches Gradle on its command line.** Owner: release-engineer (docs/release.md). Godot 4.7.2's Gradle export passes `-Prelease_keystore_password=` to the Gradle process (the text is in the engine binary). So during a release export the password sits in a process command line that other programs run by the same Windows user can read. The engine also has a verbose message, "Build Android project using gradle command:". I did not check whether that message masks the password, and build_release.sh never passes `--verbose`. I found no copy of the password in the Gradle daemon logs under %USERPROFILE%\.gradle, in android/ or in .godot/ (counted, never printed). Suggestion: add to docs/release.md that the release export never runs with `--verbose`, and that no process listing or screen recording runs during it. Nothing to change in code.

**N15. The binaries in build/ predate the expansion (round 2's N11 again).** Owner: release-engineer. build/forkline-debug.apk, forkline-release.apk and forkline-release.aab date from 2026-10-27 07:30, before S8 and every expansion commit. They request no permissions. Rebuild before any install or upload, from a clean copy (L7).

**N16. ARCHITECTURE 6 says killing the app cannot retry a daily. With adb it can go back to the last save point.** Owner: architect (docs/ARCHITECTURE.md:1595). Every normal way out saves the current tick first, so Restart, a fold, Home, recents and the back button cannot dodge a loss (see "Restart, folding and leaving" below). But `adb shell am force-stop` with the app in front skips that save. It needs only USB debugging, not root, and works on release builds too. The next launch then resumes from the last save point: the wave start or a later pause. Tower commands work during waves, so that wave can then go differently. The second bullet of section 6 already describes this resume as intended. Suggestion: reword the third bullet to "it can only go back to the last save point, at most to the start of the current wave", so the contract promises no more than the game does.
