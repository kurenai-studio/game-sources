Introduction

Modern Gameplay adds the seven agreed features in order while keeping the game's
certification current. The intended direction is a modern Guideline-style feel:
a faster speed ramp, drop points, T-spins, combos and short delays. The owner settled
that direction on October 5, 2026. It is not an unresolved planning question.

The program changes gameplay deliberately, not by copying behavior from the
implementation. Each stage starts with exact requirements, an independent
review, a clean reference-model input pack and an evidence plan. Certify the
exact release candidate before merge and release. A green test run or a model
match alone is not certification.

The seven stages are rotation direction, gravity, scoring, level progression,
T-spins and combos, delays, then hidden rows. Back-to-back, perfect clears,
start-level selection and game completion are outside this program.

This is a separate post-certification charter. It does not rewrite the completed
audit blueprint. It is independent of CI mechanisms; its only CI dependency is
that CI Pipeline Optimization closes before feature implementation begins.
The order is the owner's G4 sequence, not an added meaning of D12.

The program does not claim full Guideline compliance. Its deliberate departures

13. S1 - Rotation direction

Expected requirement change:
PCE-4.

Proposed rule (R-S1):
- a requested clockwise rotation tries only clockwise SRS tests;
- a requested counterclockwise rotation tries only counterclockwise SRS tests, in order;
- if all requested-direction tests fail, the piece is unchanged;
- the opposite direction is never tried;
- O remains non-rotating.

Proposed fixed oracle: adopt the standard SRS wall-kick tables as an owner-adopted
fixed artifact: one table shared by J, L, S, T and Z, a separate table for I, none for
O. Record the exact source text, its SHA-256 and its scope before O8 construction.
Reason: PCE-2 already specifies "the standard Super Rotation System", so this adds no
new behavior and gives O8 a source independent of production data. Source:
https://tetris.wiki/Super_Rotation_System (third party; a pinned, checksummed copy is
required before any certification use).
Context fact, implementation not model input: the game stores one clockwise table and
derives counterclockwise kicks by negating the target state's clockwise data. This was
not verified against the published table. S1 must check it against the adopted
artifact; any difference is reported as a finding, never silently changed.
Alternative (not recommended): a custom kick table.

Reassess:
- PCE-4;
- PCE-6;
- PLY-6;
- SAF-6;
- O2;
- O7;
- rotation boundaries.

D18 B2 remains geometry only and does not supply kick data.
If Phase 1 has adopted fixed kick material by activation, reuse it.
Rule 2: old fallback protections are replaced, not merely removed; a test must prove
the opposite direction is NOT tried.
D31/D32: same categories of authoritative state; only the success/failure transition
set changes.
S1 is not expected to change the save format.

14. S2 - Gravity

Expected requirement change:
PLY-2.

Expected decision supersession/restatement:
- D18 B14 gravity interval;
- D21 S10 timing claim;
- D32 gravity operation only if one gravity operation stops meaning exactly one row
  (not the case under the proposed stage default).

Facts: today PLY-2 is max(0.25, 0.7 - 0.02 x (level - 1)) seconds per row (250 ms
floor from level 24). The Guideline-style curve is (0.8 - 0.007 x (level - 1))^(level
- 1) seconds per row. Computed: L1 1000 ms, L2 793 ms, L3 618 ms, L5 355 ms, L8 135
ms, L10 64 ms, L12 28 ms, L13 18 ms, L15 7.1 ms, L20 0.5 ms. Source:
https://tetris.wiki/Marathon (third party).

Proposed default (R-S2):
- PLY-2 means the requested delay between one-row falls, which is what D21 S10 already
  judges (requested scheduler delay). It does not promise an observed fall rate.
- Interval = max(the Guideline-style formula, 1/60 s), with the formula governing
  levels 1 through 13 and the 1/60 s floor applying from level 14 upward; no level
  cap. The 1/60 s value is a deliberate project gameplay/engineering cap that keeps
  the one-row gravity model at no more than about 60 requested gravity steps per
  second. It is not asserted to be a browser timer minimum.
- Soft drop is unchanged: one row per press, then every 50 ms (INP-2); each successful
  soft-drop step still restarts the gravity timer under PLY-3. Natural gravity
  continues at the current interval between repeats. Once natural gravity is faster
  than the repeat cadence, holding soft drop is not guaranteed to produce a strictly
  faster observed fall rate; no stronger rate claim is made.
- No multi-row fall, so no collision-skipping, intermediate lock states or
  elapsed-time clock reading; D29 clock-jump falsification is not newly triggered by
  S2.
Alternatives: true 20G at high levels (a gravity operation may move many rows; new
collision, lock and D31/D32 rules needed); or keep today's 250 ms floor.
The Marathon-style formula is the recorded proposed stage default. Q1 settles the
direction, not the exact stage requirement; Section 2A review and approval still
precede implementation.

Evidence:
PLY-2, PLY-3, INP-2, PLY-6, STA-2, SAF-4, SAF-6 and timer evidence.
S2 alone is not expected to change the save format.

15. S3 - Scoring

Expected requirement change:
SCO-1 and possibly SCO-3.

Proposed defaults (R-S3), Guideline-style scoring. Source: https://tetris.wiki/Scoring
(third party):
- line clears 100, 300, 500, 800 for 1, 2, 3, 4 lines, times the level in effect
  BEFORE the clear (today SCO-1 has no multiplier);
- soft drop 1 point per cell and hard drop 2 points per cell (alternative: no drop
  points);
- high score unchanged: stored on device, replaced only by a higher score (SCO-3).
  Delegated default: keep it. Alternative considered: a new storage name resets it.
  Return to the owner only if evidence exposes a material product-direction conflict;
- numeric domain: a valid score is a non-negative safe integer; every award saturates
  at the largest safe integer; the load check and the runtime invariant use the same
  bound. This ties arithmetic safety to the certified semantic domain, the accepted
  untrusted-save domain and the guaranteed representation, not to "normal play cannot
  reach it".
T-spin and combo scoring remains S5.

Because SCO-2 derives level from score, S3 alone creates score -> level -> later-score
feedback. S3 and S4 are proposed as one Release Group; neither is released alone
(Section 10). If separated, the S3-only feedback rule must be explicitly approved and
certified.

Reverify at S3 kickoff: the existing multiple-of-100 score checks. With drop points
the score is no longer a multiple of 100; every affected protection moves consistently
under rule 2 with replacement protection.
Cross-version: an older still-running version may reject a newer valid score or save
and withdraw it under current storage semantics. This is unverified until the S3/S4
save domain is specified; if true, G8 applies.
If drop actions score points: D31/D32 assignments for those operations gain score.
Relevant decisions: D18 B11, B14, B16.

16. S4 - Level progression

Expected requirement change:
SCO-2.

Potentially also:
STA-1, STA-4, STA-6.

Proposed default (R-S4):
- level increases every 10 lines cleared, starting at level 1 (Guideline fixed-goal
  progression, https://tetris.wiki/Marathon);
- one new authoritative value, total lines cleared, because level can no longer come
  from score without the feedback loop; same safe-integer bound as score;
- no level cap (gravity floors by S2);
- legacy saves (STA-6): level is derived from the saved score under the old rule, then
  lines cleared is set to (old level - 1) x 10. This is a default, described as a
  default and not recovered history; the stored legacy level stays ignored unless
  STA-6 is intentionally changed;
- if the new rule cannot represent an old level, the fallback returns to the owner with
  evidence.
Alternative: keep level = score / 1000 + 1 (no new state; S3 feedback loop remains).

Update:
- D16 state categories;
- applicable R1 validity;
- D18 B14;
- D18 B16;
- D31/D32 operation assignments.
Evidence: SCO-2, PLY-2, STA-1, STA-4, STA-6, SAF-1, SAF-6, display evidence.
Save: likely a new format (explicit version value per G5); whether it is readable by
older versions is decided after this rule is approved.

17. S5 - T-spins and combos

Expected:
- explicit T-spin recognition requirement;
- combo requirement;
- scoring extension.

Excluded:
- back-to-back;
- perfect clears.

Proposed defaults (R-S5). Sources: https://tetris.wiki/T-Spin and
https://tetris.wiki/Scoring (third party):
- recognition, Guideline 3-corner rule: on lock, a T-spin is awarded if the last
  successful maneuver of the T was a rotation and at least 3 of the 4 diagonal corners
  around the T's center are occupied (board edge and floor count as occupied). Mini:
  only one of the two front corners is occupied, unless the last rotation used the
  1-by-2 kick offset, in which case it is a full T-spin. Alternatives: no Mini; a
  different recognition rule;
- scores, times the level before the clear: Mini no lines 100, T-spin no lines 400,
  Mini single 200, T-spin single 800, Mini double 400, T-spin double 1200, T-spin
  triple 1600;
- combo: each consecutive lock that clears at least one line adds 50 x combo count x
  level, where the first clear in a chain has count 0; a lock with no clear resets the
  chain; a T-spin with no lines clear does not continue a combo;
- state: "last maneuver was a rotation" (and whether the last rotation used the 1-by-2
  kick) and the combo count. Persist the state required for exact STA-4 restoration.
  Current-piece T-spin rotation/kick metadata resets on a new piece or Hold. The combo
  count carries across pieces and Hold; it resets only when a lock clears no line, as
  defined by the combo rule above. Persist the combo count so Continue preserves the
  chain. Alternative considered: do not persist the needed history, which would
  require an explicit approved limitation because Continue could lose a pending T-spin
  or combo state.
Rule-first: this recognition rule is the stage's requirement text; state follows from
the rule, not the reverse.

Expected decision impact:
- D16;
- R1 predicates;
- D31/D32 assignments;
- D18 B16 if persisted.
Evidence: new recognition and scoring rows; PLY-6 where relevant; STA-4 if persisted;
SAF-1; SAF-6; dedicated falsification domains.
PCE-5 is not automatically affected merely because recognition occurs at lock.
Save: likely, if state is persisted.

18. S6 - Entry and line-clear delays

This stage changes valid-state, timer and operation semantics materially.

Expected conflicts/reassessment include:
- D18 B6;
- D18 B13;
- SAF-4;
- D23 U4;
- D22 T3;
- D32 lock operation;
- D33 C1;
- D33 C3;
- D34 E1/E2/E3.

Proposed defaults (R-S6):
- durations: line-clear delay 0.4 s and entry delay 0.1 s, fixed (not
  level-dependent). These are UNSOURCED starting values: the Guideline defines lock
  delay but leaves entry delay to individual games (https://tetris.wiki/ARE,
  https://tetris.wiki/Guideline, third party). They are proposed requirement values.
  Playtesting may generate a recommendation to change them, but once adopted they are
  observable gameplay behavior; changing them follows the normal requirement/change
  process and is not an implementation-only tuning knob;
- D33 C1 is preserved (option C1-A): the line-clear save is written only when the
  delayed transition reaches the completed-turn state with the next piece in place; if
  that turn ends the game, no save is written;
- pause during a delay completes the pending transition and then pauses (option P1):
  no new persisted phase and no new save format from S6. Alternative P2 (preserve the
  pending phase) needs a persisted phase and a new format;
- inputs during either delay: movement, rotation, Hold and drops are ignored (there is
  no current piece to act on); Pause and New Game still work. Alternative: buffer one
  input for the next piece;
- held controls when a delay ends: delegated default is the same rule as resume (D33
  C3, D34 E2): a held repeating control does not repeat until released and pressed
  again. Alternative considered: a held control continues across a delay;
- D34 E1 touch semantics remain unchanged; D34 E3 token representation stays
  non-normative.

Authoritative phase: engine must distinguish falling, line-clear delay and entry
delay. Representation is not predetermined; runtime handles do not define semantic
authority.
SAF-4 replacement preserves:
- invariant check after every action;
- invariant check after every covered timer;
- broken invariant handled like SAF-3;
- "Legal play never breaks one";
- every unaffected state invariant.
Phase/resource exclusivity is explicit: while falling, gravity runs and lock delay
runs exactly while resting, and delay timers do not run; during a delay only that
delay timer runs; paused or game over runs no covered gameplay timer, subject to SAF-3
cancellation-failure semantics.
D23 U4 is superseded to include delay timers; D22 T3 then applies to their
registration and cancellation. D18 B13 must include the semantic running states.
Each delay needs a timing claim; D29 applies only if elapsed time decides state.
Inputs during delays are decided for INP-1 to INP-6, PLY-7 Hold, touch, repeats and
gamepad.

D31/D32: lock no longer necessarily performs lock, line clear, scoring and next-piece
spawn as one operation; delay-completion operations are added. Assignments cover
board, falling piece, queue, bag, score, hold-used, reset count, lowest row,
progression, T-spin and combo history and save boundary.
Evidence: SAF-3, SAF-4, STA-2 to STA-6 as applicable, PLY-5 to PLY-8, INP-1 to INP-6,
DSP-8, SAF-6, timer evidence, malformed-state attacks.
DSP-3 is reassessed if the delay implementation changes idle redraw, storage or
frame-wakeup behavior.

19. S7 - Hidden rows

Define semantics before choosing a representation.

Proposed defaults (R-S7). Reference: the Guideline playfield has a hidden buffer above
the visible matrix (https://tetris.wiki/Guideline, third party); the project today has
PCE-1 (10 by 20) and PCE-3 (spawn in the top two rows).

The modern Guideline reference commonly describes a 20-row buffer above the visible 20
rows. The proposed 2-row hidden area is therefore a deliberate project departure, just
as the proposed any-hidden-cell lock-out is stricter than the common Guideline
lock-out rule. The reference is an input to the design, not a claim of Guideline
compliance.

- 2 hidden rows above the visible board; pieces spawn in them and fall into view;
- locked cells are never allowed in hidden rows: a piece that locks with any cell in a
  hidden row ends the game (lock-out), with no save, like STA-3. This is stricter than
  the Guideline, which requires the whole piece above the visible area, but it keeps
  the locked board 10 by 20;
- block-out: a new or held piece that cannot spawn in the hidden rows ends the game
  (STA-3 reading);
- kicks may move a falling piece into hidden rows; hidden rows are not drawn;
- persistence: under the proposed stage default, the saved locked board stays 10 by 20
  (no padding, no taller board). A pause save may hold the falling piece in a hidden
  row, so the valid persisted domain for current-piece position widens upward by 2. At
  S7 impact analysis, determine whether that semantic-domain change constitutes a new
  save-format/version boundary under G5 and whether any demonstrated older-version
  incompatibility triggers G8; do not preclassify it as merely a validation change.
Alternatives: more hidden rows; locked cells allowed in hidden rows (then the
persisted board is taller and the save format changes).

Expected requirements:
- PCE-1;
- PCE-3;
- PCE-6 as required;
- SAF-4;
- possibly STA-3.
Expected decisions:
- D18 B2;
- D18 B5 only if hidden rows become locked-board rows (not under the proposed stage
  default);
- D18 B6;
- D18 B9;
- D18 B14;
- D18 B16 if persistence changes;
- D17 item 15;
- D31/D32 domains and assignments.
If valid pieces can occupy rows above current row 0, lowest-row semantics and range
are restated. Reassess PLY-5, PLY-6, INP-5, DSP-1, DSP-8. DSP-2 and DSP-3 only if
canvas resolution or idle redraw behavior changes.
Do not assume a taller persisted board, padded old saves, a mandatory new format or
older-version incompatibility; those follow only from the adopted semantics.
